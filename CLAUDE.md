# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pure client-side "burn-down queue" for YouTube subscriptions: fetch subscription videos up to a moving cutoff and play/skip through them, oldest→newest. Three static pages, each with its own entry-point module — `index.html` (the queue), `stash.html` (a hand-curated second queue), `channels.html` (per-channel prefs). Vanilla HTML/CSS/ES modules — **no build step, no framework, no bundler, no `package.json` or `node_modules` in version control**: everything committed has zero dependencies, and deploy = merging to `main`, so anything landed there is shipped. The only runtime dependencies are two Google-hosted scripts (Google Identity Services, the YouTube IFrame API) plus the YouTube Data API v3, which is a REST endpoint (`API_BASE`) and never loaded as a script. Browser verification adds none — the Playwright **MCP server** installs nothing into the repo and writes only a gitignored `.playwright-mcp/` (`.claude/skills/browser-test/SKILL.md`).

## Working style — delegate, act as overseer

Act as an **orchestrator/overseer**, not the hands: research, design, implementation, review and verification go to **subagents (Agent tool) or a Workflow** rather than being done in the main thread, and they hand back compact results, not large file/output dumps. **This governs the top-level session, not the agents it spawns.** A subagent reading this is already the delegate: it does its brief directly and spawns nothing further — fan-out included, not just handing the whole brief to one more agent. This is the owner's standing instruction.

- **What decides it is whether the task has anything to discover — never how small the change looks.** A file to find, a pattern to sweep, a behaviour to verify, a judgement to make: that goes to an agent, because absorbing that context is what an agent is *for*. A change confined to a file already read in this conversation, needing no new file located and no design decision, is made in the main thread. **The bright line is "already read in this conversation"** — that is checkable, where "I already know how to do this" is not, and treating it as the test is how the discipline erodes into doing everything by hand.
- **Delegation costs a whole agent's context, so it is not automatically the cheaper path.** Answer one-shot browser questions — where focus lands, whether a rule went live, what something looks like — **inline** with the `browser-test` skill's MCP tools; delegate browser work only when it is genuinely build-and-verify.
- **A `fork` when the task's rationale lives in this conversation, a fresh agent when the task stands on its own.** A fresh agent has only its brief, so it re-derives what the conversation already settled — or acts on a lossy summary of it. Send it self-contained work; fork anything whose *why* is in the transcript.
- **Ask an agent for the verification the risk warrants, not all of it by default.** Mutation checks, measurement tables, both themes, both pages, long structured reports each multiply what the agent costs — the brief is the multiplier, not the tooling. Spend them where the claim is hard to see (a mutation check when a passing test might not be proving the fix, measurements when the claim is "nothing moved", both themes when the change is colour); otherwise just ask for the result.

- **Work goes on a task-scoped branch and lands by a SQUASH-merged PR**, so `main` keeps **one linear commit per task** and no merge bubbles. One task per branch: a feature must not arrive tangled with tooling setup or drive-by fixes. GitHub work is the **`gh` CLI** (it resolves the repo through the `github-branets` SSH alias unaided) — but **issues are still Linear's**, never `gh issue create`.
- **The PR title leads with the Linear issue id** when the work has one — `OWL-14: Walk the card menu with the same arrows that walk the cards` — and the body then names only the narrower scope (`Batch C.`) instead of repeating the id.
- **The PR body has two halves, and only the first survives the squash.** First a very concise summary — one-sentence bullets, detail only where genuinely unavoidable — ending with the `Co-Authored-By` trailer: that half **is** the commit message on `main`, so write it as one. Then `## Details` and any further sections, as verbose as the work warrants — rationale, verification, caveats — which stay in the PR. Pass both halves explicitly (`gh pr merge --squash --subject … --body-file …`), or GitHub composes a message of its own from the branch's commits. **Re-read the PR's live title and body immediately before merging** — `gh pr view <n> --json title,body`. The owner edits both, and a merge command built from the title you *created* the PR with silently discards that edit into `main`, where `main` is protected against force-pushes and only the owner can repair it. **The subject ends with the PR number in parentheses** — `OWL-14: Walk the card menu with the same arrows that walk the cards (#1)`. GitHub appends that itself when it composes the message, so passing `--subject` is precisely what drops it, and `main`'s history is inconsistent wherever it was.
- **Merging AUTO-CLOSES the linked Linear issue.** The id in the branch name and title is enough, so an issue tracking several batches flips to Done on the first one to land — check its state after every squash and set it back unless the whole issue really is finished.
- **Delete the local branch BEFORE merging the PR.** Push first, then from another branch `git branch -d <branch>` succeeds **without force** while `origin/<branch>` still exists — a branch fully merged into its **upstream** passes that check — and it refuses while commits are unpushed, which is the safety actually worth having. Then squash-merge, and GitHub removes the remote head branch itself, leaving nothing to clean up. For a branch merged **before** you got to it, `-d` refuses (a squash-merged branch was never an ancestor of `main`) and `-D` is correct: a missing `origin/<branch>` is itself the proof it merged, since GitHub deletes it only then. Branches **abandoned** rather than merged are renamed under `archive/` instead of deleted.

## Architecture

### The FLOOR vs live CUTOFF model (core domain concept)

Two distinct ISO timestamps, both in localStorage, are the heart of the app. Understand these before touching queue logic:

- **FLOOR** (`LS_START_CUTOFF` = `yqa_start_cutoff`) — the deletion + fetch boundary. As the queue burns down it **only ever advances**, and only inside `cleanup()`; the **one other writer** is the "Change cutoff" panel (`onSaveCutoff`), which sets it outright to whatever datetime the user picks — forward *or* backward — then recomputes the cutoff from the present records. It is the lower bound for the render list, the queue count, and the per-channel lower bound when fetching.
- **CUTOFF** (`LS_CUTOFF` = `yqa_cutoff`) — the live "handled-prefix" marker shown in the stats. **Bidirectional**: `computeCutoff(records, floor)` recomputes it from scratch each call, so it advances as you mark the oldest videos handled and **retreats** when you un-mark one. Always `>= floor`.

`computeCutoff` walks the contiguous *handled* (`state !== 'new'`) prefix strictly after the floor and stops at the first `new` video. It is **tie-safe**: the returned cutoff is always strictly less than the earliest still-`new` video's `publishedAt`, so a handled video sharing a timestamp with a `new` one never pulls the cutoff onto it. Window membership is **strictly after** the cutoff.

`cleanup()` (in `subscriptions-page.js`) is the **only** place videos are deleted, and the only place the floor *advances on its own*: it deletes every present record with `publishedAt <= cutoff`, then sets `floor = cutoff`. Three sites: page-load `init()`, after a refresh sync, and the "Trim front" button. Consequence, with Hide-marked **off**: marked videos stay greyed *in place* (never reordered/removed) until the next cleanup prunes the whole handled prefix. With it **on** the card leaves the list the moment it is marked.

### The Stash (`stash.html`) — a second queue, deliberately outside FLOOR/CUTOFF

The Stash is a hand-curated companion queue, filled one video at a time — a pasted YouTube link on its own page, or a card's "Add to stash" on the subscriptions page. Nothing is fetched **by subscription** (a pasted link does cost one `getVideosByIds` plus an avatar lookup), nothing is deleted by a moving boundary, and **neither the floor nor the cutoff exists for it** — there is no stash timestamp in localStorage at all. Why it can do without them:

- **Order is arrival order.** `sortStash` sorts by **`addedAt`**, oldest first — *not* `publishedAt` — ties broken by `videoId`, with a missing/unparseable `addedAt` sorting **last** (an unstamped record is foreign/hand-edited data, and the tail is where it does least damage). It is the stash's **single sort site**: drag-to-reorder adds an `order` field and changes **only that function**.
- **Deletion is state-based, not position-based.** `stashToClean` returns every handled (`state !== 'new'`) record from **anywhere** in the list, gaps included; `videosToClean(records, cutoff)` is position-based (`publishedAt <= cutoff`) and can therefore only ever delete a contiguous **prefix** — that difference *is* the reason the burn-down queue needs a moving floor and the stash needs none. One implementation (`sweepRemoved()`) backs **both** the "Clean up" button and an on-reload sweep that runs **before the first render**, so a removed card never flashes on screen.
- **No third state.** The mark button reads **"Remove"** but stores the same `STATE_SKIPPED`, so `"handled" means state !== 'new'` holds on both queues. The label is display only (`renderQueue`'s `skipLabel`) and the `btn--skip` class is unchanged, so `setCardState` and the CSS keep working.
- **No dependency on `yqa_channels`.** A stash record carries its own `channelAvatarUrl` and `stashChannelInfo` prefers it over the map, so `pruneChannels` dropping a channel entry can never blank a stashed card. The map stays as the **fallback**, and is not dead code: records stashed before avatars were captured, and ones whose avatar fetch failed, carry none of their own.
- **Adding respects a channel's preferred speed but ignores its Ignore flag.** `addToStash` fills `preferredSpeed` from the channel only when the record has none (`undefined` *or* `null`) — the same fill-if-absent rule as a refresh. It reads the **leaf `channelPreferredSpeed`, never `applyChannelSpeeds`**, precisely because that one excludes ignored channels: **Ignore governs what gets *fetched* by subscription, and nothing here is fetched by subscription.**
- **A duplicate keeps its place, and adding it again still means something.** An already-stashed videoId never moves, is never re-stamped and is never refreshed from the incoming copy — but exactly two fields can change. It is **revived** if it was marked Remove (`state` back to `new`): the alternative is to silently do nothing to a record the next Clean up deletes. And a **present *and different*** incoming `preferredSpeed` (neither `undefined` nor `null`) **overrides** the stashed one — re-adding at the same speed reports `changed: false` and hands back the same array by identity; the paste-a-link flow carries no speed, so there it degrades to "keep what the stash has". A duplicate is deliberately **not** run through the channel-prefs fill — it went through that when first stashed, and a channel speed set since is not a statement about a video already sitting here. `changed` is what a caller persists on; `added` only picks the toast's wording, which must say when a re-add touched something.
- **The second way in costs no network and no auth.** `addCardToStash` in `subscriptions-page.js` — the card menu's one item, or the `t` key — runs the same pure `addToStash` over a freshly-read stash and freshly-read prefs, then one `putStashVideo`; the record is already complete and the avatar comes free from `state.channels` (the key **omitted entirely** when there is none, never an explicit `undefined`). The record **carries its own `positionSeconds` across**, so a part-watched card resumes in the stash where it was left; the PLAYING card is flushed first (`flushProgress`, gated on `isReady()` — before onReady `getCurrentVideoId` is already set while `getCurrentTime` can still answer 0, which would persist a 0 over the position being copied), since the poll writes only every 5s. Two rules to preserve: the stash write happens **before** the source card is marked, so a failed write leaves the card untouched and there is nothing to revert; and an already-stashed video is still marked whatever the add did over there. **The one thing that moves ahead of the write is FOCUS** (`advanceFocus`, i.e. the `t` key), because a cursor still on the card makes the next `t` re-stash it — the *mark* still waits, and the `catch` puts focus back, so "leaves the card untouched" holds for the keyboard too. The mark is `setVideoState(id, STATE_SKIPPED)`, never `toggleSkip` — a mark, not a toggle, so the menu cannot un-skip an already-skipped card.
- **It syncs across tabs, and the merge protects only what is mid-write.** `index.html`'s "Add to stash" writes this store from a tab holding a *different* lock, inserting **or updating**, so a Stash tab's list can already be stale; on the signal `store.js` posts for every committed `stash` write, `stash-page.js` re-reads and merges with the pure `reconcileStash(current, fresh, inFlight)`. The signal is **coalesced, never acted on directly**: a `syncPending` flag defers the re-read by `STASH_SYNC_COALESCE_MS`, so a burst of writes in the other tab costs **one** read and one render, not one of each. It takes **MEMBERSHIP from `fresh`, and CONTENT from `fresh` too — except for the videoIds this tab has a write IN FLIGHT for**, whose local objects are kept untouched. Do not "simplify" that exception into a wholesale replace: this page marks **optimistically**, so for the length of that write disk is behind memory for that videoId, and adopting it would silently un-mark the card the user just clicked. It **must not be widened back to "every videoId we already hold"** — the other tab *updates* existing records now, so a record this tab is not writing has to be free to change out from under it, or a remote un-mark would never land here. The scope is `inFlightWrites`, refcounted (two writes for one id can overlap) and bracketed around the module's single `putStashVideo` helper. `changed` covers **membership moving OR a record we hold coming back with different content**, and **no change means no re-render at all**; a re-render goes through `renderKeepingPlace()`, which restores an **absolute** scroll offset and re-focuses the same control in the same card, skipping hidden subtrees (a closed menu's panel) so focus cannot fall to `<body>`. It takes that offset through `page-chrome.js`'s **`captureQueueScroll()`**, which reads and writes **whichever element actually scrolls at this width** — the pane wide, the **document** stacked, where `.workspace__queue` is `overflow: visible` and its `scrollTop` is permanently 0. Reading the pane directly saved a 0 and restored nothing, leaving the correctly-refocused card ~6000px below the fold; the 1080px breakpoint is a media query over there and **must not be re-asked here**. **Not `page-chrome.js`'s `renderKeepingAnchor` — do not merge the two.** An absolute offset and a same-control refocus are exactly right *here*, where membership can only grow (the other tab inserts or updates, never deletes), so the anchor cannot vanish and focus never left the list; they are exactly wrong wherever membership SHRINKS — the Hide-skipped toggle, and **this page's own Clean up**, whose sweep takes handled records from anywhere in the list so the anchor itself can be one of them. The two live side by side in `stash-page.js` and are not interchangeable: sort them by whether the anchor can vanish, never by which one is nearer.
- **Only the stash syncs, and only one way.** `videos` has a single writer that the `yqa_tab` lock keeps single, so a `videos` broadcast could never have a consumer; and `subscriptions-page.js` subscribes to nothing in return, holding no stash state. **Do not generalize it into a per-store mechanism.**

`parseVideoId(input)` is the front door: anchored regexes, **not `new URL()`** (which throws on the protocol-less input we must accept, and a bare id is not a URL at all), covering `/watch?v=`, `/shorts|embed|live|v/`, `youtu.be/`, and a bare 11-char id, with lookalike hosts ruled out by the `^` anchor. Its sibling `parseStartSeconds` reads the same paste's `t`/`start` seconds (a plain count only, `0` and a composite `1m30s` alike being null) and seeds `positionSeconds` on a **new** record, the same field the player writes, so the first watch overwrites it; a **duplicate ignores it for free**, the short-circuit keeping only the videoId and `addToStash`'s duplicate branch reading nothing else either. All six helpers are pure, live in `queue.js`, and have tests.

### Module layering (respect these boundaries)

Data flows `auth → api → store → queue → ui/*-page.js → player`. That arrow describes **data and ownership, not the import graph**: `api.js` imports `uploadsPlaylistId`/`compareIso`/`parseIsoDuration` back out of `queue.js`, which is fine precisely because `queue.js` is pure — being pure is what makes it importable from anywhere. There are **three entry points**, one per page, all named `*-page.js`: `subscriptions-page.js` (`index.html`), `stash-page.js` (`stash.html`), `channels-page.js` (`channels.html`); `page-chrome.js` is the leaf chrome all three share. All three carry the same nav strip and the same `<h1>` "YouTube Queue" — page identity comes from `aria-current` + `<title>` + the tagline, not from the heading. Each module owns one concern:

- `config.js` — constants only (storage keys, `API_BASE`, `OAUTH_SCOPE`, states, tunables, the IndexedDB identity), each declared **exactly once** for the whole app; no module redeclares one locally. A **retired** key is the one exception, having no live constant left to point at: `migrations.js` names `yqa_playback_rate`/`yqa_default_rate` inline, to delete them. `TAB_LOCK`/`STASH_TAB_LOCK` are Web Lock **names** and `STASH_SYNC_CHANNEL` a BroadcastChannel **name** — not storage keys, despite the `yqa_` prefix. `QUEUE_PAGE_STEP` = **10** is how many items one PageUp/PageDown covers in **either** list walk — the queue's cards and the Channels page's rows alike — a count of items, not a screenful of pixels (see Gotchas). It is `queue.js`'s only import, so it must stay free of browser globals too or the Node tests break — and it is the one module every layer may import.
- `auth.js` — Google Identity Services **token model**. Access token is **in-memory only, never persisted** (so sign-in re-approves on every fresh load); re-requested **silently** near expiry (`prompt: 'none'`), but the 401 retry is `requestToken({ interactive: true })` and may put UI on screen. Scope is `youtube.force-ssl` (read + `videos.rate` write for the Like button). **`ensureAuthorized(clientId, { forceNew })` is the single composed "authorize on demand" gesture**, called by **every** API-backed control on both queue pages, always straight from the click handler so the GIS popup keeps its user-gesture exemption. It reads no storage and touches no DOM, and **throws** rather than call `initAuth(null)` on a missing Client ID. It keeps **no once-per-load memo**: `initAuth` is idempotent per Client ID and re-initializes on a *changed* one, so a cached "prepared" flag would let "Change Client ID" mid-session authorize against the stale client. `forceNew: true` is for the cases where the token we already hold **is** the problem — the 401/403 re-consent retry behind Like (`ensureToken` would hand back the same scope-less token) and Sign in. Everything auth.js throws is an `Error` **with no `.kind`** (the GIS-path ones do carry a `.code`), so it falls through any `ApiError`-only routing: each page's error router needs its non-`ApiError` tail or the user gets raw internal text.
- `api.js` — `fetch` to the YouTube Data API v3, `Bearer` token, **no API key**. **`search.list` is never used** (too expensive). The uploads playlist id comes from the **UC→UU trick** (`uploadsPlaylistId()` swaps a channelId's leading `UC` for `UU`) — no API call, except for the rare non-`UC` id, which falls back to `resolveUploadsPlaylist` → one real `channels.list?part=contentDetails` at 1 unit. Channel avatars ride along free in `subscriptions.list`. `videos.list` is batched ≤50 ids/call; `getVideoDetails` requests `part=contentDetails,status,snippet` and returns the **snippet identity fields too**, at **zero** extra quota. `getVideosByIds(ids)` assembles **full records** in the shape the playlist path builds — record assembly stays in this layer — over **no new request path**; `getChannelAvatars(ids)` is `channels.list?part=snippet`, chunked ≤50 ids/call like `getVideoDetails`, for channels not already in `yqa_channels`. Ids the API omits are simply absent from the result. Errors are `ApiError` with a `kind` (`auth`/`quota`/`forbidden`/`notfound`/`network`/`http`). Quota is 10,000 units/day.
- `store.js` — video records in **IndexedDB**: **one** `yqa` database at `IDB_VERSION` **2**, holding **two** object stores that share the keyPath `videoId` and the same record shape — `videos` (the burn-down queue) and `stash` (the curated queue, whose records carry `addedAt` + `channelAvatarUrl` on top). Two stores rather than one flagged store, so the queues can never collide on a videoId. The public video APIs are thin wrappers over private helpers parameterized by store name, so **the store names never leave this module** — no other layer may open the database itself. **IndexedDB is required — there is no localStorage fallback for videos.** **Roll forward, never back:** `IDB_VERSION` went 1 → 2 to add `stash`, and v1 code opening a v2 database gets a `VersionError` → `req.onerror` → the sticky `dbUnavailable` flag → the permanent "Storage unavailable" wall, for **every user who has already loaded v2**. Since deploy = merging to `main` with no CI, `git revert` is the natural rollback and would be **worse than any bug it undoes** — fix forward, never revert past a version bump. Two fatal conditions, each a sticky module flag after which every video API throws and the page halts startup behind a full-screen error. Genuinely **unavailable** (`indexedDB == null` — a bare global read, so a truly *absent* global `ReferenceError`s instead of producing this; `open()` throws; `req.onerror`) → `DbUnavailableError`, over a screen naming the likely causes: site data blocked for this origin, corrupt DB, full disk. **Blocked** — the data is there but inaccessible (`onblocked`, `db.onversionchange`, or the exported `standDownForOtherTab()` a page's single-tab guard calls) → `DbBlockedError`, over a "close the other tabs and reload" screen; `onversionchange` also closes this connection, so another tab's upgrade is never blocked. `dbBlocked` is checked **before** `dbUnavailable`, because an aborted blocked upgrade can set both and "close the other tab(s)" is then the actionable message. **The memoized open, both flags and `standDownForOtherTab()` are per-DATABASE, never per-store** — do not "fix" this into per-store granularity: a database that cannot be opened, or that another tab owns, is equally unusable for every store inside it. The `stash` store has **two** writers in differently-locked tabs — `stash.html`'s add form and `index.html`'s "Add to stash" — so every stash write is the single-key upsert `putStashVideo` and **there is deliberately no bulk stash put**: a whole-set `putAll` would overwrite a live Stash tab's entire list rather than one key of it. Do not restore the symmetry. **Every committed `stash` write announces itself** on the stash's BroadcastChannel, posted by the private `putOne`/`deleteAll` from `tx.oncomplete` — after the commit, so a listener re-reading on the signal can never see the pre-write state, and from inside this module so a new write site cannot forget. The signal **carries no records on purpose**: IndexedDB is the single source of truth, and a payload would be a second copy of it, stale the moment a message is missed. **One** channel object does both the posting and the delivering to the exported `onStashChanged(handler)`: a `BroadcastChannel` never receives its *own* posts, so a second object in the same document would bounce every local write straight back. Lazy and defensive — a missing (or throwing) `BroadcastChannel` leaves it null forever and every write still works, just without sync, and a failed post never fails a committed write. Settings/floor/cutoff/channels/speeds live in localStorage (an empty `yqa_channel_prefs` map removes the key). Holds **no migration logic of its own**: the localStorage read paths are plain parses, and `readAll()` — the single `getAll` path behind **both** stores — hands its result to `migrateVideos()`, so a record migration covers the stash by construction instead of fixing one store and leaving the other on the old shape.
- `migrations.js` — **every** data migration, so retiring them later is deleting this file plus its **four** call sites (`store.js`'s `readAll()` and the boot of each `*-page.js` entry point). No browser globals at import time, so `migrations.test.mjs` imports it under Node; `localStorage` is touched only inside one function body. ### State & marking

`STATE_NEW='new'` vs `STATE_SKIPPED='skipped'` are the only states, declared **once in `config.js`** and imported everywhere (including `queue.js`) — never redeclare one per-module: a copy that drifted would have the writers persisting one value while the queue derivations still keyed off the other. **"handled" everywhere means `state !== 'new'`.** There is **no state normalization on read**, and deleting it was safe because nothing anywhere compares `=== STATE_SKIPPED` (it is only ever a value *written*; every read is `=== 'new'` or `!== 'new'`) — so a legacy `watched`/`not_interested` record already behaves exactly like `skipped`.

Marking is **two functions**: `setVideoState` **never toggles** — it sets the state as given; `toggleSkip` (Skip button / `x` key) picks `new` for **any** handled value and `skipped` otherwise, then delegates. Auto-mark-on-video-end calls `setVideoState` directly and always SETS `skipped`. `stash-page.js` mirrors this exactly (`toggleRemove`, after that page's "Remove" label) — same two states, same pick, so the label is display only and **no third state exists**. UI updates optimistically (grey in place, no re-render) then persists async, reverting on failure. **One exception, and it is about the empty list, not the mark:** with Hide-marked ON the card is removed rather than greyed, and when it was the *last rendered* one `setVideoState` does call `render()` — the empty state, the disabled "Jump to last skipped" and the re-windowing of the next `QUEUE_DISPLAY_LIMIT` records all live there, so without it the pane goes blank with live controls over it. **Focus at that removal is gated on `card.contains(document.activeElement)`, not on the caller's `advanceFocus`** — which entrance asked is not what decides whether the user is standing in the card that is about to vanish, and gating on it left the menu's "Add to stash", a mouse click on Skip and auto-advance on `ENDED` all dropping focus to `<body>`. `advanceFocus` still forces the move for the keys that want it with focus elsewhere. The walk cursor moves to the neighbour **unconditionally** (`rememberCard`), so an `ENDED` advance from `<body>` resumes beside the card that left rather than at card 1; with nothing left at all, focus goes to `#hide-marked-btn` — the one live control that brings the hidden cards back. Two `ui.js` behaviours this rescue **depends on**, neither to be "simplified": `closeCardMenu` restores focus to the trigger **before** the item's `onSelect` runs (that is why the menu entrance is rescuable at all), and the capture-phase `!panel.isConnected` staleness check still earns its keep, since the non-emptying removal still drops a card without `renderQueue`.

### Player behavior

Auto-advance on `ENDED` marks the finished video `skipped` and plays `nextPlayable` (next later `new` **and embeddable** video; non-embeddable ones open on youtube.com). Watch position is polled every 5s and persisted for resume; playback speed carries across videos via `effectiveSpeed` (per-video preferred > default-speed setting > current). Like is a `videos.rate` write whose liked flag is stored **locally only** and never fetched back. The button is **not** gated on being signed in — it authorizes on demand — and the ORDER matters: authorization happens **before** the optimistic flip, so a cancelled sign-in leaves the heart exactly as it was and there is nothing to revert. `state.liking` (not auth state) is what **guards** the button for the duration, so a second click — or the `l` key — cannot stack a second token request while the consent popup is open; in the DOM that duration is `aria-disabled`, the button's real `disabled` meaning only "nothing playing" (see Conventions).

`updatePlayingControls()` in **each of the two player pages** (`channels.html` has no player) derives the empty overlay's Start button **and** its text from **one** condition — `!state.playing && firstPlayable(…)` — so the overlay shows **exactly one of {button, text}**, never both and never neither; `state.playerCaughtUp` is a **text-selector only** and can never suppress a live button. The button is **hidden, not disabled**, so it never sits dead in the tab order, and `firstPlayable` scans the **full** list: Hide-skipped and the render window limit what is *rendered*, not what can be *played*. Because it hides under its own focus, `onStartQueue` hands that focus to the **card of the video it just started** (the player pane when that card is not rendered) — in the handler, **not** here, since this runs from ~6 sites and only that one can be holding the button's focus. The same `state.playing` hides the whole now-playing bar, a **visibility layer only**: every control keeps its own `disabled` logic underneath. `showPlayerEmpty` therefore hands focus off for the **whole** region in one gate — Skip, Like, the title link, the channel link and the description's links all go at once — to "Start the queue" if one is live, else the pane. `.player__frame` sizes from its own `aspect-ratio` and the pane is top-aligned, so the bar coming and going below it never moves or resizes the video.

### Refresh: "Fetch new" vs "Refresh all"

Signed out is not a special case: `runRefresh` raises `state.refreshing` (which is also what stops a second click stacking a second token request) and then `ensureAuthorized`s inside the click, so **one** click on a signed-out page both authorizes and fetches. Both buttons call the same `runRefresh(bound, sweepSpeeds)`; only two things differ — the per-channel lower bound (the floor for "Refresh all", or `incrementalSince(…)` for "Fetch new": newest stored `publishedAt` minus a 6h buffer) and the channel-speed sweep flag, **passed explicitly, never inferred from the bound**. Upsert-by-`videoId` preserves existing state; neither resets or duplicates. Known limit: "Fetch new" won't pull the back-catalog of a newly-subscribed channel — use "Refresh all".

Per-channel prefs (`yqa_channel_prefs`, edited on `channels.html`) are read **fresh inside `runRefresh`** — never cached at startup — so edits made in a Channels tab apply to the next fetch without reloading the main tab. Ignored channels are skipped entirely in the per-channel loop (no uploads request at all — saves quota; their existing records are untouched).

A refresh is the **only** channel-pruning site, run after the merge **and** the post-sync `cleanup()` so it sees that refresh's final record set: a `yqa_channels` entry — and its `yqa_channel_prefs` entry — is dropped only when the channel is **both** absent from the freshly-fetched subscriptions **and** has zero stored records, so an unsubscribed channel with videos still queued keeps its avatar/title and drops on a later refresh once they drain. The sweep covers the **union** of both maps, so an **orphan** prefs entry with no `yqa_channels` entry is judged by those same two conditions. **An empty (or non-array) subs list prunes nothing** — that reads as a failed fetch, not as "unsubscribed from everything" — and the prune never runs on the `init()` or "Trim front" cleanup paths, which have no subs list. It re-reads the prefs fresh at the prune site.

The merge is the pure `mergeRefresh` in `queue.js`: upsert, then apply each channel's speed to the **merged** set, so brand-new arrivals are included. Either way it stays **one write** — `mergeRefresh` then a single `putVideos` — and `mergeAndPersist` stays thin enough (merge + write + recompute) that `queue.test.mjs` exercises the real composition rather than a mirror of it. The rule is **fill-if-absent**: a record whose `preferredSpeed` is unset (`undefined` *or* `null`) and whose channel has a speed gets it; a record with an explicit per-video speed is **never** overwritten or cleared; ignored channels are excluded. **How far the fill reaches depends on the mode:**

- **"Refresh all"** (`sweepSpeeds = true`) sweeps the **whole stored record set**, so older already-stored videos get the channel's speed too.
- **"Fetch new"** (`sweepSpeeds = false`) covers only the videoIds this fetch **newly inserted**, so the older part of the queue is not re-sped — and videos re-returned inside the 6h buffer window count as already-stored and keep what they have.

Known limits (accepted): after un-ignoring a channel, "Fetch new" won't backfill videos published while it was ignored — use "Refresh all"; and toggling a card's speed OFF just removes `preferredSpeed`, with no "cleared by user" marker, so a later **"Refresh all"** re-applies the channel speed to that video ("Fetch new" does not).

## Conventions

- **`queue.js` must stay pure** — no `window`/`document`/`fetch`/`localStorage`/`IndexedDB` anywhere in it, so `queue.test.mjs` can import it under Node; `config.js` is its only permitted import. New pure logic goes here **with a matching test**.
- **XSS-safe DOM** in `ui.js`/`toast.js` — all API-derived strings go through `textContent`/text nodes; never `innerHTML` for API data; ids go through `encodeURIComponent`.
- Keep the layering: persistence in `store.js`, network in `api.js`, DOM in `ui.js`, shared page chrome in `page-chrome.js`, orchestration in the `*-page.js` entry points, `player.js` state-free.
- **`disabled` for structural unavailability, `aria-disabled` for in-flight** — because disabling a control **under the user's own focus drops that focus to `<body>`**, and every one of these is a control the user just clicked or pressed a key on. A control that is *genuinely dead* (`#like-btn` with nothing playing, the player-bar Skip under a hidden bar, "Trim front" at 0, the two jump buttons) takes the real `disabled` and rightly leaves the tab order. The jump buttons are dead **exactly when their target card is not rendered**, which is why `p` never reads that property: the handler already answers the same question by returning whether it focused a card, and a second answer would be free to drift from the first. A control that is merely **busy and coming back** (`#refresh-btn`/`#refresh-new-btn`, a like round trip, the stash's Add) takes `aria-disabled="true"` and keeps focus; **the page's own state flag is the re-entry guard** (`state.refreshing`/`state.liking`/`state.adding`, each already checked at the top of its handler), never the DOM property, since `aria-disabled` blocks nothing by itself. `styles.css` gives `.btn[aria-disabled='true']` the same dimming as `:disabled` and both are excluded from the two `:hover` rules, so the two look identical. **No busy label** on any of the three: the sticky progress toast is already a live region (`aria-live="polite"`), and swapping the text would reflow the toolbar or the Add field. "Show all (N)" is the one exception that *does* relabel, because it has no toast. The stash's Add is a **hybrid**: `aria-disabled` for the flight like the others, then a hand-off to the URL field on the way out (see `stash-page.js`) — keeping focus is about the *wait*, not about where the gesture ends.
- **Hand focus off a control before it disappears**, and **gate on whether it holds focus** (`btn.contains(document.activeElement)`) rather than on which caller asked — the mistake batch D fixed at the card-removal site. `page-chrome.js`'s **`focusFirst(...candidates)`** is the one helper: it focuses the first candidate that will actually take it, verifying `document.activeElement` after each, because the obvious landing is often itself hidden, disabled or inside the subtree that just went away. Ladders always end in something that cannot fail — the URL field, `#hide-marked-btn`, or `.workspace__player` (`tabindex="0"`, and one `/` from the queue). A control that **also re-renders the list** hands focus to the place anchor rather than the first card (`focusRemembered()` ahead of the ladder): landing on card 1 is itself the jump to the top the anchor exists to prevent — measured at 5693px on Trim front. That gate answers only "did **this control** hold focus"; focus that was **in the list** is not its business and is put back by `renderKeepingAnchor` itself, which is why **every re-render the page makes on its own must go through it** — a bare `render()` is how the refresh path dropped a mid-fetch user on `<body>`.
- All localStorage keys are namespaced `yqa_`.
- The app **never auto-fetches** — signing in only authorizes; the user triggers fetches explicitly. The converse is why nothing is auth-gated: a triggered action **authorizes itself** on demand (`ensureAuthorized`) rather than requiring a prior sign-in. The Sign in / Sign out buttons and the status label stay on both queue pages — they *display* auth state, and Sign out is not otherwise reachable — but they gate nothing.
- **README stays light** — the setup/OAuth guide and the non-obvious gotchas, nothing else; depth belongs here in CLAUDE.md. Behavior a user can see by just looking at the app (a new button, a bar that hides itself) goes in **neither** file.

## Gotchas

- **Cross-origin iframe swallows keyboard/wheel/pointer events.** Focus inside the youtube.com iframe kills document-level shortcuts (including Esc). **Two mechanisms, not interchangeable — keep both.** (1) A **click** on the video still moves focus into the frame; `bindIframeFocusGuard(getIframe)` in `page-chrome.js` catches that on window blur and blurs it back to `<body>` — deliberately, since that is where the arrow walk's re-entry rule expects it — skipped when the document is hidden, so alt-tabbing doesn't yank focus. (2) **Tab** must never reach the frame at all, enforced by `player.js`'s `detachIframeFromTabOrder()` — **more** load-bearing since the pane became a real tab stop, which makes the frame easier to reach, not harder. The guard alone could not do that job: Tab from anywhere inside the player pane continues into the frame; the guard bounced focus to `<body>` but **Chrome's sequential-focus starting point stayed on the iframe** — a permanent two-element loop that killed forward Tab for the rest of the session, on both pages, reproducing with **nothing playing**. **Deliberate consequence: YouTube's own in-frame controls (captions, quality, the scrubber) are NOT Tab-reachable, and that is not to be "fixed"** — a frame that keeps focus takes the app's whole keyboard layer with it, so the guard would bounce focus straight back out anyway. The keyboard route to the video's own page is the **title link** (`renderPlayerTitle`). Preserve **both** contracts when touching focus/keyboard code.
- **Privacy curtain** (`#curtain`): on **all three pages**, from `initCurtain()` in `page-chrome.js`, which owns the covering flag (no page mirrors it). Wheel-down outside the exempt scroll area covers the page with a full-viewport overlay, wheel-up lifts it, Esc toggles it (each page wires Esc from its own keydown table). Whether wheel-**down** may cover is decided by **layout, not width**: `index.html` and `stash.html` carry `body.app-active` — added in JS when the app is revealed, not in the HTML — a `100dvh` flex column whose panes scroll internally, so covering steals no scrolling and they take the default `coverOnWheelDown: true`. **Onboarding removes it** (the setup and cutoff panels scroll the document), so those pages briefly document-scroll like `channels.html` while still able to cover on wheel-down — accepted: there is nothing behind them worth scrolling to. `channels.html` has no `app-active` — its **document** scrolls at every width — so it passes **`coverOnWheelDown: false`**, or the channel list would be unscrollable. `narrowQuery` (≤1080px stacked layout) encodes the same rule by width for the pages that do cover. **Wheel-up and Esc work everywhere, at every width.** Purely visual — it does not pause the player. **Nothing may UNCOVER the screen while it covers**: `SCREEN_ESCAPING_KEYS` is `{'f'}` — fullscreen — and each table drops that key silently before dispatch, nothing visible being able to explain the refusal anyway. It holds on a Cyrillic layout too, `f` being a shortcut character: before `normalizeKey` the physical `KeyF` produced `а` and slipped the guard entirely.
- **Single-tab guard**: **two** lock names, one per page that **writes** an object store — `TAB_LOCK` (`yqa_tab`, `index.html` → `videos`) and `STASH_TAB_LOCK` (`yqa_stash_tab`, `stash.html` → `stash`). A second tab **of the same page** yields; the holder is never interrupted. **A Subscriptions tab and a Stash tab may be open simultaneously** — that is why there are two names over two stores. Their writes are no longer strictly **disjoint** (`index.html`'s "Add to stash" writes the `stash` store), so what keeps the guard sound is the *shape* of that write: a single `putStashVideo` upsert of one videoId against a stash list re-read fresh with `getAllStashVideos()` at the moment of the add — it can never clobber what a Stash tab wrote, and never leaves one stale (the write announces itself on the stash's `BroadcastChannel`; see The Stash). **Cross-tab sync exists for the `stash` store alone**, precisely because this guard makes it pointless anywhere else: `videos` has one writer that `yqa_tab` keeps single, so nothing could ever be listening. `channels.html` asks for **neither** (it writes no video records). Each page's `init()` fires `requestTabLock(name)` at the top and awaits it at its checkpoint, **immediately after `cacheDom()`** — before any store read, settings restore, the stash's remove-sweep and `bindEvents()` — so a tab that is not granted shows `showSupersededError()` behind `#blocked-overlay` having read no records, written nothing and bound no handlers. Race-free by construction, decided once at startup — no mid-session halt. **Fails open, never closed:** without `navigator.locks`, or if the request throws or rejects, the tab boots normally — the guard must never lock the owner out of their own queue.
- **An author `display` beats the UA `[hidden]` rule**, so anything hideable needs its own `[hidden] { display: none }` in `styles.css`. Buttons are covered wholesale by the general **`.btn[hidden]`** rule: `setVisible()` sets the `hidden` attribute and `.btn` is `inline-flex`, so without it a "hidden" button renders. `body.app-active #app-main.app[hidden]` needs that exact selector to out-specify the `body.app-active #app-main.app` two-pane layout rule above it, or the fatal-storage overlay leaves the app focusable in the a11y tree behind it. **`.channels[hidden]` is the same trap, caught late**: the list is `display: flex`, so it kept its box and stayed in the a11y tree behind the "no channels" state, while `.queue[hidden]` had carried the rule all along. Miss one and the "hidden" element stays on screen.
- **A `.btn`'s height is FONT-dependent, so a row of them is equal only if the CONTAINER stretches.** The UA's `font` shorthand on `<button>` beats the body's `16px/1.5`, leaving `line-height: normal`, so the box follows whichever fallback font draws the glyph — `▶` and `↗` pull taller metrics than plain Latin, which is enough to make ▶ Play and Skip disagree — and `.btn--icon` / `.btn--speed` / `.btn--cardspeed` / `.btn--menu` each add their own padding and `line-height` on top. Equal heights come from **`align-items: stretch` on the row** (`.row__actions`, `.player__controls`, `.chan__controls`, `.queue-header`, `.stash-add__row` — an `<input>` beside a `.btn` is the same problem, and a wrapping row aligns per LINE, so a control that has dropped onto its own keeps its natural height), never from matching padding, and **every intermediate container has to pass it on** (`.row__speeds`, `.row__menu`, `.chan__speeds`) or the buttons inside it keep their own size. A group whose divider is its own `border-right` then spans the row's full height: that is the stretch, not a bug.
- Keyboard shortcuts live in **two** `onGlobalKeydown` tables — `subscriptions-page.js` and `stash-page.js` (the same gestures minus refresh / hide-marked / jump-to-last-marked) — plus a **third, smaller one** in `channels-page.js` (Esc, the brackets, the six walk keys and the per-row `x` / `1`,`5`,`2` — no `t`, no `p`, and no `/` to be inert about). **All three** ignore Ctrl/Cmd/Alt combos and typing in inputs — the third grew those guards when it stopped being Esc-only — and **Esc is the panic key, handled *before* them**, on every page and in every state, so it works mid-typing, during onboarding and with a card menu open — **which it leaves open**: Esc is the curtain's key alone, and the menu has closers enough without it. **"The focused card" is whichever `.row` *contains* `document.activeElement`** — `closest('.row')`, resolved by both tables' `focusedCardIndex` for `x`, `t` and `1`/`5`/`2`, and again inside `page-chrome`'s `moveCard` for the arrows, which the tables only delegate to — so they keep working from any control inside a card. `channels-page.js` asks the same question of its own rows (`focusedChannelId`, `closest('.chan')`), so `x` and the speed keys fire with focus on the channel link or any of its four buttons. **`t` stashes the focused card**, on `index.html` only, through the same `addCardToStash` the card menu item calls, passing `{ advanceFocus: true }` — as `x` does and the Skip button does not — so a run of `t`s walks the queue instead of firing twice on one card. **`addCardToStash` handles that option itself and does not forward it**, because it must move the cursor **before** its two IndexedDB round trips, not after: while focus is still on the card, the next `t` resolves to the *same* card and re-stashes it. **`p` jumps to the now-playing card**, on both player pages, through the very same `onScrollToPlaying` the ⮧ button clicks — so the key and the button can never disagree about where a jump lands. It is the third **absolute** jump after `/` and the brackets, works from anywhere on the page including inside the player pane (watching a video and wanting its card back is the point), and `preventDefault`s only on the handler's `true`, so with nothing playing — or its card unrendered — `p` keeps its native meaning. **The player keys are the rest of both queue tables**: `l` Like, `n` skip to the next playable, `m` mute, `f` fullscreen, `-` and `=`/`+` the speed cycle, `←`/`→` a ±5s seek — `m` and the two seeks gated on `state.playing`, so `←`/`→` keep their native meaning with nothing playing. None of them exists on `channels.html`, which has no player. `#scroll-skipped-btn` gets **no** key and stays mouse-only. **No key opens the menu**: its trigger is its only way in, and opening leaves focus *on* it. **The arrows walk it once it is open**, through `moveCard` — see the walk gotcha below. **`Enter` and `Space` are the deliberate exception, matching the `.row` exactly**: each natively activates a focused button or link, so resolving them through the containing card would double-act. Don't tidy that inconsistency away. (`1`/`5`/`2` move no focus, so a menu stays open over the speed it just set.) `ui.js`'s **capture-phase** `document` keydown swallows nothing — no `preventDefault`, no `stopPropagation` — and exists for **one** thing now that Esc is gone: a card can be dropped without `renderQueue` (Hide-marked on, auto-advance on `ENDED`), leaving a detached panel still holding both document listeners, so `!panel.isConnected` retires the menu and lets the key through untouched.
- **A shortcut is identified by `normalizeKey(e)`, never by `e.key`.** All three tables call `queue.js`'s pure helper, which returns the character the layout **produces** when that is a bound shortcut, else the US-QWERTY character at the key's **physical** position (`e.code`) when *that* is one, else the produced character unchanged. `e.key` alone is only ever what the layout produces, so on a Cyrillic, Greek, Hebrew or Arabic layout it is never a latin letter and **every letter shortcut dies the moment the user switches input** — the mapping is therefore one entry per **shortcut**, never one per language. **PRECEDENCE IS THE DESIGN**: what the keycap **prints** wins, so Dvorak/AZERTY/QWERTZ users get the letters on their own caps, and the physical fallback runs only where the produced character is no shortcut at all — the non-latin case, which has no cap to match. Code-first would scatter the shortcuts across every latin non-QWERTY layout. Accepted cost: a Dvorak user also gets Skip from the cap printed `b`, which sits where QWERTY's `x` does. **`SHORTCUT_CHARS` holds characters ONLY** — `Escape`, the four arrows, `PageUp`/`PageDown`, `Home`/`End`, `Enter` and `Space` are deliberately **out**, their `e.key` being layout-invariant already and their positions carrying no character, so they fall through the fallback untouched. Letters and digits are **derived** from the code (`KeyX` → `x`, `Digit1` → `1`), so a new letter or digit shortcut needs no entry; only punctuation is an explicit map — `Slash`, `BracketLeft`, `BracketRight`, `Minus`, `Equal` — and adding a punctuation shortcut without its code is how one silently stays layout-bound.
- **`ArrowUp`/`ArrowDown`, `PageUp`/`PageDown` and `Home`/`End` all walk `[card1 … cardN, "Show all (N)"?]`**, with the mechanics deliberately **not** in either table: the entries call `moveCard(dir, { page })` / `focusEdge(dir)` from `page-chrome.js`'s `initQueueFocus` and `preventDefault()` **only when it reports the key was taken**, so everything it declines keeps its native scrolling. The windowing footer button is a walk **item, not a card**: ArrowDown off the last card lands on it, ArrowUp from it steps back to that card **by position**, ArrowDown on it clamps, and **End** lands on it whenever one is rendered — never a card, because the two things being a card *means* (being the target the list is **entered** at, and being what `x` / `t` / `1`,`5`,`2` act on) are both meaningless for it. **Where the keys apply is a question about LAYOUT, not about what happens to hold focus.** In the two-pane layout `body.app-active` is a `100dvh` flex column whose panes scroll *internally* and the document does not scroll at all — so outside `.workspace__player` there is no native scroll for a key to belong to and it belongs to the queue, `<body>` included; inside that pane they always decline, so it goes on scrolling. In the **stacked (≤1080px)** layout the queue pane is `overflow: visible` and the **document** scrolls, so only focus genuinely *inside* `.workspace__queue` is taken. The narrow/wide question is asked as a `narrowQuery` media query — the same 1080px breakpoint `initCurtain` uses — never by measuring. **That 1080px is derived, not chosen, and is THREE numbers that must move together**: the media query, the frame cap's floor in `styles.css`, and `narrowQuery`'s default. It is set so the two-pane player column always clears the bar's `@container player (max-width: 38rem)` threshold — 608px, plus the 444px of frame the queue/gutter/padding take, plus ~15px for the pane's own scrollbar — which is what keeps the layout to **three** states. Lower it and "two panes with the bar stacked onto its own row" comes back as a fourth. **`channels.html` is the third case and the clearest**, because it is the same rule reaching the opposite answer: one column, no second pane, and therefore **no region with a native scroll of its own to protect** — so nothing is carved out, `initListWalk` asks no media query at all, and the keys apply **throughout the page**, a first press from `<body>` or the nav strip entering the list rather than declining. Carving anything out here would be the defect: the queue is walkable the moment the other two pages load, and this one would have demanded a pane switch first. **Only `.row` carries a `scroll-margin-top`** (60px, 104px stacked), and only because `.queue-header` is genuinely `position: sticky` and would otherwise cover a card landing at the top edge — measured clear by ~10px at both widths. **`.chan` carries none**: nothing on `channels.html` is sticky and its topbar scrolls away, so a row at the very top edge is fully visible. One there would be pure cost — it pushed an upward landing 66px further down than the browser asked for (66, not 132, because a fully out-of-view target is centred, which halves the margin's effect) and changed nothing at all for a partially visible one.
- **The remembered card is what a press from outside the list enters at** — a `focusin` on the queue list notes the `videoId`, never the element (`renderQueue` rebuilds the `<ul>`, so a node reference is detached one render later); it resolves against the **current** list at use time and falls back to the first card. **`focusin` is its usual writer, not its only one**: `rememberCard(videoId)` sets it outright for the **one** move that changes the user's *place* while focus is somewhere else entirely — a card removed out from under a cursor that was never in it, which fires no `focusin`, so without it the walk silently restarted at card 1. The Hide-skipped toggle reads like a second such case and is **not** one: it keeps the user's place through `renderKeepingAnchor`, which restores the cursor itself, so `rememberCard` has exactly one call site and a new caller wants justifying. **`channels.html` keeps the same note for a different reason**: nothing there throws focus out of the list — no player iframe, no `/` — so `focusin` is its only writer and there is no `rememberCard` counterpart, but `[`/`]` still leave and return — and the note is now **also what a first arrow press from `<body>` or the nav strip enters the list at**, which on a fresh load with nothing remembered is row 1. Making the row focusable is itself what forced the note: `paneFocusables` then matches the `<li>` **ahead of its own link**, so the list pane's default landing silently moved from the first channel's link to the first row, and either way restarts at the top. That pane needed an explicit `focus:` override regardless, and pointing it at `focusRemembered` is what makes resuming free. **That same `focusin`, paired with a `pointerdown`, also maintains `row--pointed`** — the class marking the card a POINTER press placed the cursor on, and half of what `styles.css` draws the card ring on (the other half being `:focus-visible`). It exists because the ring cannot be a plain `:focus`: every programmatic focus this module performs would then draw one after a **mouse** gesture — Clean up, Trim front, "Show all (N)" and the removal rescue all land focus on a card the user never chose. **The two jump buttons — `#scroll-playing-btn` (⮧) and `#scroll-skipped-btn` (⭳) — land focus deliberately, and equally deliberately do NOT ring**: both `card.focus({ preventScroll: true })` then `scrollIntoView({ block: 'center' })`, in that order and for the same reason the page keys use it, and the queue list's `focusin` writes the cursor for free, so neither calls `rememberCard`. They move the cursor because a jump that only scrolled would leave the next arrow press resuming from a card the user is no longer looking at. They stay unringed because the gesture is a press on a **queue-header button, not on the card** — so `p` rings its landing through `:focus-visible` and the mouse click does not, and the playing card already carries `.row--playing` to say where it is. Marking the one pointer gesture that *is* a placement, rather than sniffing at a modality, is what lets a future focus site inherit the right behaviour without knowing any of this exists. `pointerdown` marks only a press that does **not** land on a control (`a, button`) inside the card — an action, not a placement — and the `focusin` then retires the mark once focus moves off the marked card. For ▶ Play and Skip the two rules agree, since focus lands on the control rather than the card; it is load-bearing for exactly one press, the **thumbnail**, which redirects its focus onto the row and so lands on the marked card *itself*, the one shape `focusin` keeps. Asking what was pressed is the honest question, and "did focus land on the card" was only ever a proxy for it. Focus landing on a non-card in the list leaves the note standing: it answers "where does a press from *outside* the list go", and the footer button is never an honest place to be dropped into a queue. It matters most from `<body>`, where `bindIframeFocusGuard` drops focus on every click of the video — without it the arrows would stop working after one click. The relative keys **clamp** at the ends rather than wrapping, and the clamp does **two** things that must both survive: it still moves focus onto the item, *and* it reports **not**-handled. Landing on the `.row` is how a **page** key gets focus out of an open menu (it leaves the `.row__menu` wrapper, whose `focusout` dismisses it); reporting not-handled is what hands the pane back its native scroll at the ends of the walk. **An open card menu is walked by the same arrows, as a pre-step inside `moveCard`** — `stepCardMenu(dir)` first, and only when `!page`: `'moved'` takes the key, anything else falls through to the ordinary card step **unchanged**. That is the whole mapping, with no branch per case: from the trigger Up reaches the last item; from an item Up steps up, and off the *first* item exits; Down steps down, and off the *last* item returns to the trigger; from the trigger Down exits. An exit has already closed the menu and left focus **on the trigger — inside the `.row`** — so the card step that follows resolves that same card and moves to its neighbour, which *is* "out of the menu and on to the next card". Menu **closed**, the arrows are pure card navigation with no exception for the trigger. `PageUp`/`PageDown` and `Home`/`End` deliberately skip the menu step: they leave the wrapper outright and the `focusout` closes it. **`PageUp`/`PageDown` are `moveCard` itself with `{ page: true }`** — a step of `QUEUE_PAGE_STEP` (10) items instead of 1 — inheriting the entry rule (from outside the list they still land on the remembered card) and the clamp unchanged; do not write either a second time. **Step size is now their ONLY difference** — a page key is a plain `focus()` like a single step, so the browser's default scroll stands and the destination comes into view only if it is not already there. Worth stating exactly, since it is easy to reason wrongly from: the default edge-aligns only a **partially** visible target; a **fully** out-of-view one is **centred** (measured in Chrome), and one already in view scrolls **zero**. Cards run 370–445px, so every queue page jump is fully out of view and lands roughly centred; on `channels.html` many rows fit a screen, so a jump whose destination is already visible scrolls nothing at all — which is the point of the change. **The native page-scroll was tried and deliberately abandoned — do not restore it as a fidelity improvement**: a card is a large enough fraction of the pane that a browser page advances barely more than one card, and stalls outright when the bottom is already in view — hence a fixed step of items. (For anyone asserting on a scroll position: **Chrome animates a keyboard scroll**, so a value read straight after the key is still in flight.) **`Home`/`End` are absolute** — nothing to step from and nothing to clamp: `focusEdge(dir)` names the first / last walk item outright, and an empty list declines, keeping the keys' native meaning. All four move focus and let the scroll follow, so the **remembered card updates for free**; none gets a `<kbd>` help line, which teach only app-specific, unguessable keys — each of the **three** pages' strips lists `↑`/`↓` and none of them lists a page or edge key, which is what keeps that convention checkable.
- **`[` and `]` step a CYCLE of the page's panes**, wrapping at both ends, from `page-chrome.js`'s `initPaneNav`; each page's table calls `movePane(dir)` and `preventDefault()`s only when it reports the key taken. The cycle is that page's regions **in DOM order, which is also VISUAL order** — `index.html`: nav, toolbar, player, queue actions, queue; `stash.html` inserts the **add form** after the toolbar; `channels.html` is nav and the channel list. **The player precedes the queue in the markup**, which puts it in the left column side by side and on top when stacked, so no CSS reorders anything and no array here needs a width branch. **`styles.css` declares `order` nowhere at all, and must not start**: the two declarations it used to carry (the player pane above the queue when stacked, the player bar's controls above its title) each put focus order at odds with visual order, and the fix both times was to make source order *be* the visual order rather than to compensate for it. **Landing is a control, not a container, bar two**: a region focused whole is a tab stop the user then has to escape, and `focusFirst` skips the hidden and the disabled by verifying `activeElement`. The **player** is a container because being focusable **as a pane** is the whole point (it scrolls natively); the stash's **add form** because its only controls are a text field, where the typing guard swallows `[`, `]` and `/` alike — landing there would take the cycle its own keys. Both carry `tabindex="0"` (never `-1`: reachable one way and not the other is incoherent) and take that escape cost deliberately, and both need an explicit `focus` override, since `paneFocusables` is a `querySelectorAll` and so never matches `el` itself. The queue's landing is the **remembered card**, so arriving resumes the walk rather than restarting it at card 1. **A pane that cannot take focus is SKIPPED**, the step continuing in the same direction — not tidiness: a fresh stash has **both** its queue-action buttons `disabled` at once and an empty queue has no card, so without the skip the key would die against a region the user cannot see is unreachable. **The origin falls back to the LAST PANE FOCUS WAS IN** (default: the queue), because `bindIframeFocusGuard` puts focus on `<body>` on every click of the video; reading `<body>` as "the queue" would send `[` backwards *past* the queue to the queue actions at the one moment the user is unambiguously standing in the player. Same principle as the remembered card, and focus outside every pane leaves the note standing. Unlike the card walk these are **not** gated by `walkApplies` — leaving the player is exactly what they are for. **The cycle never deposits focus in an input**, so it has no one-way door: the stash's add-form pane lands on the form. What *is* accepted is that focus the user puts in the URL **field** themselves, by Tab or a click, swallows `[`, `]` and `/` alike; Tab or a click is the way out. **Hoisting `[`/`]` above the typing guard was considered and REJECTED.** It looks free — neither bracket can ever be legitimate input there, no video id, host or path segment containing one. It is not: `/` is a pane key too (`togglePane`) and **is** a legitimate URL character, so it can never be hoisted, and doing it for the brackets alone would leave two of the three navigation keys steering panes from inside that field and the third typing a slash. Landing the cycle on the form keeps all three consistent instead — all three work from the form, and all three are swallowed alike once focus is in the field. The wrap-and-skip order is `queue.js`'s pure `paneCandidates`, so the arithmetic is tested rather than eyeballed.
- **`/` throws focus between the two big panes, with THE QUEUE AS HOME** — from `#queue-list` into `.workspace__player`, from **anywhere else** (the player, any of the small panes, `<body>`) back to the remembered card — at **every** width, and `preventDefault()`s **whenever it reaches us**, because Firefox opens Quick Find on it (Shift allowed, so a layout that shifts `/` still reaches us, and one with no `/` at all reaches us through `normalizeKey`'s physical `Slash` fallback). Unlike Esc it sits **below** the table's typing / `appMain.hidden` / modifier guards, so it is inert in an input and throughout onboarding — Esc alone is unconditional. The `<aside id="player-pane" class="workspace__player">` on both player pages carries **`tabindex="0"`**: a real tab stop, so **Tab reaches the pane on the way INTO the workspace — out of the toolbar, ahead of the queue — while `/` reaches it from the queue**; before it was a stop at all the two gestures disagreed about whether the pane was a place you could stand, while the pane cycle said it was. Once focused it scrolls natively, the entire point, a long description being otherwise unreachable without tabbing through every card's controls. It is safe because `walkApplies` gates on `playerPane.contains(active)`, which is **true for the pane itself**, so a Tab-focused pane declines the arrows and PageUp/PageDown and goes on scrolling natively, exactly as a `/`-focused one does. **Accepted cost:** in the caught-up/empty state the pane holds nothing focusable and is an inert stop tabbed straight through — deliberately **not** made conditional, a tabindex coming and going with playback being a worse surprise than one dead stop. That `id` is what the **first** skip link ("Skip to player", ahead of the queue one, both pages matching the pane order behind them) targets, so it lands focus **on** the pane. **Every skip link targets a focusable element.** All **three** pages carry one — only the two player pages carry a *second*, `channels.html` having no other region to skip to — and `#queue-list` and `#channel-list` alike carry `tabindex="-1"` for exactly this reason — a fragment link only *focuses* its target if the target can be focused, and without it the queue link moved the sequential starting point while a screen reader's cursor stayed up in the nav. **Neither link uses that fragment, though — each `preventDefault`s and focuses the FIRST ROW of its own list**, a card on the queue pages and a `.chan` on Channels. Two faults drove it: the fragment navigation scrolls its target into view on its own, nudging a queue already at the top, and landing on an invisible container reads as nothing having happened for what is a keyboard gesture. The row rings on arrival either way (`:focus-visible` propagates from the keyboard-focused link); only a **card** additionally needs its `scroll-margin-top`, to clear the sticky `.queue-header`. A `.chan` needs none and has none — nothing on that page is sticky, and the landing measures unclipped at both widths. With an **empty** queue there is no card and the `<ul>` is `hidden` in exactly that state — focusing it is a silent no-op — so the ladder falls to whatever actually occupies the region — `#empty-state` on the queue pages, `#channels-empty` on Channels. **Both carry a `tabindex="-1"` of their own, and must**: `focusFirst` **verifies rather than forces**, so every rung of a ladder has to be independently *made* focusable — `#channels-empty` is a plain `<div>` and silently failed as a rung until it got one, which is exactly why `#empty-state` has carried one all along. The `<ul>`'s `tabindex` stays as the fragment's meaning and the ladder's tail. `.queue:focus` and `.empty:focus` are the app's one deliberate `outline: none` — three landings now, `#channels-empty` matching that same `.empty:focus` rule — landings, not controls, and the UA ring would frame a list thousands of pixels tall. (Its focus ring and the clip band it lives in are the player-pane scrollport gotcha below.) With **no cards at all**, `/` out of the player does nothing and leaves focus where it is: no honest target, and blurring to `<body>` would be a silent loss. It is `initPaneNav`'s `togglePane()`, **not `initQueueFocus`'s** — it is expressed in pane terms now, which is what lets a page opt out of it by passing no roles. **Activating "Show all (N)" destroys the button that was pressed** — the re-render removes the whole `li.queue-more` and nothing replaces it — so both pages place focus by hand or it falls to `<body>`: they read `cardCount()` **before** flipping `state.showAll` and call `focusCardAt(thatCount)` after the re-render, landing on the **first newly-revealed card** (the window only grows, so the pre-expansion count *is* the boundary). `focusCardAt` falls back to the last card, then the first — not decoration: the index is measured against a list since rebuilt. The activation is deferred behind a `Loading…` label (see the `ui.js` bullet), focus held on the button for the wait.
- **Narrowing or suppressing an author `:focus-visible` rule does not remove a focus ring — it reveals the UA's.** The element still matches `:focus-visible`; the author rule was only overriding the browser's default outline, so dropping it hands the ring back to Chrome, painted in Chrome's colour rather than `--focus`. A genuinely absent ring would take `outline: none` on a focus-visible element, which strips a real accessibility affordance and is not done here (the app's one `outline: none` is on `.queue`/`.empty`, landings rather than controls). **Where the browser insists an element is focus-visible, that is accepted rather than fought.** Asserting on it: Chrome's default ring computes as `outline-style: auto`, **not** `none`, so `outline-style` alone cannot tell "no ring" from "the UA's ring" — `outline-color`, or a screenshot actually looked at, is what distinguishes them.
- **ABOVE 1080px the player pane's SCROLLPORT is padded out past its content on every side, and that band is what stops it clipping its own focus rings.** `.workspace__player` carries a `padding` against an equal negative `margin`, so nothing moves but the **clip edge**: `overflow-y: auto` makes the pane a scroll container, which clips **both** axes at its padding box, and `#player-title` / `#player-meta` sit flush against the content edge — so their rings, painted *outside* their element like every ring here, were sliced off at x < 0. Not fixable from the link's side (its content starts on the clip edge), nor by `overflow-clip-margin`: beside `overflow-y: auto`, `overflow-x: clip` **computes to `hidden`** and the margin does nothing. Two consequences. The pane's own `outline-offset` must **not** go negative — the scrollbar rides outward with the padding box and the right-hand segment would land on it. And **the padding band IS the ring headroom: 6px against the widest reach in there, a `.btn`'s 4px** (2px outset over a 2px outline), so 2px is left over. `.player__controls` reaches the pane's right edge **always**, `.player` being `width: 100%` of it; its LEFT edge is reached only when the container query stacks the bar, which can no longer happen where a band exists (the bar stacks below 1080px, where there is no scrollport at all), so in the banded layout the live edges are the controls' right and the title/meta's left — spend that 2px on a wider offset or outline and the ring clips silently, with nothing enforcing the relationship; check it in the browser. On the **scrolling** axis the band is headroom only at the two ends of the range: a control hand-scrolled off the top still loses its top segment, as in any scroll container. **In the stacked (≤1080px) layout there is neither scrollport nor band**: the height lock is released, so the pane takes `overflow: visible` and drops the padding/margin pair together — the band cannot go on its own, `overflow-y: auto` clipping at the padding box whether or not anything actually scrolls, and keeping it once the overflow is gone buys nothing while pushing the pane's box 6px outside its own column. Rings there are clipped by nothing at all.
- **The meta row (`.row__sub`; `.player__meta` in the bar, `.chan__identity` on the Channels page — three contexts, same rules) holds ONE in-flow child**: `.row__subtext` (`.chan__identity-text` there), inline flow of `.row__channel-link`, separator, date, a wrapped name's tail carrying the date. The avatar is **inside** that link but absolutely positioned in the relative row — **out of flow is a GEOMETRY exemption, not a HIT-TESTING one**: no inline boxes, so the ring hugs the **name alone** (`.row__title`'s exactly), yet a click on it follows the link. Height and indent go with it — hand-set `min-height: 36px`, `padding-left: 42px`, no flex `gap`. **`.chan__identity` is the third context on that one shared rule, not a parallel one** — but its indent is **`46px`, not the cards' 42px**, because this row's avatar-to-name gap has always been 10px where the card's is 6px, so copying 42px across misaligns the name. **Two elements, never one**: a flex container blockifies its children, so the link has to be a *grandchild* to stay inline and let its ring fragment per line. **And never put a `filter` on the link** — a `filter` at any non-`none` value makes an element the **containing block for its absolutely-positioned descendants**, so greying `.chan__link` would re-anchor the now-out-of-flow avatar to the link's own inline box and drop it on top of the name, for ignored channels *only*, which is exactly the kind of thing that ships; `.chan--ignored` greys `.chan__identity` instead. `metaSeparator()`'s **real space text nodes** around the `·` (trailing `\u00a0`) put the only break *before* it, so no lone `·` dangles; `.row__time-abs`'s one rule, `white-space: nowrap`, keeps the date whole.
- **Hover is accent, focus is a ring, and nothing in the meta row underlines.** `.row__title` (cards *and* the now-playing title) and `.row__channel-link` are one gesture on two links: hover turns the text `var(--accent)`, focus draws the `--focus` ring and does nothing else. **`channels.html`'s `.chan__link` says it the same way** — hover accent on `.chan__title`, no underline anywhere — at **`.row__channel-link`'s ring exactly** now — the same `1px` offset at a `4px` radius — because this box is the **name alone**, the avatar having gone out of flow. A wrapped name rings per line fragment, as a wrapped card title does. Still no `999px` pill — `.chan__title` wraps, so the box grows tall and the end caps become half its height, cutting through the text.
