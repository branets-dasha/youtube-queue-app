# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pure client-side "burn-down queue" for YouTube subscriptions: fetch subscription videos up to a moving cutoff and play/skip through them, oldest→newest. Three static pages, each with its own entry-point module — `index.html` (the queue), `stash.html` (a hand-curated second queue), `channels.html` (per-channel prefs). Vanilla HTML/CSS/ES modules — **no build step, no framework, no bundler, no `package.json` or `node_modules` in version control**: everything committed has zero dependencies, and deploy = push to `main`, so anything committed is shipped. The only runtime dependencies are two Google-hosted scripts (Google Identity Services, the YouTube IFrame API) plus the YouTube Data API v3, which is a REST endpoint (`API_BASE`) and never loaded as a script. Browser verification adds none — the Playwright **MCP server** installs nothing into the repo and writes only a gitignored `.playwright-mcp/` (`.claude/skills/browser-test/SKILL.md`).

## Working style — delegate, act as overseer

Act as an **orchestrator/overseer**, not the hands: research, design, implementation, review and verification go to **subagents (Agent tool) or a Workflow** rather than being done in the main thread, and they hand back compact results, not large file/output dumps. **This governs the top-level session, not the agents it spawns.** A subagent reading this is already the delegate: it does its brief directly and spawns nothing further — fan-out included, not just handing the whole brief to one more agent. This is the owner's standing instruction.

- **What decides it is whether the task has anything to discover — never how small the change looks.** A file to find, a pattern to sweep, a behaviour to verify, a judgement to make: that goes to an agent, because absorbing that context is what an agent is *for*. A change confined to a file already read in this conversation, needing no new file located and no design decision, is made in the main thread. **The bright line is "already read in this conversation"** — that is checkable, where "I already know how to do this" is not, and treating it as the test is how the discipline erodes into doing everything by hand.
- **Delegation costs a whole agent's context, so it is not automatically the cheaper path.** Answer one-shot browser questions — where focus lands, whether a rule went live, what something looks like — **inline** with the `browser-test` skill's MCP tools; delegate browser work only when it is genuinely build-and-verify.
- **A `fork` when the task's rationale lives in this conversation, a fresh agent when the task stands on its own.** A fresh agent has only its brief, so it re-derives what the conversation already settled — or acts on a lossy summary of it. Send it self-contained work; fork anything whose *why* is in the transcript.
- **Ask an agent for the verification the risk warrants, not all of it by default.** Mutation checks, measurement tables, both themes, both pages, long structured reports each multiply what the agent costs — the brief is the multiplier, not the tooling. Spend them where the claim is hard to see (a mutation check when a passing test might not be proving the fix, measurements when the claim is "nothing moved", both themes when the change is colour); otherwise just ask for the result.

## Architecture

### The FLOOR vs live CUTOFF model (core domain concept)

Two distinct ISO timestamps, both in localStorage, are the heart of the app. Understand these before touching queue logic:

- **FLOOR** (`LS_START_CUTOFF` = `yqa_start_cutoff`) — the deletion + fetch boundary. As the queue burns down it **only ever advances**, and only inside `cleanup()`; the **one other writer** is the "Change cutoff" panel (`onSaveCutoff`), which sets it outright to whatever datetime the user picks — forward *or* backward — then recomputes the cutoff from the present records. It is the lower bound for the render list, the queue count, and the per-channel lower bound when fetching.
- **CUTOFF** (`LS_CUTOFF` = `yqa_cutoff`) — the live "handled-prefix" marker shown in the stats. **Bidirectional**: `computeCutoff(records, floor)` recomputes it from scratch each call, so it advances as you mark the oldest videos handled and **retreats** when you un-mark one. Always `>= floor`.

`computeCutoff` walks the contiguous *handled* (`state !== 'new'`) prefix strictly after the floor and stops at the first `new` video. It is **tie-safe**: the returned cutoff is always strictly less than the earliest still-`new` video's `publishedAt`, so a handled video sharing a timestamp with a `new` one never pulls the cutoff onto it. Window membership is **strictly after** the cutoff.

`cleanup()` (in `subscriptions-page.js`) is the **only** place videos are deleted, and the only place the floor *advances on its own*: it deletes every present record with `publishedAt <= cutoff`, then sets `floor = cutoff`. Three sites: page-load `init()`, after a refresh sync, and the "Trim front" button. Consequence, with Hide-marked **off**: marked videos stay greyed *in place* (never reordered/removed) until the next cleanup prunes the whole handled prefix. With it **on** the card leaves the list the moment it is marked.

### The Stash (`stash.html`) — a second queue, deliberately outside FLOOR/CUTOFF

The Stash is a hand-curated companion queue, filled one video at a time — a pasted YouTube link on its own page, or a card's "Add to stash" on the subscriptions page. Nothing is fetched **by subscription** (a pasted link does cost one `getVideosByIds` plus an avatar lookup), nothing is deleted by a moving boundary, and **neither the floor nor the cutoff exists for it** — there is no stash timestamp in localStorage at all. Why it can do without them:

- **Order is arrival order.** `sortStash` sorts by **`addedAt`**, oldest first — *not* `publishedAt` — ties broken by `videoId`, with a missing/unparseable `addedAt` sorting **last** (an unstamped record is foreign/hand-edited data, and the tail is where it does least damage). It is the stash's **single sort site**: drag-to-reorder adds an `order` field and changes **only that function**.
- **Deletion is state-based, not position-based.** `stashToClean` returns every handled (`state !== 'new'`) record from **anywhere** in the list, gaps included; `videosToClean(records, cutoff)` is position-based (`publishedAt <= cutoff`) and can therefore only ever delete a contiguous **prefix** — that difference *is* the reason the burn-down queue needs a moving floor and the stash needs none. One implementation (`sweepRemoved()`) backs **both** the "Clean up" button and an on-reload sweep that runs **before the first render**, so a removed card never flashes on screen.
- **No third state.** The mark button reads **"Remove"** but stores the same `STATE_SKIPPED`, so `"handled" means state !== 'new'` holds on both queues. The label is display only (`renderQueue`'s `skipLabel`) and the `btn--skip` class is unchanged, so `setCardState` and the CSS keep working.
- **No dependency on `yqa_channels`.** A stash record carries its own `channelAvatarUrl` and `stashChannelInfo` prefers it over the map, so `pruneChannels` dropping a channel entry can never blank a stashed card. The map stays as the **fallback**, and is not dead code: records stashed before avatars were captured, and ones whose avatar fetch failed, carry none of their own.
- **Adding respects a channel's preferred speed but ignores its Ignore flag.** `addToStash` fills `preferredSpeed` from the channel only when the record has none (`undefined` *or* `null`) — the same fill-if-absent rule as a refresh. It reads the **leaf `channelPreferredSpeed`, never `applyChannelSpeeds`**, precisely because that one excludes ignored channels: **Ignore governs what gets *fetched* by subscription, and nothing here is fetched by subscription.**
- **A duplicate keeps its place, and adding it again still means something.** An already-stashed videoId never moves, is never re-stamped and is never refreshed from the incoming copy — but exactly two fields can change. It is **revived** if it was marked Remove (`state` back to `new`): the alternative is to silently do nothing to a record the next Clean up deletes. And a **present *and different*** incoming `preferredSpeed` (neither `undefined` nor `null`) **overrides** the stashed one — re-adding at the same speed reports `changed: false` and hands back the same array by identity; the paste-a-link flow carries no speed, so there it degrades to "keep what the stash has". A duplicate is deliberately **not** run through the channel-prefs fill — it went through that when first stashed, and a channel speed set since is not a statement about a video already sitting here. `changed` is what a caller persists on; `added` only picks the toast's wording, which must say when a re-add touched something.
- **The second way in costs no network and no auth.** `addCardToStash` in `subscriptions-page.js` — the card menu's one item, or the `t` key — runs the same pure `addToStash` over a freshly-read stash and freshly-read prefs, then one `putStashVideo`; the record is already complete and the avatar comes free from `state.channels` (the key **omitted entirely** when there is none, never an explicit `undefined`). Two rules to preserve: the stash write happens **before** the source card is marked, so a failed write leaves the card untouched and there is nothing to revert; and an already-stashed video is still marked whatever the add did over there. The mark is `setVideoState(id, STATE_SKIPPED)`, never `toggleSkip` — a mark, not a toggle, so the menu cannot un-skip an already-skipped card.
- **It syncs across tabs, and the merge protects only what is mid-write.** `index.html`'s "Add to stash" writes this store from a tab holding a *different* lock, inserting **or updating**, so a Stash tab's list can already be stale; on the signal `store.js` posts for every committed `stash` write, `stash-page.js` re-reads and merges with the pure `reconcileStash(current, fresh, inFlight)`. The signal is **coalesced, never acted on directly**: a `syncPending` flag defers the re-read by `STASH_SYNC_COALESCE_MS`, so a burst of writes in the other tab costs **one** read and one render, not one of each. It takes **MEMBERSHIP from `fresh`, and CONTENT from `fresh` too — except for the videoIds this tab has a write IN FLIGHT for**, whose local objects are kept untouched. Do not "simplify" that exception into a wholesale replace: this page marks **optimistically**, so for the length of that write disk is behind memory for that videoId, and adopting it would silently un-mark the card the user just clicked. It **must not be widened back to "every videoId we already hold"** — the other tab *updates* existing records now, so a record this tab is not writing has to be free to change out from under it, or a remote un-mark would never land here. The scope is `inFlightWrites`, refcounted (two writes for one id can overlap) and bracketed around the module's single `putStashVideo` helper. `changed` covers **membership moving OR a record we hold coming back with different content**, and **no change means no re-render at all**; a re-render goes through `renderKeepingPlace()`, which restores the queue pane's `scrollTop` and re-focuses the same control in the same card, skipping hidden subtrees (a closed menu's panel) so focus cannot fall to `<body>`.
- **Only the stash syncs, and only one way.** `videos` has a single writer that the `yqa_tab` lock keeps single, so a `videos` broadcast could never have a consumer; and `subscriptions-page.js` subscribes to nothing in return, holding no stash state. **Do not generalize it into a per-store mechanism.**

`parseVideoId(input)` is the front door: anchored regexes, **not `new URL()`** (which throws on the protocol-less input we must accept, and a bare id is not a URL at all), covering `/watch?v=`, `/shorts|embed|live|v/`, `youtu.be/`, and a bare 11-char id, with lookalike hosts ruled out by the `^` anchor. All five helpers are pure, live in `queue.js`, and have tests.

### Module layering (respect these boundaries)

Data flows `auth → api → store → queue → ui/*-page.js → player`. That arrow describes **data and ownership, not the import graph**: `api.js` imports `uploadsPlaylistId`/`compareIso`/`parseIsoDuration` back out of `queue.js`, which is fine precisely because `queue.js` is pure — being pure is what makes it importable from anywhere. There are **three entry points**, one per page, all named `*-page.js`: `subscriptions-page.js` (`index.html`), `stash-page.js` (`stash.html`), `channels-page.js` (`channels.html`); `page-chrome.js` is the leaf chrome all three share. All three carry the same nav strip and the same `<h1>` "YouTube Queue" — page identity comes from `aria-current` + `<title>` + the tagline, not from the heading. Each module owns one concern:

- `config.js` — constants only (storage keys, `API_BASE`, `OAUTH_SCOPE`, states, tunables, the IndexedDB identity), each declared **exactly once** for the whole app; no module redeclares one locally. A **retired** key is the one exception, having no live constant left to point at: `migrations.js` names `yqa_playback_rate`/`yqa_default_rate` inline, to delete them. `TAB_LOCK`/`STASH_TAB_LOCK` are Web Lock **names** and `STASH_SYNC_CHANNEL` a BroadcastChannel **name** — not storage keys, despite the `yqa_` prefix. `QUEUE_PAGE_STEP` = **10** is how many items of the queue walk one PageUp/PageDown covers — a count of cards, not a screenful of pixels (see Gotchas). It is `queue.js`'s only import, so it must stay free of browser globals too or the Node tests break — and it is the one module every layer may import.
- `auth.js` — Google Identity Services **token model**. Access token is **in-memory only, never persisted** (so sign-in re-approves on every fresh load); re-requested **silently** near expiry (`prompt: 'none'`), but the 401 retry is `requestToken({ interactive: true })` and may put UI on screen. Scope is `youtube.force-ssl` (read + `videos.rate` write for the Like button). **`ensureAuthorized(clientId, { forceNew })` is the single composed "authorize on demand" gesture**, called by **every** API-backed control on both queue pages, always straight from the click handler so the GIS popup keeps its user-gesture exemption. It reads no storage and touches no DOM, and **throws** rather than call `initAuth(null)` on a missing Client ID. It keeps **no once-per-load memo**: `initAuth` is idempotent per Client ID and re-initializes on a *changed* one, so a cached "prepared" flag would let "Change Client ID" mid-session authorize against the stale client. `forceNew: true` is for the cases where the token we already hold **is** the problem — the 401/403 re-consent retry behind Like (`ensureToken` would hand back the same scope-less token) and Sign in. Everything auth.js throws is an `Error` **with no `.kind`** (the GIS-path ones do carry a `.code`), so it falls through any `ApiError`-only routing: each page's error router needs its non-`ApiError` tail or the user gets raw internal text.
- `api.js` — `fetch` to the YouTube Data API v3, `Bearer` token, **no API key**. **`search.list` is never used** (too expensive). The uploads playlist id comes from the **UC→UU trick** (`uploadsPlaylistId()` swaps a channelId's leading `UC` for `UU`) — no API call, except for the rare non-`UC` id, which falls back to `resolveUploadsPlaylist` → one real `channels.list?part=contentDetails` at 1 unit. Channel avatars ride along free in `subscriptions.list`. `videos.list` is batched ≤50 ids/call; `getVideoDetails` requests `part=contentDetails,status,snippet` and returns the **snippet identity fields too**, at **zero** extra quota. `getVideosByIds(ids)` assembles **full records** in the shape the playlist path builds — record assembly stays in this layer — over **no new request path**; `getChannelAvatars(ids)` is `channels.list?part=snippet`, chunked ≤50 ids/call like `getVideoDetails`, for channels not already in `yqa_channels`. Ids the API omits are simply absent from the result. Errors are `ApiError` with a `kind` (`auth`/`quota`/`forbidden`/`notfound`/`network`/`http`). Quota is 10,000 units/day.
- `store.js` — video records in **IndexedDB**: **one** `yqa` database at `IDB_VERSION` **2**, holding **two** object stores that share the keyPath `videoId` and the same record shape — `videos` (the burn-down queue) and `stash` (the curated queue, whose records carry `addedAt` + `channelAvatarUrl` on top). Two stores rather than one flagged store, so the queues can never collide on a videoId. The public video APIs are thin wrappers over private helpers parameterized by store name, so **the store names never leave this module** — no other layer may open the database itself. **IndexedDB is required — there is no localStorage fallback for videos.** **Roll forward, never back:** `IDB_VERSION` went 1 → 2 to add `stash`, and v1 code opening a v2 database gets a `VersionError` → `req.onerror` → the sticky `dbUnavailable` flag → the permanent "Storage unavailable" wall, for **every user who has already loaded v2**. Since deploy = push to `main` with no CI, `git revert` is the natural rollback and would be **worse than any bug it undoes** — fix forward, never revert past a version bump. Two fatal conditions, each a sticky module flag after which every video API throws and the page halts startup behind a full-screen error. Genuinely **unavailable** (`indexedDB == null` — a bare global read, so a truly *absent* global `ReferenceError`s instead of producing this; `open()` throws; `req.onerror`) → `DbUnavailableError`, over a screen naming the likely causes: site data blocked for this origin, corrupt DB, full disk. **Blocked** — the data is there but inaccessible (`onblocked`, `db.onversionchange`, or the exported `standDownForOtherTab()` a page's single-tab guard calls) → `DbBlockedError`, over a "close the other tabs and reload" screen; `onversionchange` also closes this connection, so another tab's upgrade is never blocked. `dbBlocked` is checked **before** `dbUnavailable`, because an aborted blocked upgrade can set both and "close the other tab(s)" is then the actionable message. **The memoized open, both flags and `standDownForOtherTab()` are per-DATABASE, never per-store** — do not "fix" this into per-store granularity: a database that cannot be opened, or that another tab owns, is equally unusable for every store inside it. The `stash` store has **two** writers in differently-locked tabs — `stash.html`'s add form and `index.html`'s "Add to stash" — so every stash write is the single-key upsert `putStashVideo` and **there is deliberately no bulk stash put**: a whole-set `putAll` would overwrite a live Stash tab's entire list rather than one key of it. Do not restore the symmetry. **Every committed `stash` write announces itself** on the stash's BroadcastChannel, posted by the private `putOne`/`deleteAll` from `tx.oncomplete` — after the commit, so a listener re-reading on the signal can never see the pre-write state, and from inside this module so a new write site cannot forget. The signal **carries no records on purpose**: IndexedDB is the single source of truth, and a payload would be a second copy of it, stale the moment a message is missed. **One** channel object does both the posting and the delivering to the exported `onStashChanged(handler)`: a `BroadcastChannel` never receives its *own* posts, so a second object in the same document would bounce every local write straight back. Lazy and defensive — a missing (or throwing) `BroadcastChannel` leaves it null forever and every write still works, just without sync, and a failed post never fails a committed write. Settings/floor/cutoff/channels/speeds live in localStorage (an empty `yqa_channel_prefs` map removes the key). Holds **no migration logic of its own**: the localStorage read paths are plain parses, and `readAll()` — the single `getAll` path behind **both** stores — hands its result to `migrateVideos()`, so a record migration covers the stash by construction instead of fixing one store and leaving the other on the old shape.
- `migrations.js` — **every** data migration, so retiring them later is deleting this file plus its **four** call sites (`store.js`'s `readAll()` and the boot of each `*-page.js` entry point). No browser globals at import time, so `migrations.test.mjs` imports it under Node; `localStorage` is touched only inside one function body. Its three exports are all idempotent and all tolerant of malformed entries: `migrateVideos(records)` runs on **every** IndexedDB read of **either** store, in memory only — nothing is written back, so no `IDB_VERSION` bump is needed; `migrateChannelPrefs(prefs)` is the same per prefs entry (one left with no properties is dropped — it reads identically to an absent one) but runs on **no read path at all**, `migrateLocalStorage` being its only production caller, which is exactly why `loadChannelPrefs` stays a plain parse; `migrateLocalStorage()` is the one-shot on-load pass **all three** entry points run before anything reads prefs, and the only one that rewrites storage **on disk**, so the read paths stay plain parses — it writes only when the shape changed, and never throws when storage is unavailable. **Documentation convention:** a function's JSDoc states only its general contract, while each individual migration is a date-marked `// YYYY-MM-DD — <name>: …` comment inside the body and is explained **nowhere else** — retiring one is deleting its block plus its tests; the file goes when the last block does. Imports `config.js` only — **never `store.js`**, which imports it.
- `queue.js` — **pure functions only** (see purity rule below). Every derivation lives here: the FLOOR/CUTOFF and window computations, cleanup selection, playability (one private `isPlayable` — still `new` **and** embeddable — shared by `nextPlayable`/`firstPlayable`, so eligibility is declared once), refresh merging and channel-speed application, duration/shorts helpers, the two channel-display resolvers, the channel-prefs helpers, and the stash's five (see The Stash above).
- `ui.js` — XSS-safe DOM construction. **`skipLabel` is display only** (`'Remove'` on the stash): it never changes the mark button's `btn--skip` class, so `setCardState` and the CSS keep working. **`cardMenu(rec)`'s presence on `handlers` plus a non-empty return** is what renders a card's overflow menu — a page suppresses it per record by returning nothing — and it runs once per card during row construction, so keep it **cheap and side-effect-free**. `handlers` stays a **callbacks-only bag** — which is why `skipLabel` is a positional param and `cardMenu`, being a callback, may live there. The menu goes into **both** footers (a non-embeddable video can still be stashed) as a `.row__menu` **wrapper**, never a bare `.btn` child of `.row__actions`: every direct `.btn` there takes an equal flex share and a fourth would squeeze ▶ Play. The wrapper is no `.row` and carries neither `btn--skip` nor `btn--cardspeed`, so arrow-key card navigation, `setCardState` and `setCardSpeed` keep finding what they expect. **At most one menu is ever open** (opening a second closes the first); its reference and both document listeners come off in `closeCardMenu()`, which `renderQueue` calls **before** it clears the list — a menu whose DOM is about to be discarded must never leave a live listener or a dangling reference behind. The trigger is its **only** way in and `ui.js` exports nothing for it, so no page module ever names `.btn--menu` or `.row__menu-panel`. It is a **disclosure, not an ARIA menu**: `aria-expanded` plus an `aria-controls` naming the panel's per-card id, and no `role="menu"` / `role="menuitem"` / `aria-haspopup`, because opening moves no focus. The trigger renders **no text** — its three dots are a `content` on `.btn--menu::before`, so the glyph is declared in one place — and generated content cannot reach the accessible name, so its `aria-label` ("More actions") is the only thing naming it. **Tab reaches the items** only because the panel is the trigger's next sibling inside the wrapper — move it out and both that and the wrapper's `focusout` break. **Three closers, not one** — a `focusout` on the wrapper whose `relatedTarget` is outside it, an outside `pointerdown`, and Esc — because focusout alone misses a click on something unfocusable; `relatedTarget: null` (focus fell into the player iframe — see that gotcha) is safe to treat as *left*. Closing **restores focus to the trigger only while focus is still inside the panel**; a focusout-driven close passes `restoreFocus: false` and leaves focus where the user is taking it. **`renderQueue` gives "Show all (N)" a busy label (`Loading…`) and DEFERS `more.onShowAll`** by one *painted* frame — building thousands of cards freezes the page, and nothing said the click had registered — via a **`setTimeout(…, 0)` scheduled from inside a `requestAnimationFrame`**, since rAF callbacks run *before* the frame is painted. Its re-entry guard is a plain flag and **never the `disabled` property**: disabling the focused control drops focus to `<body>`, and the arrows land a keyboard user on exactly this button. If `onShowAll` throws, the idle label goes back, the flag clears, and the error is rethrown untouched. `buildAvatar` renders an **already-resolved** `{ title, avatarUrl }` and holds **no** resolution policy: pages pass a `resolveChannel(rec)` closure, not a `channels` map. Both policies are pure, in `queue.js` — **`subscriptionChannelInfo`** is the map ALONE, a record-carried `channelAvatarUrl` deliberately ignored, since `index.html` writes `yqa_channels` and its `state.channels` is the authority (so a stored video self-heals on the next refresh); **`stashChannelInfo`** takes the record's own avatar first, the map as fallback. `buildChannelBadge` resolves the title **once** for the whole badge, so a card can never show two answers for one channel; inside the link the avatar is **decorative** (`buildAvatar(info, true)`, `alt=''`) — the name beside it is already the link text. **`renderPlayerTitle` appends an `<a class="row__title">` as a CHILD of the unchanged `<p id="player-title">`**, never replacing the container — the id, the tag and the live region survive, and an empty player is an empty paragraph with no tab stop. A link, because the player frame is deliberately out of the tab order (see that gotcha) and the video's own page was otherwise keyboard-unreachable; borrowing the card's class — as `renderPlayerMeta` borrows the meta row's — is what stops the bar and a card drifting apart. All three watch URLs come from **one private `watchUrl(videoId)`**. `toast.js` — notifications.
- `player.js` — YouTube IFrame API wrapper; holds **no queue/app state** (callbacks wire it to the page module that created it). Uses the **standard `youtube.com`** IFrame API, not `youtube-nocookie` — the standard domain feeds watch history when signed in. Its one piece of DOM policy is `detachIframeFromTabOrder()`, the `tabindex="-1"` that keeps the frame out of the sequential tab order (see the iframe gotcha): it lives here because this module **creates** the element and alone knows the moment it exists. It runs at exactly **two** sites — after the `YT.Player` constructor and again in `onReady` — and nothing **after** ready can replace the element, so **no MutationObserver is warranted**.
- `page-chrome.js` — leaf **page chrome** shared by every entry point, with **no app state and no queue logic**: the tab lock, the fatal-storage screens, the error describers, `reportIfFatalDb` (put it on `.catch()` for best-effort writes, so a mid-session stand-down surfaces instead of silently no-oping), the curtain, the iframe focus guard, and `initQueueFocus` — the two-pane focus navigation both player pages drive (see Gotchas). **First cause wins** on the error screens: one per page load, since one fatal condition routinely produces another and every screen ends in Reload anyway. `initQueueFocus` owns the **remembered card** as closure state (no page's `state` mirrors it) and is built on one gate and one walk, so a new key calls them rather than re-deriving either; keep it single-copy — duplicated per page, these tables drift apart. Everything page-specific is a **parameter** — lock name, curtain node, iframe getter, the two panes — so a new entry point needs no change here. Imports only `ui.js`, `toast.js`, the two error classes from `store.js` and one tunable from `config.js`, and owns **no keydown listener**: it binds its own wheel, window-blur and queue-list `focusin` handlers, but hands *keys* back as functions, so every shortcut stays in its page's own keydown table.
- `subscriptions-page.js` — entry point for **`index.html`**, the wiring/state hub (`state` object + `dom` refs). `stash-page.js` reaches the same layer set, so what is **only here** is the domain: fetching, the FLOOR/CUTOFF machinery, the `yqa_channels`/`yqa_channel_prefs` maps and the cutoff onboarding. Owns event binding, its page's keyboard shortcuts, onboarding, `cleanup()`, `setVideoState`/`toggleSkip`, refresh orchestration, and the `yqa_tab` single-tab guard (see Gotchas). It also writes the **`stash`** object store, via `addCardToStash()` (card menu + `t` key; one `putStashVideo` upsert, skipped entirely when `addToStash` reports the add changed nothing — see The Stash), so **`stash.html` is not that store's only writer**. It **subscribes to nothing** in return, holding no stash state a signal could update.
- `stash-page.js` — entry point for **`stash.html`** (the domain model is in The Stash above). A **sibling** of `subscriptions-page.js`: **never import that module — it boots the other page**. Self-sufficient, carrying its own Client ID setup panel, so a brand-new browser can be set up here. Smaller purely by omission — no fetching, no FLOOR/CUTOFF, no stats, no hide-marked filter, no jump-to-last-skipped, and no keys for any of them. Records enter **through this page** only via the add form (the other entrance is `index.html`'s "Add to stash"), and **all of the add flow's** feedback is a toast — errors, the duplicate notice, progress and success alike — because an inline status line under the field reflowed the page on every add. (The Client ID setup panel keeps its own inline `showStatus` line; nothing about it reflows a queue.) The field keeps only `aria-invalid` on a parse failure — validity state, not a message — cleared by the next keystroke. It is also the **only** subscriber to the stash's cross-tab signal (inert until `state.booted`). Shares `yqa_playback_speed` / `yqa_default_speed` with the subscriptions page — one global player setting — and holds the `yqa_stash_tab` lock.
- `channels-page.js` — entry point for the standalone **`channels.html`** page (reached from the shared nav strip): channels alphabetically with per-channel prefs, an Ignore toggle and a preferred-speed toggle. **Never imports `subscriptions-page.js`** (importing it boots the whole app). No auth, no API calls, and it **never writes video records** — multi-tab safe, so it takes no tab lock: it only reads `loadChannels()` and reads/writes `yqa_channel_prefs` (`LS_CHANNEL_PREFS`; shape `{ [channelId]: { ignored?: true, speed?: number } }`, only non-default values stored; the pure helpers live in `queue.js`). Its whole chrome is `initCurtain({ exemptSelector: '.channels-main', coverOnWheelDown: false })` plus an Esc-only keydown handler.

### State & marking

`STATE_NEW='new'` vs `STATE_SKIPPED='skipped'` are the only states, declared **once in `config.js`** and imported everywhere (including `queue.js`) — never redeclare one per-module: a copy that drifted would have the writers persisting one value while the queue derivations still keyed off the other. **"handled" everywhere means `state !== 'new'`.** There is **no state normalization on read**, and deleting it was safe because nothing anywhere compares `=== STATE_SKIPPED` (it is only ever a value *written*; every read is `=== 'new'` or `!== 'new'`) — so a legacy `watched`/`not_interested` record already behaves exactly like `skipped`.

Marking is **two functions**: `setVideoState` **never toggles** — it sets the state as given; `toggleSkip` (Skip button / `x` key) picks `new` for **any** handled value and `skipped` otherwise, then delegates. Auto-mark-on-video-end calls `setVideoState` directly and always SETS `skipped`. `stash-page.js` mirrors this exactly (`toggleRemove`, after that page's "Remove" label) — same two states, same pick, so the label is display only and **no third state exists**. UI updates optimistically (grey in place, no re-render) then persists async, reverting on failure.

### Player behavior

Auto-advance on `ENDED` marks the finished video `skipped` and plays `nextPlayable` (next later `new` **and embeddable** video; non-embeddable ones open on youtube.com). Watch position is polled every 5s and persisted for resume; playback speed carries across videos via `effectiveSpeed` (per-video preferred > default-speed setting > current). Like is a `videos.rate` write whose liked flag is stored **locally only** and never fetched back. The button is **not** gated on being signed in — it authorizes on demand — and the ORDER matters: authorization happens **before** the optimistic flip, so a cancelled sign-in leaves the heart exactly as it was and there is nothing to revert. `state.liking` (not auth state) is what disables the button for the duration, so a second click — or the `l` key — cannot stack a second token request while the consent popup is open.

`updatePlayingControls()` in **each of the two player pages** (`channels.html` has no player) derives the empty overlay's Start button **and** its text from **one** condition — `!state.playing && firstPlayable(…)` — so the overlay shows **exactly one of {button, text}**, never both and never neither; `state.playerCaughtUp` is a **text-selector only** and can never suppress a live button. The button is **hidden, not disabled**, so it never sits dead in the tab order, and `firstPlayable` scans the **full** list: Hide-skipped and the render window limit what is *rendered*, not what can be *played*. The same `state.playing` hides the whole now-playing bar, a **visibility layer only**: every control keeps its own `disabled` logic underneath. `.player__frame` sizes from its own `aspect-ratio` and the pane is top-aligned, so the bar coming and going below it never moves or resizes the video.

### Refresh: "Fetch new" vs "Refresh all"

Signed out is not a special case: `runRefresh` raises `state.refreshing` (which is also what stops a second click stacking a second token request) and then `ensureAuthorized`s inside the click, so **one** click on a signed-out page both authorizes and fetches. Both buttons call the same `runRefresh(bound, sweepSpeeds)`; only two things differ — the per-channel lower bound (the floor for "Refresh all", or `incrementalSince(…)` for "Fetch new": newest stored `publishedAt` minus a 6h buffer) and the channel-speed sweep flag, **passed explicitly, never inferred from the bound**. Upsert-by-`videoId` preserves existing state; neither resets or duplicates. Known limit: "Fetch new" won't pull the back-catalog of a newly-subscribed channel — use "Refresh all".

Per-channel prefs (`yqa_channel_prefs`, edited on `channels.html`) are read **fresh inside `runRefresh`** — never cached at startup — so edits made in a Channels tab apply to the next fetch without reloading the main tab. Ignored channels are skipped entirely in the per-channel loop (no uploads request at all — saves quota; their existing records are untouched).

A refresh is the **only** channel-pruning site, run after the merge **and** the post-sync `cleanup()` so it sees that refresh's final record set: a `yqa_channels` entry — and its `yqa_channel_prefs` entry — is dropped only when the channel is **both** absent from the freshly-fetched subscriptions **and** has zero stored records, so an unsubscribed channel with videos still queued keeps its avatar/title and drops on a later refresh once they drain. The sweep covers the **union** of both maps, so an **orphan** prefs entry with no `yqa_channels` entry is judged by those same two conditions. **An empty (or non-array) subs list prunes nothing** — that reads as a failed fetch, not as "unsubscribed from everything" — and the prune never runs on the `init()` or "Trim front" cleanup paths, which have no subs list. It re-reads the prefs fresh at the prune site.

The merge is the pure `mergeRefresh` in `queue.js`: upsert, then apply each channel's speed to the **merged** set, so brand-new arrivals are included. Either way it stays **one write** — `mergeRefresh` then a single `putVideos` — and `mergeAndPersist` stays thin enough (merge + write + recompute) that `queue.test.mjs` exercises the real composition rather than a mirror of it. The rule is **fill-if-absent**: a record whose `preferredSpeed` is unset (`undefined` *or* `null`) and whose channel has a speed gets it; a record with an explicit per-video speed is **never** overwritten or cleared; ignored channels are excluded. **How far the fill reaches depends on the mode:**

- **"Refresh all"** (`sweepSpeeds = true`) sweeps the **whole stored record set**, so older already-stored videos get the channel's speed too.
- **"Fetch new"** (`sweepSpeeds = false`) covers only the videoIds this fetch **newly inserted**, so the older part of the queue is not re-sped — and videos re-returned inside the 6h buffer window count as already-stored and keep what they have.

Known limits (accepted): after un-ignoring a channel, "Fetch new" won't backfill videos published while it was ignored — use "Refresh all"; and toggling a card's speed OFF just removes `preferredSpeed`, with no "cleared by user" marker, so a later **"Refresh all"** re-applies the channel speed to that video ("Fetch new" does not).

## Conventions

- **`queue.js` must stay pure** — no `window`/`document`/`fetch`/`localStorage`/`IndexedDB` anywhere in it, so `queue.test.mjs` can import it under Node; `config.js` is its only permitted import. New pure logic goes here **with a matching test**.
- **XSS-safe DOM** in `ui.js`/`toast.js` — all API-derived strings go through `textContent`/text nodes; never `innerHTML` for API data; ids go through `encodeURIComponent`.
- Keep the layering: persistence in `store.js`, network in `api.js`, DOM in `ui.js`, shared page chrome in `page-chrome.js`, orchestration in the `*-page.js` entry points, `player.js` state-free.
- All localStorage keys are namespaced `yqa_`.
- The app **never auto-fetches** — signing in only authorizes; the user triggers fetches explicitly. The converse is why nothing is auth-gated: a triggered action **authorizes itself** on demand (`ensureAuthorized`) rather than requiring a prior sign-in. The Sign in / Sign out buttons and the status label stay on both queue pages — they *display* auth state, and Sign out is not otherwise reachable — but they gate nothing.
- **README stays light** — the setup/OAuth guide and the non-obvious gotchas, nothing else; depth belongs here in CLAUDE.md. Behavior a user can see by just looking at the app (a new button, a bar that hides itself) goes in **neither** file.

## Gotchas

- **Cross-origin iframe swallows keyboard/wheel/pointer events.** Focus inside the youtube.com iframe kills document-level shortcuts (including Esc). **Two mechanisms, not interchangeable — keep both.** (1) A **click** on the video still moves focus into the frame; `bindIframeFocusGuard(getIframe)` in `page-chrome.js` catches that on window blur and blurs it back to `<body>` — deliberately, since that is where the arrow walk's re-entry rule expects it — skipped when the document is hidden, so alt-tabbing doesn't yank focus. (2) **Tab** must never reach the frame at all, enforced by `player.js`'s `detachIframeFromTabOrder()`. The guard alone could not do that job: `.workspace__player` is `tabindex="-1"`, so Tab out of the pane entered the frame; the guard bounced focus to `<body>` but **Chrome's sequential-focus starting point stayed on the iframe** — a permanent two-element loop that killed forward Tab for the rest of the session, on both pages, reproducing with **nothing playing**. **Deliberate consequence: YouTube's own in-frame controls (captions, quality, the scrubber) are NOT Tab-reachable, and that is not to be "fixed"** — a frame that keeps focus takes the app's whole keyboard layer with it, so the guard would bounce focus straight back out anyway. The keyboard route to the video's own page is the **title link** (`renderPlayerTitle`). Preserve **both** contracts when touching focus/keyboard code.
- **Privacy curtain** (`#curtain`): on **all three pages**, from `initCurtain()` in `page-chrome.js`, which owns the covering flag (no page mirrors it). Wheel-down outside the exempt scroll area covers the page with a full-viewport overlay, wheel-up lifts it, Esc toggles it (each page wires Esc from its own keydown table). Whether wheel-**down** may cover is decided by **layout, not width**: `index.html` and `stash.html` carry `body.app-active` — added in JS when the app is revealed, not in the HTML — a `100dvh` flex column whose panes scroll internally, so covering steals no scrolling and they take the default `coverOnWheelDown: true`. **Onboarding removes it** (the setup and cutoff panels scroll the document), so those pages briefly document-scroll like `channels.html` while still able to cover on wheel-down — accepted: there is nothing behind them worth scrolling to. `channels.html` has no `app-active` — its **document** scrolls at every width — so it passes **`coverOnWheelDown: false`**, or the channel list would be unscrollable. `narrowQuery` (≤900px stacked layout) encodes the same rule by width for the pages that do cover. **Wheel-up and Esc work everywhere, at every width.** Purely visual — it does not pause the player.
- **Single-tab guard**: **two** lock names, one per page that **writes** an object store — `TAB_LOCK` (`yqa_tab`, `index.html` → `videos`) and `STASH_TAB_LOCK` (`yqa_stash_tab`, `stash.html` → `stash`). A second tab **of the same page** yields; the holder is never interrupted. **A Subscriptions tab and a Stash tab may be open simultaneously** — that is why there are two names over two stores. Their writes are no longer strictly **disjoint** (`index.html`'s "Add to stash" writes the `stash` store), so what keeps the guard sound is the *shape* of that write: a single `putStashVideo` upsert of one videoId against a stash list re-read fresh with `getAllStashVideos()` at the moment of the add — it can never clobber what a Stash tab wrote, and never leaves one stale (the write announces itself on the stash's `BroadcastChannel`; see The Stash). **Cross-tab sync exists for the `stash` store alone**, precisely because this guard makes it pointless anywhere else: `videos` has one writer that `yqa_tab` keeps single, so nothing could ever be listening. `channels.html` asks for **neither** (it writes no video records). Each page's `init()` fires `requestTabLock(name)` at the top and awaits it at its checkpoint, **immediately after `cacheDom()`** — before any store read, settings restore, the stash's remove-sweep and `bindEvents()` — so a tab that is not granted shows `showSupersededError()` behind `#blocked-overlay` having read no records, written nothing and bound no handlers. Race-free by construction, decided once at startup — no mid-session halt. **Fails open, never closed:** without `navigator.locks`, or if the request throws or rejects, the tab boots normally — the guard must never lock the owner out of their own queue.
- **An author `display` beats the UA `[hidden]` rule**, so anything hideable needs its own `[hidden] { display: none }` in `styles.css`. Buttons are covered wholesale by the general **`.btn[hidden]`** rule: `setVisible()` sets the `hidden` attribute and `.btn` is `inline-flex`, so without it a "hidden" button renders. `body.app-active #app-main.app[hidden]` needs that exact selector to out-specify the `body.app-active #app-main.app` two-pane layout rule above it, or the fatal-storage overlay leaves the app focusable in the a11y tree behind it. Miss one and the "hidden" element stays on screen.
- Keyboard shortcuts live in **two** `onGlobalKeydown` tables — `subscriptions-page.js` and `stash-page.js` (the same gestures minus refresh / hide-marked / jump-to-last-marked) — plus an **Esc-only** handler in `channels-page.js`. **Both tables** ignore Ctrl/Cmd/Alt combos and typing in inputs; the Esc-only handler checks modifiers alone, which is harmless because **Esc is the panic key and is handled *before* those guards**, on every page and in every state, so it works mid-typing, during onboarding and with a card menu open — that menu closes itself on the press but neither stops nor prevents the event, or two document listeners strand behind the curtain. **"The focused card" is whichever `.row` *contains* `document.activeElement`** — `closest('.row')`, resolved by both tables' `focusedCardIndex` for `x`, `t` and `1`/`5`/`2`, and again inside `page-chrome`'s `moveCard` for the arrows, which the tables only delegate to — so they keep working from any control inside a card. **`t` stashes the focused card**, on `index.html` only, through the same `addCardToStash` the card menu item calls, passing `{ advanceFocus: true }` — as `x` does and the Skip button does not — so a run of `t`s walks the queue instead of firing twice on one card. **No key opens the menu**: its trigger is its only way in, and opening leaves focus *on* it. **`Enter` and `Space` are the deliberate exception, matching the `.row` exactly**: each natively activates a focused button or link, so resolving them through the containing card would double-act. Don't tidy that inconsistency away. (`1`/`5`/`2` move no focus, so a menu stays open over the speed it just set.) `ui.js`'s **capture-phase** `document` keydown swallows nothing: that Esc close, plus a staleness check first — a card can be dropped without `renderQueue` (Hide-marked on, auto-advance on `ENDED`), leaving a detached panel still holding both document listeners, so `!panel.isConnected` retires the menu and lets the key through untouched.
- **`ArrowUp`/`ArrowDown`, `PageUp`/`PageDown` and `Home`/`End` all walk `[card1 … cardN, "Show all (N)"?]`**, with the mechanics deliberately **not** in either table: the entries call `moveCard(dir, { page })` / `focusEdge(dir)` from `page-chrome.js`'s `initQueueFocus` and `preventDefault()` **only when it reports the key was taken**, so everything it declines keeps its native scrolling. The windowing footer button is a walk **item, not a card**: ArrowDown off the last card lands on it, ArrowUp from it steps back to that card **by position**, ArrowDown on it clamps, and **End** lands on it whenever one is rendered — never a card, because the two things being a card *means* (being the target the list is **entered** at, and being what `x` / `t` / `1`,`5`,`2` act on) are both meaningless for it. **Where the keys apply is a question about LAYOUT, not about what happens to hold focus.** In the two-pane layout `body.app-active` is a `100dvh` flex column whose panes scroll *internally* and the document does not scroll at all — so outside `.workspace__player` there is no native scroll for a key to belong to and it belongs to the queue, `<body>` included; inside that pane they always decline, so it goes on scrolling. In the **stacked (≤900px)** layout the queue pane is `overflow: visible` and the **document** scrolls, so only focus genuinely *inside* `.workspace__queue` is taken. The narrow/wide question is asked as a `narrowQuery` media query — the same 900px breakpoint `initCurtain` uses — never by measuring.
- **The remembered card is what a press from outside the list enters at** — a `focusin` on the queue list notes the `videoId`, never the element (`renderQueue` rebuilds the `<ul>`, so a node reference is detached one render later); it resolves against the **current** list at use time and falls back to the first card. Focus landing on a non-card in the list leaves the note standing: it answers "where does a press from *outside* the list go", and the footer button is never an honest place to be dropped into a queue. It matters most from `<body>`, where `bindIframeFocusGuard` drops focus on every click of the video — without it the arrows would stop working after one click. The relative keys **clamp** at the ends rather than wrapping, and the clamp does **two** things that must both survive: it still moves focus onto the item, *and* it reports **not**-handled. Landing on the `.row` is how an arrow gets focus **out** of an open menu (it leaves the `.row__menu` wrapper, whose `focusout` dismisses it); reporting not-handled is what hands the pane back its native scroll at the ends of the walk. **`PageUp`/`PageDown` are `moveCard` itself with `{ page: true }`** — a step of `QUEUE_PAGE_STEP` (10) items instead of 1 — inheriting the entry rule (from outside the list they still land on the remembered card) and the clamp unchanged; do not write either a second time. Their one difference: **landing the destination at the top of the pane** — `focus({ preventScroll: true })` then `scrollIntoView({ block: 'start' })`, in that order so the default "nearest" scroll never happens and then gets corrected — since "nearest" pins a ten-item jump against the **bottom** edge and reads as an overshoot. **The native page-scroll was tried and deliberately abandoned — do not restore it as a fidelity improvement**: a card is a large enough fraction of the pane that a browser page advances barely more than one card, and stalls outright when the bottom is already in view — hence a fixed step of items. (For anyone asserting on a scroll position: **Chrome animates a keyboard scroll**, so a value read straight after the key is still in flight.) **`Home`/`End` are absolute** — nothing to step from and nothing to clamp: `focusEdge(dir)` names the first / last walk item outright, and an empty list declines, keeping the keys' native meaning. All four move focus and let the scroll follow, so the **remembered card updates for free**; none gets a `<kbd>` help line, which teach only app-specific, unguessable keys.
- **`/` throws focus between the two panes** — out of `.workspace__player` back to the remembered card, from anywhere else into it — at **every** width, and `preventDefault()`s **whenever it reaches us**, because Firefox opens Quick Find on it (read off `e.key`, Shift allowed, so a layout that shifts `/` still reaches us). Unlike Esc it sits **below** the table's typing / `appMain.hidden` / modifier guards, so it is inert in an input and throughout onboarding — Esc alone is unconditional. The `<aside class="workspace__player">` on both player pages carries **`tabindex="-1"`**: programmatic focus only, never a new tab stop, and once focused it scrolls natively — the entire point, a long description being otherwise unreachable without tabbing through every card's controls. (Its focus ring and the clip band it lives in are the player-pane scrollport gotcha below.) With **no cards at all**, `/` out of the player does nothing and leaves focus where it is: no honest target, and blurring to `<body>` would be a silent loss. **Activating "Show all (N)" destroys the button that was pressed** — the re-render removes the whole `li.queue-more` and nothing replaces it — so both pages place focus by hand or it falls to `<body>`: they read `cardCount()` **before** flipping `state.showAll` and call `focusCardAt(thatCount)` after the re-render, landing on the **first newly-revealed card** (the window only grows, so the pre-expansion count *is* the boundary). `focusCardAt` falls back to the last card, then the first — not decoration: the index is measured against a list since rebuilt. The activation is deferred behind a `Loading…` label (see the `ui.js` bullet), focus held on the button for the wait.
- **The player pane's SCROLLPORT is padded out past its content on every side, and that band is what stops it clipping its own focus rings.** `.workspace__player` carries a `padding` against an equal negative `margin`, so nothing moves but the **clip edge**: `overflow-y: auto` makes the pane a scroll container, which clips **both** axes at its padding box, and `#player-title` / `#player-meta` sit flush against the content edge — so their rings, painted *outside* their element like every ring here, were sliced off at x < 0. Not fixable from the link's side (its content starts on the clip edge), nor by `overflow-clip-margin`: beside `overflow-y: auto`, `overflow-x: clip` **computes to `hidden`** and the margin does nothing. Two consequences. The pane's own `outline-offset` must **not** go negative — the scrollbar rides outward with the padding box and the right-hand segment would land on it. And **the padding band IS the ring headroom**: a ring reaching past it clips silently, with nothing enforcing the relationship — check it in the browser. On the **scrolling** axis the band is headroom only at the two ends of the range: a control hand-scrolled off the top still loses its top segment, as in any scroll container.
- **The channel badge's ring is a PILL drawn INSET into a box padded for it, with the padding cancelled so nothing moves** — the avatar still sits on the row's content edge. `.row__channel-link`'s ring is `999px` (the house radius) at a **negative** `outline-offset`, so it is drawn inside the outermost band of that padded box and **its reach is what the padding must cover** — on the left, inside `.workspace__player`'s scrollport band (above); on the right, paid for by `.row__dot`'s margin. That margin sits on the dot rather than on the row's `gap` because `buildChannelBadge` drops the avatar and the name in as bare flex items when a record has no `channelId`, and that fallback has no ring to make room for. One rule serves the card and the player bar.
- **Hover is accent, focus is a ring, and nothing in the meta row underlines.** `.row__title` (cards *and* the now-playing title) and `.row__channel-link` are one gesture on two links: hover turns the text `var(--accent)`, focus draws the `--focus` ring and does nothing else. **`channels.html`'s `.chan__link` says it the same way** — hover accent on `.chan__title`, no underline anywhere — but keeps the house `1px` offset and takes a **corner radius, not the pill**: `.chan__title` wraps, so that box grows tall and a `999px` radius then makes end caps of half that height, cutting through the text. It needs neither of `.row__channel-link`'s two departures — nothing clips it, `.chan` being no scroll container.
- Shorts detection is a duration ≤90s heuristic (badge only — the API exposes no isShort flag).
