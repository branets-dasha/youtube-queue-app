# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pure client-side "burn-down queue" for YouTube subscriptions: fetch videos from your subscriptions up to a moving cutoff, display them oldest→newest, and play/skip through them. Three static pages, each with its own entry-point module — `index.html` (the queue), `stash.html` (a second, hand-curated queue) and `channels.html` (per-channel prefs). Vanilla HTML/CSS/ES modules — **no build step, no framework, no bundler, no `package.json`, no `node_modules`**. The only runtime dependencies are three Google-hosted scripts (Google Identity Services, YouTube IFrame API, YouTube Data API v3).

Then open `http://localhost:5173`. The served port must match an **Authorized JavaScript origin** on your OAuth Client ID (see OAuth setup in README.md — each user brings their own Client ID; there is no shared one, no API key, no client secret).

## Architecture

### The FLOOR vs live CUTOFF model (core domain concept)

Two distinct ISO timestamps, both in localStorage, are the heart of the app. Understand these before touching queue logic:

- **FLOOR** (`LS_START_CUTOFF` = `yqa_start_cutoff`) — the deletion + fetch boundary. **Moves forward only**, and only inside `cleanup()`. It is the lower bound for the render list, the queue count, and the per-channel lower bound when fetching.
- **CUTOFF** (`LS_CUTOFF` = `yqa_cutoff`) — the live "handled-prefix" marker shown in the stats. **Bidirectional**: `computeCutoff(records, floor)` recomputes it from scratch each call, so it advances as you mark the oldest videos handled and **retreats** when you un-mark one. Always `>= floor`.

`computeCutoff` walks the contiguous *handled* (`state !== 'new'`) prefix strictly after the floor and stops at the first `new` video. It is **tie-safe**: the returned cutoff is always strictly less than the earliest still-`new` video's `publishedAt`, so a handled video sharing a timestamp with a `new` one never pulls the cutoff onto it. Window membership is **strictly after** the cutoff.

`cleanup()` (in `subscriptions-page.js`) is the **only** place videos are deleted and the floor advances: it deletes every present record with `publishedAt <= cutoff`, then sets `floor = cutoff`. It runs in exactly three sites: page-load `init()` (prune-on-reload), after a refresh sync, and the "Trim front" button. Consequence: marked videos stay greyed *in place* (never reordered/removed) until the next cleanup prunes the whole handled prefix.

### The Stash (`stash.html`) — a second queue, deliberately outside FLOOR/CUTOFF

The Stash is a hand-curated companion queue, filled one video at a time — a pasted YouTube link on its own page, or a card's "Add to stash" on the subscriptions page. Nothing is fetched, nothing is deleted by a moving boundary, and **neither the floor nor the cutoff exists for it** — there is no stash timestamp in localStorage at all. Why it can do without them:

- **Order is arrival order.** `sortStash(records)` sorts by **`addedAt`**, oldest first — *not* `publishedAt` — ties broken by `videoId`, with a missing/unparseable `addedAt` sorting **last** (an unstamped record is foreign/hand-edited data, and the tail is where it does least damage). It is the stash's **single sort site**: Phase 3 drag-to-reorder adds an `order` field and changes **only that function**.
- **Deletion is state-based, not position-based.** `stashToClean(records)` returns every handled (`state !== 'new'`) record from **anywhere** in the list, gaps included. Contrast `videosToClean(records, cutoff)`, which is position-based (`publishedAt <= cutoff`) and can therefore only ever delete a contiguous **prefix** — that difference *is* the reason the burn-down queue needs a moving floor and the stash needs none. One implementation (`sweepRemoved()` in `stash-page.js`) backs **both** the "Clean up" button and an on-reload sweep that runs **before the first render**, so a removed card never flashes on screen.
- **No third state.** The mark button reads **"Remove"**, but it stores the same `STATE_SKIPPED`, so `"handled" means state !== 'new'` still holds on both queues. The label is display only (`renderQueue`'s `skipLabel`); the `btn--skip` class is unchanged, so `setCardState` and the CSS are untouched.
- **No dependency on `yqa_channels`.** A stash record carries its own `channelAvatarUrl` (taken free from the already-known map when possible, else one `getChannelAvatars` call), and this page's resolver `stashChannelInfo` prefers it over the map — so `pruneChannels` deleting a channel entry can never blank a stashed card. The map stays as its **fallback**, which is not dead code: records stashed before avatars were captured, and ones whose `attachAvatar` fetch failed, carry none of their own.
- **Adding respects a channel's preferred speed but ignores its Ignore flag.** `addToStash(records, incoming, { addedAt, prefs })` appends, stamps `state`/`addedAt`, and fills `preferredSpeed` from the channel only when the record has none (`undefined` *or* `null`) — the same fill-if-absent rule as a refresh. It reads the **leaf `channelPreferredSpeed`, never `applyChannelSpeeds`**, precisely because that one excludes ignored channels: **Ignore governs what gets *fetched* by subscription, and nothing here is fetched by subscription.** A duplicate videoId mutates nothing — the input array comes back **by identity** with `added: false` and the existing record, so an already-stashed video keeps its place, its `addedAt` and its Remove mark rather than jumping to the end.
- **The second way in costs no network and no auth.** A subscriptions card goes to the stash straight from the queue — its "⋯" menu's one item, "Add to stash", or the `t` key — through `addCardToStash` in `subscriptions-page.js`: it runs that same pure `addToStash` over a freshly-read `getAllStashVideos()` and a freshly-read `loadChannelPrefs()`, then one `putStashVideo`. Unlike the paste-a-link form there is **no `ensureAuthorized`, no `getVideosByIds`, no `getChannelAvatars`** — the record that page already holds is complete, and the avatar comes free from `state.channels`, the map it owns; the avatar is copied onto the record (the key **omitted entirely** when there is none, never an explicit `undefined`) for exactly the reason a hand-added record carries its own. Two decisions worth preserving: the stash write happens **before** the source card is marked — the same ordering rule as the Like button, so a failed write leaves the card untouched and there is nothing to revert — and an **already-stashed** video is still marked (an info toast, no write), because "it is in the stash now" is true either way. The mark is `setVideoState(id, STATE_SKIPPED)`, never `toggleSkip`: a mark, not a toggle, so using the menu on a card that is already skipped cannot un-skip it.

`parseVideoId(input)` is the front door: anchored regexes, **not `new URL()`** (which throws on the protocol-less input we must accept, and a bare id is not a URL at all), covering `/watch?v=`, `/shorts|embed|live|v/`, `youtu.be/`, and a bare 11-char id, with lookalike hosts ruled out by the `^` anchor. All four helpers are pure, live in `queue.js`, and have tests.

### Module layering (respect these boundaries)

Data flows `auth → api → store → queue → ui/*-page.js → player`. There are **three entry points**, one per page, all named `*-page.js`: `subscriptions-page.js` (`index.html`), `stash-page.js` (`stash.html`), `channels-page.js` (`channels.html`); `page-chrome.js` is the leaf chrome all three share. All three pages carry the **same nav strip** in `.topbar__row` (`Subscriptions | Stash | Channels`) with the current page rendered as a `<span aria-current="page">` instead of a link, and the same `<h1>` "YouTube Queue" — page identity comes from `aria-current` + `<title>` + the tagline, not from the heading. Each module owns one concern:

- `config.js` — constants only (storage keys, `API_BASE`, `OAUTH_SCOPE`, states, tunables), each declared **exactly once** for the whole app; no module redeclares one locally. Also the IndexedDB identity (`IDB_NAME`, `IDB_VERSION`, `IDB_STORE_VIDEOS`, `IDB_STORE_STASH`, `IDB_KEYPATH`) and the two Web Lock **names** — `TAB_LOCK` = `yqa_tab`, `STASH_TAB_LOCK` = `yqa_stash_tab` — which are lock names, **not** storage keys, despite the `yqa_` prefix. It is `queue.js`'s only import, so it must stay free of browser globals too or the Node tests break.
- `auth.js` — Google Identity Services **token model**. Access token is **in-memory only, never persisted** (so sign-in re-approves on every fresh load); silently re-requested near expiry / on 401. Scope is `youtube.force-ssl` (read + `videos.rate` write for the Like button). **`ensureAuthorized(clientId, { forceNew })` is the single composed “authorize on demand” gesture** — `waitForGis()` → `initAuth(clientId)` → `ensureToken({ interactiveFallback: true })` — called by **every** API-backed control on both queue pages (Fetch new, Refresh all, Like, the stash's Add, and Sign in itself), always straight from the click handler so the GIS popup keeps its user-gesture exemption. It lives here, not in a page module, because this layer already owns the token model and takes the `clientId` as a parameter; one copy is what keeps the two pages identical (it replaced a page-local `ensureAuthReady()` on `stash-page.js`). It reads no storage and touches no DOM — the caller still supplies the Client ID — and it **throws** rather than call `initAuth(null)` when that id is missing. It carries **no once-per-load memo**: `initAuth` is already idempotent per Client ID (and re-initializes on a *changed* one, so “Change Client ID” mid-session can never authorize against the stale client), and `waitForGis` resolves synchronously once GIS is up, so a cached “prepared” flag would only be a second thing to keep in sync with the id. `forceNew: true` swaps the token step for `requestToken({ interactive: true })` and is for the two cases where the token we already hold **is** the problem: the 401/403 re-consent retry behind Like (where `ensureToken` would hand back the same scope-less token and the retry would fail identically), and Sign in (no session to reuse). Everything auth.js throws is a **plain `Error` with no `.kind`** — GIS not loaded, a token request already in flight, a missing Client ID, a cancelled/blocked popup — so it falls through any `ApiError`-only routing: each page's error router needs its non-`ApiError` tail (`describeAuthFailure` on the subscriptions page, `describeAddFailure` on the stash) or the user gets raw internal text.
- `api.js` — `fetch` to the YouTube Data API v3, `Bearer` token, **no API key**. **`search.list` is never used** (too expensive). Uploads playlist id is derived with the **UC→UU trick** (`uploadsPlaylistId()` swaps the leading `UC` of a channelId for `UU`) — no API call. Channel avatars ride along free in `subscriptions.list`. `videos.list` is batched ≤50 ids/call. `getVideoDetails` requests `part=contentDetails,status,snippet` and returns the **snippet identity fields too** (`title`/`channelId`/`channelTitle`/`publishedAt`/`thumbnailUrl`) — they were always fetched and thrown away, so widening it cost **zero** extra quota and is backward compatible. On top of it: `getVideosByIds(ids)` assembles **full records** in the same shape the playlist path builds (record assembly stays here, next to its sibling producer, rather than migrating into a page module) and adds **no new request path**; `getChannelAvatars(ids)` is one `channels.list?part=snippet` batch, called only for a channel not already in `yqa_channels`. Ids/channels the API omits are simply absent from the result. Errors are `ApiError` with a `kind` (`auth`/`quota`/`forbidden`/`notfound`/`network`/`http`). Quota is 10,000 units/day.
- `store.js` — video records in **IndexedDB**: **one** `yqa` database at `IDB_VERSION` **2**, holding **two** object stores that share the keyPath `videoId` and the same record shape — `videos` (the burn-down queue, written by `index.html`) and `stash` (`IDB_STORE_STASH`; the curated queue, written by `stash.html`, whose records carry `addedAt` + `channelAvatarUrl` on top). Two stores rather than one flagged store so the queues can never collide on a videoId. The `videos` store has exactly **one** writer, `index.html`; the `stash` store has **two** — `stash.html`'s add form and `index.html`'s "Add to stash" card menu — so the pages are **not** strictly disjoint writers, and what lets both tabs be open at once is instead the *shape* of every stash write: the single-key upsert `putStashVideo`, never a whole-set put (see the single-tab guard). **IndexedDB is required — there is no localStorage fallback for videos.** **Roll forward, never back:** `IDB_VERSION` went 1 → 2 to add `stash`, and v1 code opening a v2 database gets a `VersionError` → `req.onerror` → the sticky `dbUnavailable` flag → the permanent "Storage unavailable" wall, for **every user who has already loaded v2**. Since deploy = push to `main` with no CI, `git revert` is the natural rollback and would be **worse than any bug it undoes** — fix forward, never revert past a version bump. (The 1 → 2 changeover itself costs each user exactly one "close the other tabs and reload" screen, from a v1 tab still holding the DB open.) Three triggers in `openDb()` mean genuinely **unavailable** — no `indexedDB` global, `indexedDB.open()` throws, or `req.onerror` — and each sets a sticky module flag, after which every video API throws `DbUnavailableError` and the page halts startup with a blocking full-screen error naming the likely causes (site data blocked for this origin, corrupt DB, full disk). **Distinct case:** `onblocked` (another tab holds the DB open at a different schema version) — the real data is in IndexedDB but inaccessible, so every video API throws `DbBlockedError` and the page halts startup with a blocking full-screen error (`#blocked-overlay`, shared by both via `page-chrome.js`'s `showFatalStorageError`) telling the user to close the other tabs and reload. The open success path installs `db.onversionchange` (a future schema upgrade started by another tab): it closes this connection and flips the same sticky blocked flag, so the other tab's upgrade is never blocked and subsequent video APIs here throw `DbBlockedError`. The **third** setter of that same flag is the exported `standDownForOtherTab()` — called only by a page's single-tab guard (below), it sets `dbBlocked` and closes this connection, deliberately reusing the flag rather than adding a fourth one: the condition is identical (the data is there, this page must not touch it, close the other tab and reload), so no new guard lines are needed. **The memoized open, both sticky flags, `onversionchange`, `onblocked` and `standDownForOtherTab()` are per-DATABASE, never per-store** — do not "fix" this into per-store granularity: a database that cannot be opened, or that another tab owns, is equally unusable for every store inside it, and standing a superseded tab down from *both* queues is exactly what its caller wants. The **seven** video APIs (`getAllVideos`/`putVideo`/`putVideos`/`deleteVideos` and `getAllStashVideos`/`putStashVideo`/`deleteStashVideos`) are thin wrappers over five private helpers parameterized by store name — `openGuarded`, `readAll`, `putOne`, `putAll`, `deleteAll` — so the store names never leave this module and the guard order is written down **exactly once**: `openGuarded` checks `dbBlocked` **before** `dbUnavailable`, because an aborted blocked upgrade can set both flags and "close the other tab(s)" is then the actionable message. **Seven, not eight: there is deliberately no bulk stash put** — `stash.html` may be open beside a queue tab, so every stash write is the one-key upsert `putStashVideo`, which cannot clobber what that tab just wrote the way a whole-set `putAll` would. That reason has since doubled: `index.html` writes this store too ("Add to stash"), from a tab holding a *different* lock, so a bulk put from there would overwrite a live Stash tab's entire list rather than one key of it. `putAll` therefore has exactly one caller, `putVideos`. Do not restore the symmetry. Settings/floor/cutoff/channels/speeds all in localStorage (`getPlaybackSpeed`/`setPlaybackSpeed` for `yqa_playback_speed`, `getDefaultSpeed`/`setDefaultSpeed` for `yqa_default_speed`), plus `loadChannelPrefs()`/`saveChannelPrefs()` for `yqa_channel_prefs` (an empty map removes the key). Holds **no migration logic of its own**: the localStorage read paths are plain parses, and `readAll()` — the single `getAll` path behind **both** stores — hands its result to `migrateVideos()` from `migrations.js`, so a record migration covers the stash by construction instead of silently fixing one store and leaving the other on the old shape.
- `migrations.js` — **every** data migration, so retiring them later is deleting this file plus its **four** call sites (`store.js` `readAll()`, and `init()` in each of the three `*-page.js` entry points). No browser globals at import time, so `migrations.test.mjs` imports it under Node; `localStorage` is touched only inside one function body. Exports exactly three, all idempotent, all tolerant of malformed entries: `migrateVideos(records)` — record shape, run on **every** IndexedDB read of **either** store (mutates + returns, nothing written back, so no `IDB_VERSION` bump — the next put persists the new shape). `migrateChannelPrefs(prefs)` — the same per channel-prefs entry, in memory (an entry a migration leaves with no properties is dropped: it reads identically to an absent one). `migrateLocalStorage()` — the one-shot on-load pass **all three** entry points run before anything reads prefs, and the only one that rewrites storage **on disk** (write only if the shape changed; empty map removes the key), so the read paths stay plain parses; never throws when storage is unavailable. **Documentation convention:** a function's JSDoc states only its general contract, while each individual migration is a date-marked `// YYYY-MM-DD — <name>: …` comment inside the body and is explained **nowhere else** — retiring one is deleting its block plus its tests; the file goes when the last block does. Imports `config.js` only — **never `store.js`**, which imports it.
- `queue.js` — **pure functions only** (see purity rule below). All the derivations: `computeCutoff`, `computeQueue`, `computeVisible`, `videosToClean`, `nextPlayable`/`firstPlayable` (one private `isPlayable` rule — still `new` **and** embeddable — shared by both, so eligibility is declared once), `incrementalSince`, `resumeStart`, `effectiveSpeed`, `applyChannelSpeeds`, `mergeRefresh`, duration/shorts helpers, the two channel-display resolvers (below), and the stash's four (`parseVideoId`, `sortStash`, `stashToClean`, `addToStash` — see The Stash above).
- `ui.js` — XSS-safe DOM construction. `buildQueueRow`/`renderQueue` take a trailing `skipLabel` (default `'Skip'`, `'Remove'` on the stash) — a positional param with a default rather than a key on `handlers`, which is a pure bag of callbacks everywhere else; it changes the mark button's visible label, `aria-label` and `title` and **never** its `btn--skip` class, so `setCardState` and the CSS keep working. The bag itself now carries **one optional key, `onStash(id)`**, and **its presence alone** decides whether a card renders the "⋯" overflow menu — which is exactly why *it* belongs in the bag and `skipLabel` does not: it is a callback, not a display string. `subscriptions-page.js` passes one; `stash-page.js` passes none, so its cards are untouched. The menu goes into **both** footers, embeddable and not (a non-embeddable video can still be stashed), as a `.row__menu` **wrapper** rather than a bare `.btn` child of `.row__actions` — every direct `.btn` there takes an equal flex share and a fourth would squeeze ▶ Play — and the wrapper is not a `.row` and carries neither `btn--skip` nor `btn--cardspeed`, so `j`/`k` navigation, `setCardState` and `setCardSpeed` keep finding exactly what they expect. With it `ui.js` holds its **first interaction state**: one module-level reference to the single open menu (opening a second closes the first, so at most one is ever open) plus the module's only document-level listeners — a capture-phase `keydown` and a `pointerdown` — both removed by `closeCardMenu()`, which `renderQueue` calls **before** it clears the list, so a menu whose DOM is about to be discarded never leaves a live listener or a dangling reference behind. The menu's **only** way in is its own trigger, and `ui.js` exports nothing for it, so no page module ever names `.btn--menu` or `.row__menu-panel`. It is a **disclosure, not an ARIA menu**: no `role="menu"` on the panel, no `role="menuitem"` on the item, no `aria-haspopup` (which announces a menu/dialog/listbox) — only **`aria-expanded`** plus an **`aria-controls`** naming the panel's per-card id, built with `encodeURIComponent` like every other id here, and that pair *is* the whole disclosure contract. The roles came off because **opening moves no focus**: the trigger keeps it, for a mouse click and a keyboard activation alike, so the same key pressed again toggles the menu shut — while the ARIA menu-button pattern *requires* focus to enter the menu on open, so keeping the roles while refusing that would describe the widget to a screen reader as something it is not. A plain container needs no accessible name, so the panel's `aria-label` went with its role; the trigger keeps its own "More actions". **Tab reaches the item** because the panel is the trigger's next sibling inside the wrapper, and leaving is what dismisses: a **`focusout` on the `.row__menu` wrapper** whose `relatedTarget` is outside it closes the menu, which is what stops a Tab from stranding one open behind the card it left (it covers Shift+Tab and clicking away too). Three closers, not one — focusout, the outside `pointerdown` and Esc — because focusout alone misses a click on something unfocusable. `relatedTarget: null` (focus fell into the player iframe — see that gotcha) is safe to treat as *left* here: this widget only asks whether focus is still inside itself, and it is not. Closing **restores focus to the trigger only while focus is still inside the panel** (an Esc press or the item being used); a focusout-driven close passes `restoreFocus: false` and leaves focus exactly where the user is taking it. `buildAvatar(info, decorative)` renders an **already-resolved** `{ title, avatarUrl }` and holds **no** resolution policy of its own: every page passes a `resolveChannel(rec)` closure instead of a `channels` map, threaded `renderQueue` → `buildQueueRow` → `buildChannelBadge` and straight into `renderPlayerMeta`. The two policies are pure and tested in `queue.js`: **`subscriptionChannelInfo(rec, channels)`** is the map ALONE — a record-carried `channelAvatarUrl` is deliberately ignored, because `index.html` is the page that *writes* `yqa_channels` and its `state.channels` is the authority (so a stored video self-heals on the next refresh) — while **`stashChannelInfo(rec, channels)`** takes the record's own avatar first and the map as fallback (see The Stash). Both fall the TITLE back from the record to the map, and `buildChannelBadge` feeds that one resolved title to both the avatar `alt` and the visible name, so a card can never show two answers for one channel. `channels.html` calls `buildAvatar({ title, avatarUrl }, true)` directly — `sortChannels` already yields exactly that shape, so no video record is faked. `toast.js` — notifications.
- `player.js` — YouTube IFrame API wrapper; holds **no queue/app state** (callbacks wire it to whichever page module created it). Uses the **standard `youtube.com`** IFrame API, not `youtube-nocookie` (standard domain feeds watch history when signed in).
- `page-chrome.js` — leaf **page chrome** shared by every entry point, with no app state and no queue logic: `requestTabLock(name)`; the fatal-storage screen family — `showFatalStorageError` plus `showBlockedError`/`showDbUnavailableError`/`showSupersededError`/`showDbReadError`, where **first cause wins** (one screen per page load, since one fatal condition routinely produces another and every screen ends in Reload anyway); `describeError`; `reportIfFatalDb` (for `.catch()` on best-effort writes, so a mid-session stand-down surfaces instead of silently no-oping); `initCurtain({ node, exemptSelector, narrowQuery, coverOnWheelDown })`; and `bindIframeFocusGuard(getIframe)`. Everything that varies per page is a **parameter** — lock name, curtain node, iframe getter — so a new entry point gets the chrome without this module learning about it. Imports only `ui.js`, `toast.js` and the two error classes from `store.js`, and owns **no keyboard shortcut**: Esc stays in each page's own keydown table.
- `subscriptions-page.js` — entry point for **`index.html`**, and the wiring/state hub (`state` object + `dom` refs); the only module that reaches into every layer. Owns event binding, its page's keyboard shortcuts, onboarding, `cleanup()`, `setVideoState`/`toggleSkip`, refresh orchestration, and its **single-tab guard** (see Gotchas) — the sole user of the `yqa_tab` Web Lock. It also writes the **`stash`** object store, through `addCardToStash()` behind a card's "⋯" menu and the `t` key (one `putStashVideo` upsert — see The Stash), so `stash.html` is not that store's only writer.
- `stash-page.js` — entry point for **`stash.html`** (the domain model is in The Stash above). A deliberate **sibling** of `subscriptions-page.js`, never a subclass — importing that module would boot the other page. Self-sufficient: it carries its own Client ID setup panel (same ids as `index.html`, one implementation of the flow), so a brand-new browser can be set up here. Smaller purely by omission — no fetching, no FLOOR/CUTOFF, no stats, no hide-marked filter, no jump-to-last-skipped, and no keys for any of them. The **only** way records enter **through this page** is the add form (the other entrance is `index.html`'s "Add to stash" — see The Stash): `parseVideoId` → `getVideosByIds` → `attachAvatar` → `addToStash` → `putStashVideo`, and **all** of its feedback is a toast — errors, the duplicate notice, the progress messages and success alike (an inline status line under the field appeared and disappeared per message, reflowing the page on every add; moving only some cases would have kept the jump for the rest). The field itself keeps only `aria-invalid` on a parse failure — validity state, not a message — cleared by the next keystroke. Shares `yqa_playback_speed` / `yqa_default_speed` with the subscriptions page — one global player setting — and holds the `yqa_stash_tab` lock.
- `channels-page.js` — entry point for the standalone **`channels.html`** page (reached from the shared nav strip — plain same-tab navigation): channels alphabetically with per-channel prefs — an Ignore toggle and a preferred-speed toggle mirroring the card 1× / 1.5× / 2× buttons. Imports `migrations`/`store`/`queue`/`ui`/`page-chrome` — **never `subscriptions-page.js`** (importing it boots the whole app). No auth, no API calls, and it **never writes video records** (multi-tab safe, and it therefore takes no tab lock): it only reads `loadChannels()` and reads/writes `yqa_channel_prefs` (`LS_CHANNEL_PREFS`; shape `{ [channelId]: { ignored?: true, speed?: number } }`, only non-default values stored — pure helpers `sortChannels`/`setChannelPref`/`isChannelIgnored`/`channelPreferredSpeed` live in `queue.js`). Its whole chrome is `initCurtain({ exemptSelector: '.channels-main', coverOnWheelDown: false })` plus an Esc-only keydown handler wired to it.

### State & marking

`STATE_NEW='new'` vs `STATE_SKIPPED='skipped'` are the only states, declared **once in `config.js`** and imported everywhere (including `queue.js`) — never redeclare them per-module, a copy that drifted would have the writers persisting one value while the queue derivations still keyed off the other; **"handled" everywhere means `state !== 'new'`**. There is **no state normalization on read** — it was safe to delete because nothing anywhere compares `=== STATE_SKIPPED` (it is only ever a value *written*; every read is `=== 'new'` or `!== 'new'`), so a legacy `watched`/`not_interested` record already behaves exactly like `skipped`. `computeQueue` (still-`new` after floor) drives the "Queued" count; `computeVisible` (all states after floor) is the render list. Marking is **two functions**: `setVideoState(videoId, nextState, opts)` does the actual work and **never toggles** — it sets the state as given; `toggleSkip(videoId, opts)` is the Skip button / `x` key wrapper that picks `rec.state !== STATE_NEW ? STATE_NEW : STATE_SKIPPED` (so **any** handled value returns to `new` in one press) and delegates. Auto-mark-on-video-end calls `setVideoState` directly and always SETS `skipped`. `stash-page.js` mirrors this exactly, its wrapper named `toggleRemove` after that page's "Remove" label — same two states, same pick, so the label is display only and **no third state exists**. UI updates optimistically (grey in place, no re-render) then persists async, reverting on failure. `u` undoes the last mark.

### Player behavior

Auto-advance on `ENDED` marks the finished video `skipped` and plays `nextPlayable` (next later `new` **and embeddable** video; non-embeddable ones open on youtube.com). Watch position is polled every 5s and persisted for resume. Playback speed carries across videos via `effectiveSpeed` (per-video preferred > default-speed setting > current), applied through `player.js`'s `setSpeed`/`getSpeed`. Like is a `videos.rate` write; the liked flag is stored **locally only** and never fetched back. On `index.html` the Like button is **not** gated on being signed in — it authorizes on demand — and the ORDER matters: authorization happens **before** the optimistic flip, so a cancelled sign-in leaves the heart exactly as it was and there is nothing to revert. `state.liking` (not auth state) is what disables the button for the duration, so a second click — or the `l` key — cannot stack a second token request while the consent popup is open.

With nothing loaded, the empty overlay offers a **"Start the queue"** button (`#start-queue-btn`; "Start the stash" on `stash.html`) that plays `firstPlayable` — the oldest still-`new`, embeddable video — through the same `playVideo()` a card's Play button uses. `updatePlayingControls()` in **each** page module derives the button **and** the text from **one** condition — `!state.playing && firstPlayable(…)`, over `state.visible` on the subscriptions page and `state.records` on the stash — so the overlay shows **exactly one of {button, text}**, never both (a "Select a video to play" prompt beside a button that does exactly that is a contradiction) and never neither. Consequence: a queue drained to "all caught up" and then refilled by a refresh flips back to a working button on that refresh's `render()`, with no stale message — `state.playerCaughtUp` is a **text-selector only** and can never suppress a live button. The button is **hidden, not disabled**, so it never sits dead in the tab order, and `firstPlayable` scans that **full** list: Hide-skipped and the render window limit what is *rendered*, not what can be *played*. The same `state.playing` hides the whole now-playing bar (`#player-bar` — title + meta + Like / speeds / Skip), a **visibility layer only**: every control keeps its own `disabled` logic underneath. `.player__frame` sizes from its own `aspect-ratio` and the pane is top-aligned, so the bar coming and going below it never moves or resizes the video.

### Refresh: "Fetch new" vs "Refresh all"

Signed out is not a special case: `runRefresh` raises `state.refreshing` (which is also what stops a second click stacking a second token request) and then `ensureAuthorized`s inside the click, so **one** click on a signed-out page both authorizes and fetches. Both call the same `runRefresh(bound, sweepSpeeds)`; only two things differ — the per-channel lower bound (the floor for "Refresh all" (full), or `incrementalSince(records, floor, buffer)` for "Fetch new": newest stored `publishedAt` minus a 6h buffer) and the channel-speed sweep flag (see below). Upsert-by-`videoId` preserves existing state; neither resets or duplicates. Known limit: "Fetch new" won't pull the back-catalog of a newly-subscribed channel — use "Refresh all".

Per-channel prefs (`yqa_channel_prefs`, edited on `channels.html`) are read **fresh inside `runRefresh`** — never cached at startup — so edits made in a Channels tab apply to the next fetch without reloading the main tab. Ignored channels are skipped entirely in the per-channel loop (no uploads request at all — saves quota; their existing records are untouched).

A refresh is also the **only** channel-pruning site (`pruneStaleChannels` → the pure `pruneChannels` in `queue.js`, called after the merge **and** the post-sync `cleanup()`, so it sees that refresh's final record set): a `yqa_channels` entry — and its `yqa_channel_prefs` entry — is dropped only when the channel is **both** absent from the freshly-fetched subscriptions **and** has zero stored records, so an unsubscribed channel with videos still queued keeps its avatar/title and drops on a later refresh once they drain. The sweep covers the **union** of both maps (deduped, channels keys first), so an **orphan** prefs entry — one with no `yqa_channels` entry, from a hand edit or from before pruning existed — is judged by those same two conditions rather than lingering forever; each map is written only when it actually changed, since a prune can touch just one. **An empty (or non-array) subs list prunes nothing** — that reads as a failed fetch, not as "unsubscribed from everything" — and the prune never runs on the `init()` or "Trim front" cleanup paths, which have no subs list. It is silent (no toast) and re-reads the prefs fresh at the prune site.

The whole merge lives in the pure `mergeRefresh(existing, incoming, prefs, { sweepSpeeds })` in `queue.js`: it upserts, then applies each channel's `speed` via `applyChannelSpeeds(records, prefs, onlyVideoIds)` — applied to the **merged** set, so brand-new arrivals are included. `mergeAndPersist` in `subscriptions-page.js` is only `mergeRefresh` + one write + `recompute`, so `queue.test.mjs` exercises the real composition rather than a mirror of it. The rule is **fill-if-absent**: a record whose `preferredSpeed` is unset (`undefined` *or* `null`) and whose channel has a speed gets it; a record with an explicit per-video speed is **never** overwritten or cleared; ignored channels are excluded.

**How far the fill reaches depends on the refresh mode**, passed explicitly as `runRefresh(bound, sweepSpeeds)` — never inferred from the bound:

- **"Refresh all"** (`sweepSpeeds = true` → `onlyVideoIds = null`) sweeps the **whole stored record set**, so older already-stored videos get the channel's speed too.
- **"Fetch new"** (`sweepSpeeds = false`) passes only the videoIds this fetch **newly inserted** (computed inside `mergeRefresh` as incoming ids minus the **stored** ids — the merged set no longer tells arrivals apart). It doesn't touch the older part of the queue, so it doesn't re-speed it either — videos re-returned inside the 6h buffer window count as already-stored and keep what they have.

Either way it stays one write — `mergeRefresh(...)` then a single `putVideos`. `mergeAndPersist` has one call site per exit path — normal completion, and the quota-abort branch that merges what it has and then throws — so exactly one of them runs per refresh, and both derive the scope the same way from `sweepSpeeds`. Known limits (accepted): after un-ignoring a channel, "Fetch new" won't backfill videos published while it was ignored — use "Refresh all"; and toggling a card's speed OFF just removes `preferredSpeed` (`onCardSpeed` sets it to `undefined`, with no "cleared by user" marker), so a later **"Refresh all"** re-applies the channel speed to that video ("Fetch new" does not).

## Conventions

- **`queue.js` must stay pure** — no `window`/`document`/`fetch`/`localStorage`/`IndexedDB` anywhere in it, so `queue.test.mjs` can import it under Node; `config.js` is its only permitted import. New pure logic goes here **with a matching test**.
- **XSS-safe DOM** in `ui.js`/`toast.js` — all API-derived strings go through `textContent`/text nodes; never `innerHTML` for API data; ids go through `encodeURIComponent`.
- Keep the layering: persistence in `store.js`, network in `api.js`, DOM in `ui.js`, shared page chrome in `page-chrome.js`, orchestration in the `*-page.js` entry points, `player.js` state-free.
- All localStorage keys are namespaced `yqa_`.
- The app **never auto-fetches** — signing in only authorizes; the user triggers fetches explicitly. The converse is also true and is why nothing is auth-gated: a triggered action **authorizes itself** on demand (`ensureAuthorized`) rather than requiring a prior sign-in. The explicit Sign in / Sign out buttons and the status label stay on both queue pages — they *display* auth state, and Sign out is not otherwise reachable — but they gate nothing.
- **README stays light** — it carries the setup/OAuth guide and the non-obvious gotchas, and nothing else; depth belongs here in CLAUDE.md. Behavior a user can see by just looking at the app (a new button, a bar that hides itself) goes in **neither** file.

## Gotchas

- **Cross-origin iframe swallows keyboard/wheel/pointer events.** Clicking the video moves focus into the youtube.com iframe and kills document-level shortcuts (including Esc). `bindIframeFocusGuard(getIframe)` in `page-chrome.js` — called by both player pages — detects focus landing on the iframe on window blur and blurs it back (skipped when the document is hidden, so alt-tabbing doesn't yank focus). Preserve this contract when touching focus/keyboard code.
- **Privacy curtain** (`#curtain`): on **all three pages**, from `initCurtain()` in `page-chrome.js` (which owns the covering flag — no page mirrors it). Wheel-down outside the exempt scroll area covers the page with a full-viewport overlay, wheel-up lifts it, Esc toggles it (each page wires Esc from its own keydown table). Whether wheel-**down** may cover is decided by **layout, not width**: `index.html` and `stash.html` set `body.app-active` — a `100dvh` flex column whose `.workspace` panes scroll internally — so covering steals no scrolling and they take the default `coverOnWheelDown: true`. `channels.html` has no `app-active`, so its **document** scrolls at every width; it passes **`coverOnWheelDown: false`**, because a curtain that covered on wheel-down there would make the channel list unscrollable. The `narrowQuery` (≤900px stacked layout) encodes that same rule by width, for the pages that do cover. **Wheel-up and Esc work everywhere, at every width.** Purely visual — it does not pause the player.
- **Single-tab guard**: **two** lock names now, one per page that **writes** an object store — `TAB_LOCK` (`yqa_tab`, `index.html` → `videos`) and `STASH_TAB_LOCK` (`yqa_stash_tab`, `stash.html` → `stash`). A second tab **of the same page** yields; the holder is never interrupted. **A Subscriptions tab and a Stash tab may be open simultaneously** — that is precisely why there are two names over two object stores. Their writes are no longer strictly **disjoint** — `index.html`'s "Add to stash" writes the `stash` store too — so what keeps the guard sound is the shape of that write: a single `putStashVideo` upsert of one videoId, against a stash list re-read fresh with `getAllStashVideos()` at the moment of the add, so the dedupe is judged on real current data rather than a snapshot this page has been holding. It can therefore never clobber what a Stash tab wrote; the residual cost is **staleness, not corruption** — an open Stash tab won't show the new video until it reloads, which is the app's standing "no cross-tab sync" behavior rather than a new hazard. `channels.html` asks for **neither** (it writes no video records). The mechanism is `page-chrome.js`'s `requestTabLock(name)`: it takes the name as a parameter and returns the granted/not-granted **answer** as its own promise. Each page's `init()` fires it at the top and awaits it at its checkpoint, immediately after `cacheDom()` — before the store read, the settings restores, the stash's remove-sweep and `bindEvents()`; not granted → `standDownForOtherTab()` + `showSupersededError()` behind the shared `#blocked-overlay`, having read no records, written nothing and bound no handlers. `cacheDom()` is the checkpoint's only prerequisite: `showFatalStorageError` resolves its nodes by id and wires its Reload button inline. The grant is held for the document's lifetime by a callback promise that never settles (so `request()` never settles either — hence the separate answer promise), and the browser releases it when the document dies. Race-free by construction: no handshake, no simultaneous-open window, and a frozen background tab still holds its lock. A superseded tab binds no shortcuts at all (the checkpoint precedes `bindEvents()`), so there is nothing live behind the overlay; `standDownForOtherTab()` stays as depth-in-defense, making any write that somehow ran throw rather than persist — and since its flag is per-database it stands that document down from **both** stores, which is what a superseded tab deserves. Decided once at startup — no mid-session halt, nothing to do about the player. **Fails open, never closed:** without `navigator.locks`, or if the request throws or rejects, the tab boots normally — the guard must never lock the owner out of their own queue.
- **An author `display` beats the UA `[hidden]` rule**, so anything hideable needs its own `[hidden] { display: none }` in `styles.css`. Buttons are covered wholesale by the general **`.btn[hidden]`** rule, which replaced a special-case `.player__empty-btn[hidden]` — and in doing so fixed a real, pre-existing bug: `setVisible()` sets the `hidden` attribute, `.btn` is `inline-flex`, so `#signout-btn` was rendering while "hidden" on `index.html`. The same reason gives `.player__bar`, `.player__empty`, `.player__description`, `.queue` and `body.app-active #app-main.app` their own `[hidden]` rules — the last needs that exact selector to out-specify the `0-1-3-1` rule above it, or the fatal-storage overlay leaves the app focusable in the a11y tree behind it. Miss one and the "hidden" element stays on screen.
- Keyboard shortcuts live in **two** `onGlobalKeydown` tables — `subscriptions-page.js` and `stash-page.js` (the same gestures minus refresh / hide-marked / jump-to-last-marked, which that page has no controls for) — plus a small **Esc-only** handler in `channels-page.js`. All ignore Ctrl/Cmd/Alt combos and typing in inputs; **Esc is the panic key and is handled *before* those guards** on every page and in every state, so the curtain works mid-typing, during onboarding and with a card menu open — that menu closes itself on the press but neither stops nor prevents the event, so one keystroke both dismisses it and covers the page (leaving it open would strand two document listeners behind the curtain). **`t` stashes the focused card**, on `index.html` only (from the stash there is nothing to stash to): it sits beside `x` and `1`/`5`/`2`, calls the same `addCardToStash` the "⋯" menu item calls, and passes `{ advanceFocus: true }` — as `x` does and the Skip button does not — so a run of `t`s walks the queue instead of firing twice on one card. **No key opens the menu**: with `t` there a keyboard user never needs it, so its trigger is its only way in, and opening leaves focus *on* it. **"The focused card" is whichever `.row` *contains* `document.activeElement`** — `closest('.row')`, in both tables, for `j`/`k`, `x`, `t` and `1`/`5`/`2` — so those keys keep working from any control inside a card (the "⋯" trigger, its item, Play, Skip, a speed button), where an exact match made every one of them inert. It also makes `j`/`k` the way **out** of an open menu: they focus the `.row` itself, leaving the `.row__menu` wrapper for its `focusout` to dismiss — hence both **clamp** at the ends of the list rather than doing nothing there, or a menu on the first or last card would have no `j`/`k` exit. **`Enter` and `Space` are the deliberate exception, matching the `.row` exactly**: each natively activates a focused button or link, so resolving them through the containing card would double-act — activate the control *and* run the shortcut. Don't tidy that inconsistency away. (`1`/`5`/`2` move no focus, so a menu stays open over the speed it just set.) `ui.js`'s **capture-phase** `document` keydown therefore swallows nothing: its job is that Esc close plus a staleness check that runs first — a card can be dropped without `renderQueue` (Hide-marked on, `setVideoState` removes the card it just marked; auto-advance-on-`ENDED` does it to the playing card, whose menu may be open), leaving a detached panel that still holds both document listeners, so `!panel.isConnected` retires the menu and lets the key through untouched. It self-checks rather than being notified because `ui.js` owns the menu and both its listeners; notification would be a new obligation on every page module at every site that drops a card.
- Shorts detection is a duration ≤90s heuristic (badge only — the API exposes no isShort flag).
