# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A pure client-side "burn-down queue" for YouTube subscriptions: fetch videos from your subscriptions up to a moving cutoff, display them oldest→newest, and play/skip through them. Three static pages, each with its own entry-point module — `index.html` (the queue), `stash.html` (a second, hand-curated queue) and `channels.html` (per-channel prefs). Vanilla HTML/CSS/ES modules — **no build step, no framework, no bundler, and no `package.json` or `node_modules` anywhere in version control**: the app and everything committed have zero dependencies, and since deploy = push to `main`, anything committed is shipped. The only runtime dependencies are three Google-hosted scripts (Google Identity Services, YouTube IFrame API, YouTube Data API v3). There is no exception to that anywhere on disk: browser verification runs through the Playwright **MCP server** in-session, which installs nothing into the repo and writes only a gitignored `.playwright-mcp/` scratch directory. See `.claude/skills/browser-test/SKILL.md`.

```

```
Then open `http://localhost:5173`. The served port must match an **Authorized JavaScript origin** on your OAuth Client ID (see OAuth setup in README.md — each user brings their own Client ID; there is no shared one, no API key, no client secret).

**Test:**
```
node js/queue.test.mjs
node js/migrations.test.mjs
```
Two suites, both plain Node `node:assert`, no test framework, zero dependencies. Each runs every test top-to-bottom and throws on the first failure — there is **no filter/single-test runner**; to isolate one, comment out the others in the file. These two suites stay the first stop for anything pure.

**Deploy:** GitHub Pages serves the repo root of `main` directly. There is no CI and no build/deploy step — **deployment = push to `main`**. Live at `https://branets-dasha.github.io/youtube-queue-app/`.

## Architecture

### The FLOOR vs live CUTOFF model (core domain concept)

Two distinct ISO timestamps, both in localStorage, are the heart of the app. Understand these before touching queue logic:

- **FLOOR** (`LS_START_CUTOFF` = `yqa_start_cutoff`) — the deletion + fetch boundary. **Moves forward only**, and only inside `cleanup()`. It is the lower bound for the render list, the queue count, and the per-channel lower bound when fetching.
- **CUTOFF** (`LS_CUTOFF` = `yqa_cutoff`) — the live "handled-prefix" marker shown in the stats. **Bidirectional**: `computeCutoff(records, floor)` recomputes it from scratch each call, so it advances as you mark the oldest videos handled and **retreats** when you un-mark one. Always `>= floor`.

`computeCutoff` walks the contiguous *handled* (`state !== 'new'`) prefix strictly after the floor and stops at the first `new` video. It is **tie-safe**: the returned cutoff is always strictly less than the earliest still-`new` video's `publishedAt`, so a handled video sharing a timestamp with a `new` one never pulls the cutoff onto it. Window membership is **strictly after** the cutoff.

`cleanup()` (in `subscriptions-page.js`) is the **only** place videos are deleted and the floor advances: it deletes every present record with `publishedAt <= cutoff`, then sets `floor = cutoff`. It runs in exactly three sites: page-load `init()` (prune-on-reload), after a refresh sync, and the "Trim front" button. Consequence: marked videos stay greyed *in place* (never reordered/removed) until the next cleanup prunes the whole handled prefix.

### The Stash (`stash.html`) — a second queue, deliberately outside FLOOR/CUTOFF

The Stash is a hand-curated companion queue, filled one video at a time — a pasted YouTube link on its own page, or a card's "Add to stash" on the subscriptions page. Nothing is fetched, nothing is deleted by a moving boundary, and **neither the floor nor the cutoff exists for it** — there is no stash timestamp in localStorage at all. Why it can do without them:

- **Order is arrival order.** `sortStash(records)` sorts by **`addedAt`**, oldest first — *not* `publishedAt` — ties broken by `videoId`, with a missing/unparseable `addedAt` sorting **last** (an unstamped record is foreign/hand-edited data, and the tail is where it does least damage). It is the stash's **single sort site**: Phase 3 drag-to-reorder adds an `order` field and changes **only that function**.
- **Deletion is state-based, not position-based.** `stashToClean(records)` returns every handled (`state !== 'new'`) record from **anywhere** in the list, gaps included. Contrast `videosToClean(records, cutoff)`, which is position-based (`publishedAt <= cutoff`) and can therefore only ever delete a contiguous **prefix** — that difference *is* the reason the burn-down queue needs a moving floor and the stash needs none. One implementation (`sweepRemoved()` in `stash-page.js`) backs **both** the "Clean up" button and an on-reload sweep that runs **before the first render**, so a removed card never flashes on screen.
- **No third state.** The mark button reads **"Remove"**, but it stores the same `STATE_SKIPPED`, so `"handled" means state !== 'new'` still holds on both queues. The label is display only (`renderQueue`'s `skipLabel`); the `btn--skip` class is unchanged, so `setCardState` and the CSS are untouched.
- **No dependency on `yqa_channels`.** A stash record carries its own `channelAvatarUrl` (taken free from the already-known map when possible, else one `getChannelAvatars` call), and this page's resolver `stashChannelInfo` prefers it over the map — so `pruneChannels` deleting a channel entry can never blank a stashed card. The map stays as its **fallback**, which is not dead code: records stashed before avatars were captured, and ones whose `attachAvatar` fetch failed, carry none of their own.
- **Adding respects a channel's preferred speed but ignores its Ignore flag.** `addToStash(records, incoming, { addedAt, prefs })` appends, stamps `state`/`addedAt`, and fills `preferredSpeed` from the channel only when the record has none (`undefined` *or* `null`) — the same fill-if-absent rule as a refresh. It reads the **leaf `channelPreferredSpeed`, never `applyChannelSpeeds`**, precisely because that one excludes ignored channels: **Ignore governs what gets *fetched* by subscription, and nothing here is fetched by subscription.**
- **A duplicate keeps its place, and adding it again still means something.** An already-stashed videoId never moves, is never re-stamped and is never refreshed from the incoming copy — it keeps its position, its `addedAt` and its metadata rather than jumping to the end — but exactly two fields can change, because a re-add is a gesture with a meaning. It is **revived** if it was marked Remove (`state` back to `new`): re-adding a video you had removed is the plainest way there is of saying you want it back, and the alternative is to silently do nothing to a record the next Clean up deletes. And an incoming `preferredSpeed` that is **present** — neither `undefined` nor `null`, the same test the fill-if-absent path uses — **overrides** the stashed one. That is one rule serving both entrances rather than two: a subscriptions card carries whatever speed you set on it, while the paste-a-link flow builds its record from `getVideosByIds`, which has no speed to carry, so there it always degrades to "keep what the stash has". A duplicate is deliberately **not** run through the channel-prefs fill — it went through that when it was first stashed, and a channel speed set since is not a statement about a video already sitting here — so it takes an explicit incoming speed and nothing else. The return is `{ records, added, changed, record }`: **`changed` is what a caller persists on** (true for an arrival, true for a duplicate one of those rules touched), while `added` only picks the wording of the toast — "already in your stash" for an untouched duplicate, "already in your stash — updated it" for a touched one, since the first alone would be a lie by omission the moment a re-add un-marks something. A duplicate nothing happened to is the one case that still comes back **by identity**, so "there is nothing to write" stays visible to the caller as an identity check; a touched one comes back as an updated **copy substituted at the same index** of a new array, so the function still mutates neither input.
- **The second way in costs no network and no auth.** A subscriptions card goes to the stash straight from the queue — its card menu's one item, "Add to stash", or the `t` key — through `addCardToStash` in `subscriptions-page.js`: it runs that same pure `addToStash` over a freshly-read `getAllStashVideos()` and a freshly-read `loadChannelPrefs()`, then one `putStashVideo`. Unlike the paste-a-link form there is **no `ensureAuthorized`, no `getVideosByIds`, no `getChannelAvatars`** — the record that page already holds is complete, and the avatar comes free from `state.channels`, the map it owns; the avatar is copied onto the record (the key **omitted entirely** when there is none, never an explicit `undefined`) for exactly the reason a hand-added record carries its own. Two decisions worth preserving: the stash write happens **before** the source card is marked — the same ordering rule as the Like button, so a failed write leaves the card untouched and there is nothing to revert — and an **already-stashed** video is still marked whatever the add did over there (nothing, an un-mark, a new speed), because "it is in the stash now" is true in all three cases; only the toast and the write itself vary, and the write happens exactly when `addToStash` reports `changed`. The mark is `setVideoState(id, STATE_SKIPPED)`, never `toggleSkip`: a mark, not a toggle, so using the menu on a card that is already skipped cannot un-skip it.
- **It syncs across tabs, and the merge protects only what is mid-write.** `index.html`'s "Add to stash" writes this store from a tab holding a *different* lock — inserting a record, or *updating* one already there — so a Stash tab can be looking at a list that has already moved on. Every committed write to the `stash` store posts a bare signal on one `BroadcastChannel` (`STASH_SYNC_CHANNEL` = `yqa_stash_sync`) from inside `store.js`'s private `putOne`/`deleteAll` — the same argument that keeps `migrateVideos()` inside `readAll()`: a future stash write cannot forget it. `stash-page.js` listens, coalesces a burst behind one short timer (`STASH_SYNC_COALESCE_MS`), re-reads `getAllStashVideos()` and merges with the pure `reconcileStash(current, fresh)`. The message **carries no records on purpose** — IndexedDB is the single source of truth, and a payload would be a second copy of it, stale the moment a message is missed. **`reconcileStash(current, fresh, inFlight)` takes MEMBERSHIP from `fresh`, and CONTENT from `fresh` too — except for the videoIds this tab has a write IN FLIGHT for:** it adds a videoId only `fresh` has, drops one `fresh` lacks, and for a videoId in **both** takes `fresh`'s content unless that id is in `inFlight`, in which case the local object is kept untouched. That exception is the whole point of it, and the thing not to "simplify" into a wholesale replace: this page marks **optimistically** (`setVideoState` sets `rec.state` in memory and only *then* awaits the write), so for the length of that write **disk is behind memory** for that one videoId, and adopting it would re-read the pre-mark state and silently un-mark the card the user just clicked. It is scoped to in-flight ids and **must not be widened back to "every videoId we already hold"**: the other tab *updates* existing stash records now — re-adding a stashed video revives it — so a record this tab is not writing has to be free to change out from under it, or a remote un-mark would never land here. `stash-page.js` supplies that scope as `inFlightWrites`, a **refcounted** Map keyed by videoId that its one write helper `persistRecord` brackets around every `putStashVideo` (refcounted because two writes for one id can overlap — a mark then an un-mark — and the first to settle must not clear the guard the second stands behind; released when the write *settles*, failure included, since the revert that follows a failure puts memory back to what disk already says). Nothing else in that module calls `putStashVideo`, so a new write site cannot forget the guard — the same argument that keeps the broadcast inside `store.js`'s `putOne`. It returns `{ records, changed }` and leaves sorting to the caller, exactly as `addToStash` does, so `sortStash` stays the single sort site; `changed` covers **membership moving OR a record we hold coming back with different content** (a shallow whole-record field compare, in which an absent key differs from a present `undefined` one) — membership alone was sufficient only while local content always won, and a remote un-mark has to re-render — while a record that was *kept*, in flight or byte-identical to disk, is never a change, and **no change means no re-render at all**. When one does run it goes through `renderKeepingPlace()`, which restores the queue pane's `scrollTop` and re-focuses the same control inside the same card, by index among that card's *focusable* controls — anything in a hidden subtree is skipped, since a card menu's panel is hidden whenever it is closed and a re-render closes it, so restoring onto an item in there would drop focus to `<body>`: `renderQueue` empties and rebuilds the `<ul>`, and every *other* `render()` call site follows a gesture that then places focus itself (Clean up focuses the first card, an add scrolls to the new one), so this is the first re-render nobody asked for. The player lives in the other pane and is untouched.
- **Only the stash syncs, and only one way.** `videos` has a single writer that the `yqa_tab` lock keeps single, so a `videos` broadcast could never have a consumer; and `subscriptions-page.js` subscribes to nothing in return — it holds no stash state, re-reading `getAllStashVideos()` inside `addCardToStash` on every add. The asymmetry is deliberate, in the same spirit as "seven, not eight": do not generalize it into a per-store mechanism.

`parseVideoId(input)` is the front door: anchored regexes, **not `new URL()`** (which throws on the protocol-less input we must accept, and a bare id is not a URL at all), covering `/watch?v=`, `/shorts|embed|live|v/`, `youtu.be/`, and a bare 11-char id, with lookalike hosts ruled out by the `^` anchor. All five helpers are pure, live in `queue.js`, and have tests.

### Module layering (respect these boundaries)

Data flows `auth → api → store → queue → ui/*-page.js → player`. There are **three entry points**, one per page, all named `*-page.js`: `subscriptions-page.js` (`index.html`), `stash-page.js` (`stash.html`), `channels-page.js` (`channels.html`); `page-chrome.js` is the leaf chrome all three share. All three pages carry the **same nav strip** in `.topbar__row` (`Subscriptions | Stash | Channels`) with the current page rendered as a `<span aria-current="page">` instead of a link, and the same `<h1>` "YouTube Queue" — page identity comes from `aria-current` + `<title>` + the tagline, not from the heading. Each module owns one concern:

- `config.js` — constants only (storage keys, `API_BASE`, `OAUTH_SCOPE`, states, tunables), each declared **exactly once** for the whole app; no module redeclares one locally. Also the IndexedDB identity (`IDB_NAME`, `IDB_VERSION`, `IDB_STORE_VIDEOS`, `IDB_STORE_STASH`, `IDB_KEYPATH`) and the two Web Lock **names** — `TAB_LOCK` = `yqa_tab`, `STASH_TAB_LOCK` = `yqa_stash_tab` — which are lock names, **not** storage keys, despite the `yqa_` prefix. Same again for `STASH_SYNC_CHANNEL` = `yqa_stash_sync` (a BroadcastChannel name) and its `STASH_SYNC_COALESCE_MS` tunable — see The Stash. `QUEUE_PAGE_STEP` = **10** is the other tunable of that kind: how many items of the queue walk one PageUp/PageDown covers — a count of cards, not a screenful of pixels (see Gotchas). It is `queue.js`'s only import, so it must stay free of browser globals too or the Node tests break — and it is the one module every layer may import, which is why `page-chrome.js` taking a constant from it does not breach its "no layer module" rule.
- `auth.js` — Google Identity Services **token model**. Access token is **in-memory only, never persisted** (so sign-in re-approves on every fresh load); silently re-requested near expiry / on 401. Scope is `youtube.force-ssl` (read + `videos.rate` write for the Like button). **`ensureAuthorized(clientId, { forceNew })` is the single composed “authorize on demand” gesture** — `waitForGis()` → `initAuth(clientId)` → `ensureToken({ interactiveFallback: true })` — called by **every** API-backed control on both queue pages (Fetch new, Refresh all, Like, the stash's Add, and Sign in itself), always straight from the click handler so the GIS popup keeps its user-gesture exemption. It lives here, not in a page module, because this layer already owns the token model and takes the `clientId` as a parameter; one copy is what keeps the two pages identical (it replaced a page-local `ensureAuthReady()` on `stash-page.js`). It reads no storage and touches no DOM — the caller still supplies the Client ID — and it **throws** rather than call `initAuth(null)` when that id is missing. It carries **no once-per-load memo**: `initAuth` is already idempotent per Client ID (and re-initializes on a *changed* one, so “Change Client ID” mid-session can never authorize against the stale client), and `waitForGis` resolves synchronously once GIS is up, so a cached “prepared” flag would only be a second thing to keep in sync with the id. `forceNew: true` swaps the token step for `requestToken({ interactive: true })` and is for the two cases where the token we already hold **is** the problem: the 401/403 re-consent retry behind Like (where `ensureToken` would hand back the same scope-less token and the retry would fail identically), and Sign in (no session to reuse). Everything auth.js throws is a **plain `Error` with no `.kind`** — GIS not loaded, a token request already in flight, a missing Client ID, a cancelled/blocked popup — so it falls through any `ApiError`-only routing: each page's error router needs its non-`ApiError` tail (`describeAuthFailure` on the subscriptions page, `describeAddFailure` on the stash) or the user gets raw internal text.
- `api.js` — `fetch` to the YouTube Data API v3, `Bearer` token, **no API key**. **`search.list` is never used** (too expensive). Uploads playlist id is derived with the **UC→UU trick** (`uploadsPlaylistId()` swaps the leading `UC` of a channelId for `UU`) — no API call. Channel avatars ride along free in `subscriptions.list`. `videos.list` is batched ≤50 ids/call. `getVideoDetails` requests `part=contentDetails,status,snippet` and returns the **snippet identity fields too** (`title`/`channelId`/`channelTitle`/`publishedAt`/`thumbnailUrl`) — they were always fetched and thrown away, so widening it cost **zero** extra quota and is backward compatible. On top of it: `getVideosByIds(ids)` assembles **full records** in the same shape the playlist path builds (record assembly stays here, next to its sibling producer, rather than migrating into a page module) and adds **no new request path**; `getChannelAvatars(ids)` is one `channels.list?part=snippet` batch, called only for a channel not already in `yqa_channels`. Ids/channels the API omits are simply absent from the result. Errors are `ApiError` with a `kind` (`auth`/`quota`/`forbidden`/`notfound`/`network`/`http`). Quota is 10,000 units/day.
- `store.js` — video records in **IndexedDB**: **one** `yqa` database at `IDB_VERSION` **2**, holding **two** object stores that share the keyPath `videoId` and the same record shape — `videos` (the burn-down queue, written by `index.html`) and `stash` (`IDB_STORE_STASH`; the curated queue, written by `stash.html`, whose records carry `addedAt` + `channelAvatarUrl` on top). Two stores rather than one flagged store so the queues can never collide on a videoId. The `videos` store has exactly **one** writer, `index.html`; the `stash` store has **two** — `stash.html`'s add form and `index.html`'s "Add to stash" card menu — so the pages are **not** strictly disjoint writers, and what lets both tabs be open at once is instead the *shape* of every stash write: the single-key upsert `putStashVideo`, never a whole-set put (see the single-tab guard). **IndexedDB is required — there is no localStorage fallback for videos.** **Roll forward, never back:** `IDB_VERSION` went 1 → 2 to add `stash`, and v1 code opening a v2 database gets a `VersionError` → `req.onerror` → the sticky `dbUnavailable` flag → the permanent "Storage unavailable" wall, for **every user who has already loaded v2**. Since deploy = push to `main` with no CI, `git revert` is the natural rollback and would be **worse than any bug it undoes** — fix forward, never revert past a version bump. (The 1 → 2 changeover itself costs each user exactly one "close the other tabs and reload" screen, from a v1 tab still holding the DB open.) Three triggers in `openDb()` mean genuinely **unavailable** — no `indexedDB` global, `indexedDB.open()` throws, or `req.onerror` — and each sets a sticky module flag, after which every video API throws `DbUnavailableError` and the page halts startup with a blocking full-screen error naming the likely causes (site data blocked for this origin, corrupt DB, full disk). **Distinct case:** `onblocked` (another tab holds the DB open at a different schema version) — the real data is in IndexedDB but inaccessible, so every video API throws `DbBlockedError` and the page halts startup with a blocking full-screen error (`#blocked-overlay`, shared by both via `page-chrome.js`'s `showFatalStorageError`) telling the user to close the other tabs and reload. The open success path installs `db.onversionchange` (a future schema upgrade started by another tab): it closes this connection and flips the same sticky blocked flag, so the other tab's upgrade is never blocked and subsequent video APIs here throw `DbBlockedError`. The **third** setter of that same flag is the exported `standDownForOtherTab()` — called only by a page's single-tab guard (below), it sets `dbBlocked` and closes this connection, deliberately reusing the flag rather than adding a fourth one: the condition is identical (the data is there, this page must not touch it, close the other tab and reload), so no new guard lines are needed. **The memoized open, both sticky flags, `onversionchange`, `onblocked` and `standDownForOtherTab()` are per-DATABASE, never per-store** — do not "fix" this into per-store granularity: a database that cannot be opened, or that another tab owns, is equally unusable for every store inside it, and standing a superseded tab down from *both* queues is exactly what its caller wants. The **seven** video APIs (`getAllVideos`/`putVideo`/`putVideos`/`deleteVideos` and `getAllStashVideos`/`putStashVideo`/`deleteStashVideos`) are thin wrappers over five private helpers parameterized by store name — `openGuarded`, `readAll`, `putOne`, `putAll`, `deleteAll` — so the store names never leave this module and the guard order is written down **exactly once**: `openGuarded` checks `dbBlocked` **before** `dbUnavailable`, because an aborted blocked upgrade can set both flags and "close the other tab(s)" is then the actionable message. **Seven, not eight: there is deliberately no bulk stash put** — `stash.html` may be open beside a queue tab, so every stash write is the one-key upsert `putStashVideo`, which cannot clobber what that tab just wrote the way a whole-set `putAll` would. That reason has since doubled: `index.html` writes this store too ("Add to stash"), from a tab holding a *different* lock, so a bulk put from there would overwrite a live Stash tab's entire list rather than one key of it. `putAll` therefore has exactly one caller, `putVideos`. Do not restore the symmetry. **Every committed `stash` write also announces itself**, for cross-tab sync: `putOne` and `deleteAll` post on the stash's BroadcastChannel from `tx.oncomplete` — *after* the commit, so a listener that re-reads on the signal can never see the pre-write state — guarded by the store name, so the announcement sits beside the write instead of in the two public wrappers that could forget it (`putAll` is not a site: it never gets the stash store). **One** channel object does both the posting and the delivering to the exported `onStashChanged(handler)`, and that is load-bearing: a `BroadcastChannel` never receives its *own* posts, so a tab is never woken by its own write — a second channel object in the same document would be, and every local mark would bounce straight back. Lazy and defensive: no `BroadcastChannel` global (or a constructor that throws) leaves it null forever and every write still works, just without sync, and a failed post never fails a write that already committed. Settings/floor/cutoff/channels/speeds all in localStorage (`getPlaybackSpeed`/`setPlaybackSpeed` for `yqa_playback_speed`, `getDefaultSpeed`/`setDefaultSpeed` for `yqa_default_speed`), plus `loadChannelPrefs()`/`saveChannelPrefs()` for `yqa_channel_prefs` (an empty map removes the key). Holds **no migration logic of its own**: the localStorage read paths are plain parses, and `readAll()` — the single `getAll` path behind **both** stores — hands its result to `migrateVideos()` from `migrations.js`, so a record migration covers the stash by construction instead of silently fixing one store and leaving the other on the old shape.
- `migrations.js` — **every** data migration, so retiring them later is deleting this file plus its **four** call sites (`store.js` `readAll()`, and `init()` in each of the three `*-page.js` entry points). No browser globals at import time, so `migrations.test.mjs` imports it under Node; `localStorage` is touched only inside one function body. Exports exactly three, all idempotent, all tolerant of malformed entries: `migrateVideos(records)` — record shape, run on **every** IndexedDB read of **either** store (mutates + returns, nothing written back, so no `IDB_VERSION` bump — the next put persists the new shape). `migrateChannelPrefs(prefs)` — the same per channel-prefs entry, in memory (an entry a migration leaves with no properties is dropped: it reads identically to an absent one). `migrateLocalStorage()` — the one-shot on-load pass **all three** entry points run before anything reads prefs, and the only one that rewrites storage **on disk** (write only if the shape changed; empty map removes the key), so the read paths stay plain parses; never throws when storage is unavailable. **Documentation convention:** a function's JSDoc states only its general contract, while each individual migration is a date-marked `// YYYY-MM-DD — <name>: …` comment inside the body and is explained **nowhere else** — retiring one is deleting its block plus its tests; the file goes when the last block does. Imports `config.js` only — **never `store.js`**, which imports it.

All the derivations: `computeCutoff`, `computeQueue`, `computeVisible`, `videosToClean`, `nextPlayable`/`firstPlayable` (one private `isPlayable` rule — still `new` **and** embeddable — shared by both, so eligibility is declared once), `incrementalSince`, `resumeStart`, `effectiveSpeed`, `applyChannelSpeeds`, `mergeRefresh`, duration/shorts helpers, the two channel-display resolvers (below), and the stash's five (`parseVideoId`, `sortStash`, `stashToClean`, `addToStash`, `reconcileStash` — see The Stash above).

That is why *it* belongs in the bag and `skipLabel` does not, and the callbacks-only rule still holds, because `cardMenu` **is** a callback: the labels are what it *returns*, not what the bag *stores*. It runs during row construction, once per card — keep it **cheap and side-effect-free**. `ui.js` maps the descriptors to `.row__menu-item` buttons and knows nothing of what they do; `subscriptions-page.js` returns the one "Add to stash", `stash-page.js` no `cardMenu` at all, so its cards are untouched. With it `ui.js` holds its **first interaction state**: one module-level reference to the single open menu (opening a second closes the first, so at most one is ever open) plus the module's only document-level listeners — a capture-phase `keydown` and a `pointerdown` — both removed by `closeCardMenu()`, which `renderQueue` calls **before** it clears the list, so a menu whose DOM is about to be discarded never leaves a live listener or a dangling reference behind. The windowing footer button is this module's **second** piece of interaction state, and deliberately not a module-level one: **`renderQueue` gives "Show all (N)" a busy label (`Loading…`) and DEFERS `more.onShowAll`**, so the page's expansion runs one *painted* frame after the activation instead of in the same task — on a queue of thousands, building the cards takes long enough that the page visibly freezes, and nothing said the click had registered. It lives here rather than in the two page modules for the same reason the label does: `ui.js` builds this button and owns its text, so the idle label to restore on failure and the re-entry flag are just **closure variables of the button being built** — born fresh with each render, dying with it, nothing to reset — while a page-side version would be this code twice over a node `ui.js` created. Each half of the deferral is load-bearing: style, layout and paint happen only once the current task ends (so setting the text and expanding together paints *nothing*), and `requestAnimationFrame` callbacks run **before** that frame is painted — hence a **`setTimeout(…, 0)` scheduled from inside a rAF**, whose task is the first thing to run after the frame carrying the label. The guard is a plain flag and **never the `disabled` property**: disabling the focused control drops focus to `<body>`, and the arrows land a keyboard user on exactly this button. If `onShowAll` throws, the idle label goes back and the flag clears — the re-render that removes the button is what failed, so the button is still on screen — and the error is rethrown untouched. The menu's **only** way in is its own trigger, and `ui.js` exports nothing for it, so no page module ever names `.btn--menu` or `.row__menu-panel`. It is a **disclosure, not an ARIA menu**: no `role="menu"` on the panel, no `role="menuitem"` on its items, no `aria-haspopup` (which announces a menu/dialog/listbox) — only **`aria-expanded`** plus an **`aria-controls`** naming the panel's per-card id, built with `encodeURIComponent` like every other id here, and that pair *is* the whole disclosure contract. The roles came off because **opening moves no focus**: the trigger keeps it, for a mouse click and a keyboard activation alike, so the same key pressed again toggles the menu shut — while the ARIA menu-button pattern *requires* focus to enter the menu on open, so keeping the roles while refusing that would describe the widget to a screen reader as something it is not. A plain container needs no accessible name, so the panel's `aria-label` went with its role; the trigger keeps its own "More actions". The trigger renders **no text at all**: its three dots are a `content` on `.btn--menu::before` in `styles.css` (the stylesheet's only `content`), so the glyph and the font that must draw it are declared in one place instead of two files that have to agree — and generated content cannot reach the accessible name, which `aria-label` already fixes at "More actions". **Tab reaches the items** because the panel is the trigger's next sibling inside the wrapper, and leaving is what dismisses: a **`focusout` on the `.row__menu` wrapper** whose `relatedTarget` is outside it closes the menu, which is what stops a Tab from stranding one open behind the card it left (it covers Shift+Tab and clicking away too). Three closers, not one — focusout, the outside `pointerdown` and Esc — because focusout alone misses a click on something unfocusable. `relatedTarget: null` (focus fell into the player iframe — see that gotcha) is safe to treat as *left* here: this widget only asks whether focus is still inside itself, and it is not. Closing **restores focus to the trigger only while focus is still inside the panel** (an Esc press or an item being used); a focusout-driven close passes `restoreFocus: false` and leaves focus exactly where the user is taking it. `buildAvatar(info, decorative)` renders an **already-resolved** `{ title, avatarUrl }` and holds **no** resolution policy of its own: every page passes a `resolveChannel(rec)` closure instead of a `channels` map, threaded `renderQueue` → `buildQueueRow` → `buildChannelBadge` and straight into `renderPlayerMeta`. The two policies are pure and tested in `queue.js`: **`subscriptionChannelInfo(rec, channels)`** is the map ALONE — a record-carried `channelAvatarUrl` is deliberately ignored, because `index.html` is the page that *writes* `yqa_channels` and its `state.channels` is the authority (so a stored video self-heals on the next refresh) — while **`stashChannelInfo(rec, channels)`** takes the record's own avatar first and the map as fallback (see The Stash). Both fall the TITLE back from the record to the map, and `buildChannelBadge` feeds that one resolved title to both the avatar `alt` and the visible name, so a card can never show two answers for one channel. `channels.html` calls `buildAvatar({ title, avatarUrl }, true)` directly — `sortChannels` already yields exactly that shape, so no video record is faked. **`renderPlayerTitle(container, rec)` is the same trick one level up**: the now-playing title is an `<a class="row__title">` — the *card's* class, not a new one — rendered into the page's unchanged `<p id="player-title" aria-live="polite">`, `rec = null` clearing it. It is a link because the frame is deliberately out of the tab order (see that gotcha), so the video's own page was unreachable from the keyboard; it borrows `.row__title` for the same reason `renderPlayerMeta` borrows `row__channel-link` / `row__channel` / `row__dot` / `row__time-abs` — the bar and a card must not be able to drift — and, concretely, because that class is what sets `color: var(--text)` and `text-decoration: none` over the stylesheet's bare `a { color: var(--accent) }`, so it looks exactly like the plain text it replaced, and brings a `:focus-visible` ring nobody has to write twice. The `<a>` is a **child** of the container rather than the container itself: the id, the tag and the live region are untouched, an empty player is an empty paragraph (no anchor, so no tab stop and no stale `href` to strip), and an inline anchor changes the paragraph's box by nothing — the whole bar measures identically. All three watch URLs (`buildQueueRow`'s title + thumbnail, this, and `renderDescription`'s timestamp base) come from **one private `watchUrl(videoId)`** here, so "the same URL shape" is enforced rather than asserted; it stays in `ui.js` rather than moving to `queue.js` because it is the href half of the DOM these functions build, not a domain derivation. `toast.js` — notifications.
- `player.js` — YouTube IFrame API wrapper; holds **no queue/app state** (callbacks wire it to whichever page module created it). Uses the **standard `youtube.com`** IFrame API, not `youtube-nocookie` (standard domain feeds watch history when signed in). ### State & marking

`STATE_NEW='new'` vs `STATE_SKIPPED='skipped'` are the only states, declared **once in `config.js`** and imported everywhere (including `queue.js`) — never redeclare them per-module, a copy that drifted would have the writers persisting one value while the queue derivations still keyed off the other; **"handled" everywhere means `state !== 'new'`**. There is **no state normalization on read** — it was safe to delete because nothing anywhere compares `=== STATE_SKIPPED` (it is only ever a value *written*; every read is `=== 'new'` or `!== 'new'`), so a legacy `watched`/`not_interested` record already behaves exactly like `skipped`. `computeQueue` (still-`new` after floor) drives the "Queued" count; `computeVisible` (all states after floor) is the render list. Marking is **two functions**: `setVideoState(videoId, nextState, opts)` does the actual work and **never toggles** — it sets the state as given; `toggleSkip(videoId, opts)` is the Skip button / `x` key wrapper that picks `rec.state !== STATE_NEW ? STATE_NEW : STATE_SKIPPED` (so **any** handled value returns to `new` in one press) and delegates. Auto-mark-on-video-end calls `setVideoState` directly and always SETS `skipped`. `stash-page.js` mirrors this exactly, its wrapper named `toggleRemove` after that page's "Remove" label — same two states, same pick, so the label is display only and **no third state exists**. UI updates optimistically (grey in place, no re-render) then persists async, reverting on failure.

### Player behavior

Auto-advance on `ENDED` marks the finished video `skipped` and plays `nextPlayable` (next later `new` **and embeddable** video; non-embeddable ones open on youtube.com). Watch position is polled every 5s and persisted for resume. Playback speed carries across videos via `effectiveSpeed` (per-video preferred > default-speed setting > current), applied through `player.js`'s `setSpeed`/`getSpeed`. Like is a `videos.rate` write; the liked flag is stored **locally only** and never fetched back. On `index.html` the Like button is **not** gated on being signed in — it authorizes on demand — and the ORDER matters: authorization happens **before** the optimistic flip, so a cancelled sign-in leaves the heart exactly as it was and there is nothing to revert. `state.liking` (not auth state) is what disables the button for the duration, so a second click — or the `l` key — cannot stack a second token request while the consent popup is open.

With nothing loaded, the empty overlay offers a **"Start the queue"** button (`#start-queue-btn`; "Start the stash" on `stash.html`) that plays `firstPlayable` — the oldest still-`new`, embeddable video — through the same `playVideo()` a card's Play button uses. `updatePlayingControls()` in **each** page module derives the button **and** the text from **one** condition — `!state.playing && firstPlayable(…)`, over `state.visible` on the subscriptions page and `state.records` on the stash — so the overlay shows **exactly one of {button, text}**, never both (a "Select a video to play" prompt beside a button that does exactly that is a contradiction) and never neither. Consequence: a queue drained to "all caught up" and then refilled by a refresh flips back to a working button on that refresh's `render()`, with no stale message — `state.playerCaughtUp` is a **text-selector only** and can never suppress a live button. The button is **hidden, not disabled**, so it never sits dead in the tab order, and `firstPlayable` scans that **full** list: Hide-skipped and the render window limit what is *rendered*, not what can be *played*. The same `state.playing` hides the whole now-playing bar (`#player-bar` — title + meta + Like / speeds / Skip), a **visibility layer only**: every control keeps its own `disabled` logic underneath. `.player__frame` sizes from its own `aspect-ratio` and the pane is top-aligned, so the bar coming and going below it never moves or resizes the video.

### Refresh: "Fetch new" vs "Refresh all"

Signed out is not a special case: `runRefresh` raises `state.refreshing` (which is also what stops a second click stacking a second token request) and then `ensureAuthorized`s inside the click, so **one** click on a signed-out page both authorizes and fetches. Both call the same `runRefresh(bound, sweepSpeeds)`; only two things differ — the per-channel lower bound (the floor for "Refresh all" (full), or `incrementalSince(records, floor, buffer)` for "Fetch new": newest stored `publishedAt` minus a 6h buffer) and the channel-speed sweep flag (see below). Upsert-by-`videoId` preserves existing state; neither resets or duplicates. Known limit: "Fetch new" won't pull the back-catalog of a newly-subscribed channel — use "Refresh all".

Per-channel prefs (`yqa_channel_prefs`, edited on `channels.html`) are read **fresh inside `runRefresh`** — never cached at startup — so edits made in a Channels tab apply to the next fetch without reloading the main tab. Ignored channels are skipped entirely in the per-channel loop (no uploads request at all — saves quota; their existing records are untouched).

A refresh is also the **only** channel-pruning site (`pruneStaleChannels` → the pure `pruneChannels` in `queue.js`, called after the merge **and** the post-sync `cleanup()`, so it sees that refresh's final record set): a `yqa_channels` entry — and its `yqa_channel_prefs` entry — is dropped only when the channel is **both** absent from the freshly-fetched subscriptions **and** has zero stored records, so an unsubscribed channel with videos still queued keeps its avatar/title and drops on a later refresh once they drain. The sweep covers the **union** of both maps (deduped, channels keys first), so an **orphan** prefs entry — one with no `yqa_channels` entry, from a hand edit or from before pruning existed — is judged by those same two conditions rather than lingering forever; each map is written only when it actually changed, since a prune can touch just one. **An empty (or non-array) subs list prunes nothing** — that reads as a failed fetch, not as "unsubscribed from everything" — and the prune never runs on the `init()` or "Trim front" cleanup paths, which have no subs list. It is silent (no toast) and re-reads the prefs fresh at the prune site.

The whole merge lives in the pure `mergeRefresh(existing, incoming, prefs, { sweepSpeeds })` in `queue.js`: it upserts, then applies each channel's `speed` via `applyChannelSpeeds(records, prefs, onlyVideoIds)` — applied to the **merged** set, so brand-new arrivals are included. `mergeAndPersist` in `subscriptions-page.js` is only `mergeRefresh` + one write + `recompute`, so `queue.test.mjs` exercises the real composition rather than a mirror of it. The rule is **fill-if-absent**: a record whose `preferredSpeed` is unset (`undefined` *or* `null`) and whose channel has a speed gets it; a record with an explicit per-video speed is **never** overwritten or cleared; ignored channels are excluded.

**How far the fill reaches depends on the refresh mode**, passed explicitly as `runRefresh(bound, sweepSpeeds)` — never inferred from the bound:

- **"Refresh all"** (`sweepSpeeds = true` → `onlyVideoIds = null`) sweeps the **whole stored record set**, so older already-stored videos get the channel's speed too.
- **"Fetch new"** (`sweepSpeeds = false`) passes only the videoIds this fetch **newly inserted** (computed inside `mergeRefresh` as incoming ids minus the **stored** ids — the merged set no longer tells arrivals apart). It doesn't touch the older part of the queue, so it doesn't re-speed it either — videos re-returned inside the 6h buffer window count as already-stored and keep what they have.

Either way it stays one write — `mergeRefresh(...)` then a single `putVideos`. `mergeAndPersist` has one call site per exit path — normal completion, and the quota-abort branch that merges what it has and then throws — so exactly one of them runs per refresh, and both derive the scope the same way from `sweepSpeeds`. Known limits (accepted): after un-ignoring a channel, "Fetch new" won't backfill videos published while it was ignored — use "Refresh all"; and toggling a card's speed OFF just removes `preferredSpeed` (`onCardSpeed` sets it to `undefined`, with no "cleared by user" marker), so a later **"Refresh all"** re-applies the channel speed to that video ("Fetch new" does not).

## Conventions

- **`queue.js` must stay pure** — no `window`/`document`/`fetch`/`localStorage`/`IndexedDB` anywhere in it, so `queue.test.mjs` can import it under Node; `config.js` is its only permitted import. New pure logic goes here **with a matching test**.
- **XSS-safe DOM** in `ui.js`/`toast.js` — all API-derived strings go through `textContent`/text nodes; never `innerHTML` for API data; ids go through `encodeURIComponent`.
- Keep the layering: persistence in `store.js`, network in `api.js`, DOM in `ui.js`, shared page chrome in `page-chrome.js`, orchestration in the `*-page.js` entry points, `player.js` state-free.
- All localStorage keys are namespaced `yqa_`.
- The app **never auto-fetches** — signing in only authorizes; the user triggers fetches explicitly. The converse is also true and is why nothing is auth-gated: a triggered action **authorizes itself** on demand (`ensureAuthorized`) rather than requiring a prior sign-in. The explicit Sign in / Sign out buttons and the status label stay on both queue pages — they *display* auth state, and Sign out is not otherwise reachable — but they gate nothing.
- **README stays light** — it carries the setup/OAuth guide and the non-obvious gotchas, and nothing else; depth belongs here in CLAUDE.md. Behavior a user can see by just looking at the app (a new button, a bar that hides itself) goes in **neither** file.

## Gotchas

- **Cross-origin iframe swallows keyboard/wheel/pointer events.** Focus inside the youtube.com iframe kills document-level shortcuts (including Esc). **Two mechanisms, and they are not interchangeable — keep both.** (1) A **click** on the video still moves focus into the frame, and `bindIframeFocusGuard(getIframe)` in `page-chrome.js` — called by both player pages — detects that on window blur and blurs it back (skipped when the document is hidden, so alt-tabbing doesn't yank focus); focus lands on `<body>`, deliberately, because that is where the arrow walk's re-entry rule expects it. (2) **Tab** must never reach the frame at all, which is what `player.js`'s `detachIframeFromTabOrder()` enforces. The guard alone could not do that job: `.workspace__player` is `tabindex="-1"`, so a Tab out of the focused pane continued into its first focusable descendant — the frame — the guard bounced focus to `<body>`, but **Chrome's sequential-focus starting point stayed on the iframe**, so the next Tab re-entered and bounced again. That was a permanent two-element loop: forward Tab dead for the rest of the session, on both pages, reproducing with **nothing playing** (`ensurePlayer()` runs at startup), and everything after the frame — the now-playing **title link**, the player-meta channel link, `#like-btn`, the three speed buttons, `#skip-btn`, the description's `.player__desc-ts` / `.player__desc-link`, and `#start-queue-btn` — an unreachable island. With `tabindex="-1"` on the frame, Tab from the pane runs title link → channel link → Like → 1x/1.5x/2x → Skip → description links while playing, and lands straight on `#start-queue-btn` when nothing is (the bar and that button are mutually exclusive — see `updatePlayingControls` — so it is the pane's *only* stop in the idle state, never "after the bar"). **Consequence, and it is deliberate: YouTube's own in-frame controls (captions, quality, the scrubber) are NOT Tab-reachable, and that is not to be "fixed".** It is structural, and it is the price the guard was already paying — a frame that keeps focus takes the app's whole keyboard layer with it, so the guard would bounce focus straight back out anyway; the attribute only makes the consequence deliberate instead of an infinite loop. Users who want the native controls use the frame's own right-click / fullscreen or open the video on youtube.com — **and the way to reach that page from the keyboard is the title link**, which is the whole reason `renderPlayerTitle` makes one: the frame's own title is inside the frame, so without it "open this on YouTube" was a mouse-only gesture. Preserve **both** contracts when touching focus/keyboard code.
- **Privacy curtain** (`#curtain`): on **all three pages**, from `initCurtain()` in `page-chrome.js` (which owns the covering flag — no page mirrors it). Wheel-down outside the exempt scroll area covers the page with a full-viewport overlay, wheel-up lifts it, Esc toggles it (each page wires Esc from its own keydown table). Whether wheel-**down** may cover is decided by **layout, not width**: `index.html` and `stash.html` set `body.app-active` — a `100dvh` flex column whose `.workspace` panes scroll internally — so covering steals no scrolling and they take the default `coverOnWheelDown: true`. `channels.html` has no `app-active`, so its **document** scrolls at every width; it passes **`coverOnWheelDown: false`**, because a curtain that covered on wheel-down there would make the channel list unscrollable. The `narrowQuery` (≤900px stacked layout) encodes that same rule by width, for the pages that do cover. **Wheel-up and Esc work everywhere, at every width.** Purely visual — it does not pause the player.
- **Single-tab guard**: **two** lock names now, one per page that **writes** an object store — `TAB_LOCK` (`yqa_tab`, `index.html` → `videos`) and `STASH_TAB_LOCK` (`yqa_stash_tab`, `stash.html` → `stash`). A second tab **of the same page** yields; the holder is never interrupted. **A Subscriptions tab and a Stash tab may be open simultaneously** — that is precisely why there are two names over two object stores. Their writes are no longer strictly **disjoint** — `index.html`'s "Add to stash" writes the `stash` store too — so what keeps the guard sound is the shape of that write: a single `putStashVideo` upsert of one videoId, against a stash list re-read fresh with `getAllStashVideos()` at the moment of the add, so the dedupe is judged on real current data rather than a snapshot this page has been holding. It can therefore never clobber what a Stash tab wrote — and it no longer leaves one stale either: that write announces itself on the stash's `BroadcastChannel` and the Stash tab reconciles in place, with no reload (see The Stash). **Cross-tab sync exists for the `stash` store alone**, precisely because this guard makes it pointless anywhere else: `videos` has one writer that `yqa_tab` keeps single, so nothing could ever be listening. `channels.html` asks for **neither** (it writes no video records). The mechanism is `page-chrome.js`'s `requestTabLock(name)`: it takes the name as a parameter and returns the granted/not-granted **answer** as its own promise. Each page's `init()` fires it at the top and awaits it at its checkpoint, immediately after `cacheDom()` — before the store read, the settings restores, the stash's remove-sweep and `bindEvents()`; not granted → `standDownForOtherTab()` + `showSupersededError()` behind the shared `#blocked-overlay`, having read no records, written nothing and bound no handlers. `cacheDom()` is the checkpoint's only prerequisite: `showFatalStorageError` resolves its nodes by id and wires its Reload button inline. The grant is held for the document's lifetime by a callback promise that never settles (so `request()` never settles either — hence the separate answer promise), and the browser releases it when the document dies. Race-free by construction: no handshake, no simultaneous-open window, and a frozen background tab still holds its lock. A superseded tab binds no shortcuts at all (the checkpoint precedes `bindEvents()`), so there is nothing live behind the overlay; `standDownForOtherTab()` stays as depth-in-defense, making any write that somehow ran throw rather than persist — and since its flag is per-database it stands that document down from **both** stores, which is what a superseded tab deserves. Decided once at startup — no mid-session halt, nothing to do about the player. **Fails open, never closed:** without `navigator.locks`, or if the request throws or rejects, the tab boots normally — the guard must never lock the owner out of their own queue.
- **An author `display` beats the UA `[hidden]` rule**, so anything hideable needs its own `[hidden] { display: none }` in `styles.css`. Buttons are covered wholesale by the general **`.btn[hidden]`** rule, which replaced a special-case `.player__empty-btn[hidden]` — and in doing so fixed a real, pre-existing bug: `setVisible()` sets the `hidden` attribute, `.btn` is `inline-flex`, so `#signout-btn` was rendering while "hidden" on `index.html`. The same reason gives `.player__bar`, `.player__empty`, `.player__description`, `.queue` and `body.app-active #app-main.app` their own `[hidden]` rules — the last needs that exact selector to out-specify the `0-1-3-1` rule above it, or the fatal-storage overlay leaves the app focusable in the a11y tree behind it. Miss one and the "hidden" element stays on screen.
- Keyboard shortcuts live in **two** `onGlobalKeydown` tables — `subscriptions-page.js` and `stash-page.js` (the same gestures minus refresh / hide-marked / jump-to-last-marked, which that page has no controls for) — plus a small **Esc-only** handler in `channels-page.js`. All ignore Ctrl/Cmd/Alt combos and typing in inputs; **Esc is the panic key and is handled *before* those guards** on every page and in every state, so the curtain works mid-typing, during onboarding and with a card menu open — that menu closes itself on the press but neither stops nor prevents the event, so one keystroke both dismisses it and covers the page (leaving it open would strand two document listeners behind the curtain). **`t` stashes the focused card**, on `index.html` only (from the stash there is nothing to stash to): it sits beside `x` and `1`/`5`/`2`, calls the same `addCardToStash` the card menu item calls, and passes `{ advanceFocus: true }` — as `x` does and the Skip button does not — so a run of `t`s walks the queue instead of firing twice on one card. **No key opens the menu**: with `t` there a keyboard user never needs it, so its trigger is its only way in, and opening leaves focus *on* it. **"The focused card" is whichever `.row` *contains* `document.activeElement`** — `closest('.row')`, in both tables, for `ArrowUp`/`ArrowDown`, `x`, `t` and `1`/`5`/`2` — so those keys keep working from any control inside a card (the card menu's trigger, its item, Play, Skip, a speed button), where an exact match made every one of them inert. **`ArrowUp`/`ArrowDown` walk the queue** (they replaced `j`/`k`), and their mechanics are deliberately **not** in either table: both entries call `moveCard(dir)` from `page-chrome.js`'s `initQueueFocus` and `preventDefault()` **only when it reports the key was taken**, so every case it declines keeps its native scrolling. **What they walk is `[card1 … cardN, "Show all (N)"?]`** — the cards, then the windowing footer button when one is rendered, found by its `.queue-more__btn` class. That button is a walk **item, not a card**: ArrowDown off the last card lands on it, ArrowUp from it steps back to that last card **by position** (not to the remembered card — you arrived by coming down off it, so that is where up must return you), and ArrowDown on it clamps. It is deliberately never a card, because the two things being a card *means* — being the target the list is **entered** at, and being what `x` / `t` / `1`,`5`,`2` act on — are both meaningless for it. With no button rendered the last card clamps exactly as before. **Where the keys apply is a question about LAYOUT, not about what happens to hold focus.** In the two-pane layout `body.app-active` is a `100dvh` flex column whose panes scroll *internally* and the document does not scroll at all — so outside `.workspace__player` there is no native scroll for an arrow to belong to, and it belongs to the queue: from the topbar, the Refresh/Sign-in toolbar, the stats, a sticky header button and from `<body>` alike, every one of which *enters* the card list. (The "Show all (N)" footer is no longer in that list — it is now the walk's last item, so a press from it is a **step**, not an entry.) Inside `.workspace__player` it always declines, because the arrows must go on scrolling that pane — which is the whole reason the pane is focusable at all. In the **stacked (≤900px)** layout the queue pane is `overflow: visible` and the **document** scrolls, so there very much is a native scroll to respect and only focus genuinely *inside* `.workspace__queue` is taken. That single rule replaced a `<body>`-shaped special case, and it is what makes the arrows work where `j`/`k` used to from the page chrome. **The remembered card** is what a press from outside the list enters at: a `focusin` on the queue list notes the `videoId` — never the element, since `renderQueue` empties the `<ul>` and rebuilds it, so a node reference would be detached one render later — of the last card that *contained* focus, by that same `closest('.row')` rule, matched later by walking the rows and comparing `dataset.videoId` the way `findCard` does rather than through a `[data-video-id="…"]` selector that would need escaping. It is resolved against the **current** list at use time and falls back to the first card when that video is gone (cleaned up, filtered out, outside the render window) — which is also the answer for a first press with nothing remembered yet. Focus landing on something in the list that is **not** a card — in practice the "Show all (N)" button — leaves the note standing, and the note stays **cards-only**: it answers "where does a press from *outside* the list go", and the footer button is never an honest place to be dropped into a queue. It is not what gets you back off that button either — ArrowUp from it is positional (see the walk, above). Re-entry matters most from `<body>`, where focus lands constantly — `bindIframeFocusGuard` puts it there every time the user clicks the video — so without the remembered card the arrows would effectively stop working after one click. The narrow/wide question is asked as a `narrowQuery` media query — the same 900px breakpoint, written the same way `initCurtain` writes it — rather than by measuring, so there is one way to ask it. Both keys **clamp** at the ends of the walk rather than wrapping, and the clamp does **two** things that must both survive: it still moves focus onto the item, *and* it reports **not**-handled. Landing on the `.row` is how the arrows get focus **out** of an open menu — it leaves the `.row__menu` wrapper, whose `focusout` dismisses it — so a menu on the first or last card would have no arrow exit if the key did nothing at all there. Reporting not-handled is what hands the pane back its native scroll at the ends of the walk, so ArrowDown on the **last item** still scrolls to the bottom of a tall card and on to the end of the pane, exactly as it did under `j`/`k`; a clamp that claimed the key made that unreachable. In the ordinary case the `focus()` is a no-op (the item already had focus) and only really moves anything when focus was on a control *inside* that card. **`PageUp`/`PageDown` and `Home`/`End` walk the same list through the same gate, and the split between them is STEP versus EDGE.** All four **move focus and let the scroll follow**, exactly as the arrows do — the app scrolls in every case, and nothing here rides on the browser's own scrolling. They share `moveCard`'s two private rules — `walkApplies()` and `walkItems()`, reused rather than re-derived — so they decline inside `.workspace__player` (those keys must go on scrolling the description) and, in the stacked layout, act only when focus is genuinely inside `.workspace__queue`; declining means **doing nothing at all**, leaving the native behavior untouched. **`PageUp`/`PageDown` are `moveCard` itself, called with `{ page: true }`** — a step of `QUEUE_PAGE_STEP` (10) walk items instead of 1 — so they inherit the arrows' whole contract unchanged: entering from outside the list lands on the **remembered card** (an entry is an entry; there is no "from" to page away from yet), and the **clamp** at either end places focus and reports **not**-handled, so PageDown on the last item hands the key back and native scrolling finishes the pane just as ArrowDown does there. One function, not two, because the keys differ in nothing but distance; writing the walk resolution, the entry rule and the clamp a second time is precisely the drift `page-chrome.js` exists to prevent. The one thing a page jump does differently is **land its destination at the top of the pane** (`scrollIntoView({ block: 'start' })` after a `focus({ preventScroll: true })`, in that order so the default "nearest" scroll never happens and then gets corrected): under "nearest" a ten-item jump pins the destination against the **bottom** edge with the nine skipped items above it, which reads as a scroll that overshot rather than a page that turned. A single arrow step keeps plain `.focus()`. **`Home`/`End` are absolute** — "the beginning" and "the end" are properties of the *list*, so there is no position to step from and nothing to clamp: `focusEdge(dir)` names the first / last walk item outright, `preventDefault()`s via the same took-the-key boolean (an empty list declines and the keys keep their native meaning), and lets an ordinary `focus()` carry the pane. **End lands on "Show all (N)"** when one is rendered, because there is **one walk and one rule**: ArrowDown off the last card, a PageDown clamp and End all arrive at the same place, and nothing special-cases the footer button. **The native scroll was tried first and deliberately abandoned — do not restore it as a fidelity improvement.** PageUp/PageDown originally went un-`preventDefault()`ed with the focus cursor synced onto the topmost visible card afterwards. A card here is **~383px tall in a ~531px pane**, so a browser page advances barely more than **one card**: the fidelity being preserved was ArrowDown with a frame-watcher bolted on. It also **stalled outright** — a PageDown that landed on the second-to-last card with the bottom already in view scrolled nothing, so the sync re-found the card focus was already on and the key did nothing at all (there is a browser spec for that case). A fixed step of items cannot stall and needs no timing at all. Worth keeping from that attempt, because it will bite anyone writing a spec that asserts on a scroll position: **Chrome animates a keyboard scroll**, ~9 frames for one native PageDown, so a single `requestAnimationFrame` reads a barely-started scroll. The **remembered card updates for free** on all four keys, since each moves focus with a real `focus()` and the `focusin` listener notes it like any other — which is what keeps `/` and re-entry from `<body>` honest afterwards. **None of the four gets a `<kbd>` help line**, deliberately: every entry on those already-crowded lines teaches a key whose effect is *app-specific and unguessable* (`x` skip, `t` stash, `1`/`5`/`2` speed, `/` switch pane, `Esc` curtain), while these four do very nearly what a user already expects paging and Home/End keys to do. **Activating "Show all (N)" destroys the button that was pressed** — `onShowAll` → `render()` → `renderQueue` → `clear(listEl)` removes the whole `li.queue-more`, and with `more` then null nothing replaces it — so both pages place focus by hand afterwards, or it would fall to `<body>`: they read `cardCount()` **before** flipping `state.showAll` and call `focusCardAt(thatCount)` after the re-render, landing on the **first newly-revealed card** (the window only ever grows, so the pre-expansion count *is* the boundary). `focusCardAt` falls back to the last card, then the first, and leaves focus alone on an empty list — not decoration, since the index is measured against a list that has since been rebuilt. Making the button easy to arrow onto is what made this worth fixing: a landing that strands focus is not a landing. **The activation itself is deferred behind a `Loading…` label** — `renderQueue` wraps `onShowAll` rather than either page doing it (see the `ui.js` bullet); focus stays on the button for the length of the wait, held there by a plain re-entry flag and never by `disabled`, and the `cardCount()` / `focusCardAt()` pair above runs inside the deferred callback exactly as it did inline. **`/` throws focus between the two panes** — out of `.workspace__player` back to the remembered card, from anywhere else into `.workspace__player` — at **every** width, and always `preventDefault()`s, because Firefox opens Quick Find on it (it is read off `e.key`, and Shift stays allowed, so a layout that shifts `/` still reaches us). The `<aside class="workspace__player">` in both `index.html` and `stash.html` carries **`tabindex="-1"`**: programmatic focus only, never a new tab stop, and once focused it scrolls natively with the arrows / PageUp / PageDown — which is the entire point, since a long description is otherwise unreachable without tabbing through every control of every card. Its `:focus-visible` ring is restrained, follows the app's `--radius` (an outline traces its element's `border-radius`, so the pane carries one purely to shape the ring), and its `outline-offset` is **non-negative** — the ring sits wholly OUTSIDE the pane's border box. That is not cosmetic: an element paints its outline **before** its descendants, so the inset `-2px` ring this shipped as first was painted over by `.player__frame` (full-bleed, black, flush to the pane's top and left corner), leaving about a quarter of the left segment and a tenth of the top one visible, and on the right it ran through the outer 2px of the scrollbar. Outside the border box nothing the pane contains can reach it, scrollbar included, and it is clipped by nothing: `.workspace`'s grid gap to its left, 12px to its right and below (the `100dvh` column always keeps that bottom padding, so the pane is never flush with the viewport), at every width and in the stacked ≤900px layout too. Do not "fix" it back to inset, and do not reach for a reserved transparent border instead — it costs 2px of pane permanently and needs an `outline: none` this stylesheet has nowhere. With **no cards at all**, `/` out of the player does nothing and leaves focus where it is: there is no honest target, and blurring to `<body>` would be a silent loss. **`Enter` and `Space` are the deliberate exception, matching the `.row` exactly**: each natively activates a focused button or link, so resolving them through the containing card would double-act — activate the control *and* run the shortcut. Don't tidy that inconsistency away. (`1`/`5`/`2` move no focus, so a menu stays open over the speed it just set.) `ui.js`'s **capture-phase** `document` keydown therefore swallows nothing: its job is that Esc close plus a staleness check that runs first — a card can be dropped without `renderQueue` (Hide-marked on, `setVideoState` removes the card it just marked; auto-advance-on-`ENDED` does it to the playing card, whose menu may be open), leaving a detached panel that still holds both document listeners, so `!panel.isConnected` retires the menu and lets the key through untouched. It self-checks rather than being notified because `ui.js` owns the menu and both its listeners; notification would be a new obligation on every page module at every site that drops a card.
- **The player pane's SCROLLPORT is 4px bigger than its content on every side, and that is what stops it clipping its own focus rings.** `.workspace__player` carries `padding: 4px` with an equal `margin: -4px`: the padding pushes the content in, the negative margin pulls the whole box back out, so the video, the now-playing bar and the description land on **exactly the pixels they did before** (asserted in the rig, box for box) and the only thing that moves is the **clip edge**. It exists because `overflow-y: auto` makes the pane a scroll container, which clips **both** axes at its padding box, and `#player-title` / `#player-meta` sit flush against the content-box left edge — so the rings on the title link and the channel badge, which like every ring in `styles.css` are painted *outside* their element, were drawn at x < 0 and sliced flat off. It cannot be fixed from the link's side: a ring that does not overlap its own content must start left of that content, and that content starts on the clip edge. Nor by `overflow-clip-margin` — beside `overflow-y: auto`, `overflow-x: clip` **computes to `hidden`** and the clip margin does nothing (tried, measured). Moving the content instead was rejected because the bar and the description align to the **video's** left edge by design. Two consequences to keep straight. The pane's own ring is 4px further from the video than it used to be, which is why its `outline-offset` came down from `2px` to `0` — as tight as it can be drawn while staying outside the box, and it must **not** go negative to recover the rest, because the scrollbar rides outward with the padding box and the right-hand segment would land on it again. And 4px is exactly `.row__channel-link:focus-visible`'s **left-hand** reach, with nothing spare, deliberately: that link is padded `4px` on that side against an equal negative margin and draws its ring **inset** into the padding, so the ring's outer edge lands precisely on the link's own margin edge — the pane's clip edge. Nothing enforces that any more (the browser rig that asserted "every ring in the pane fits inside the clip box" is retired), so a ring given more reach on that side clips silently: check it in the browser. Its right-hand reach is `8px`, but that side points into the row, not at the clip edge. On the **scrolling** axis the 4px is only headroom at the two ends of the range — content can always be hand-scrolled to a scrollport edge, so a ring on a control the user scrolls off the top still loses its top segment, exactly as in any scroll container and exactly as before. `scroll-padding` was tried for the focus-driven half of that and removed: measured, this pane's focus scrolls never park a control flush against an edge anyway.
- **The channel badge's ring is a PILL drawn INSIDE a box that is padded for it, and the padding is cancelled so nothing moves.** `.row__channel-link` wraps a 36px round avatar plus a line of text; it carries `padding: 4px 8px 4px 4px` against an exactly equal negative `margin`, so the avatar still sits on the row's content edge — aligned with the title above it and, in the player bar, with the video's left edge — while the box it paints into is 4px bigger on three sides and 8px on the right. The ring is `999px` (the house radius) at `outline-offset: -2px`, so it occupies the **outermost 2px of that padded box** and its reach *is* the padding: 4px left and vertical, 8px right. Both numbers matter. **4px** is the whole of `.workspace__player`'s scrollport band (above), so the left cap lands exactly on the clip edge and a wider left padding would clip. **8px** is what buys the clearance on the text side — ~6px at the midline and ~5px at the glyphs' extremes, against 2px and ~1px before — and it is paid for by `.row__dot`, whose `margin: 0 6px` widens the separator's flex gaps from 6px to 12px on both sides, moving the `·` 6px and the date 12px to the right in the card and the player bar alike. That margin sits on the dot rather than on the row's `gap` so the row's gap stays 6px where it is still felt directly: `buildChannelBadge` drops the avatar and the name in as two bare flex items when a record has no `channelId`, and that fallback has no ring to make room for. Two earlier attempts, for the record: a pill on the **unpadded** box put its end caps back through the last glyph of the name and around the avatar's own circumference (that is why the ring was a `12px` rounded rectangle at `+2px` until now — and beside a round avatar it kept 2px at the midline and ballooned at the corners, which is what read as accidental); and an **outset** ring on the padded box reaches 2px further on every side, which the pane's clip band cannot take on the left. One rule serves the card and the player bar, as it always did.
- **Hover is accent, focus is a ring, and nothing in the meta row underlines.** `.row__title` (cards *and* the now-playing title) and `.row__channel-link` are one gesture on two links, so they say it the same way: hover turns the text `var(--accent)`, focus draws the `--focus` ring and does nothing else. The channel link used to underline `.row__channel` on hover **and** again on `:focus-visible` — three idioms for two states, the focus underline competing with the ring that is the focus affordance everywhere else in the stylesheet. Both underlines are gone. **`channels.html`'s `.chan__link` says it the same way** — hover accent on `.chan__title`, no underline anywhere — but its ring keeps the house `1px` offset and takes a **corner radius, not the pill**: `.chan__title` wraps, so that link's box grows tall, and a `999px` radius then makes end caps of half that height, measured cutting through the last glyph of the first line at 400px. It needs neither of `.row__channel-link`'s two departures — its box is a `flex: 1 1 200px` item stretched far past its own text rather than one hugging it, and nothing clips it, `.chan` being no scroll container — so the padded box does not transfer either.
